# v0.87.0 Implementation Plan — Low-Impact Refresh

> **Status:** Planned
> **Target:** v0.87.0
> **Baseline:** v0.86.0
> **Roadmap:** [roadmap/v0.87.0.md](../roadmap/v0.87.0.md)
> **Last updated:** 2026-08-20

## 1. Outcome

v0.87.0 makes pg_trickle a predictable tenant of a busy PostgreSQL instance.
The release must reduce write-path overhead, bound refresh working memory,
avoid scheduler stampedes, yield when application work is contended, and turn
the claim into a blocking benchmark contract.

The release adds or completes:

- a cursor-backed differential pipeline with batch-local staging and apply;
- one canonical batching GUC, `pg_trickle.pipeline_batch_size`;
- measured completion of statement-level CDC batching and capture-time column
  pruning already present in the v0.86 baseline;
- a correctness-safe no-op trigger body while every consumer is inactive;
- load-aware scheduler admission, deterministic jitter, fair dispatch, and
  interval-derived deadlines;
- one `pg_trickle.memory_budget_mb` sizing policy and component high-water
  accounting; and
- a versioned `pgbench` overhead suite that blocks regressions in CI.

LOW-3, the shared-memory change-buffer ring, remains deferred. This release
must first measure the cheaper LOW-1 and LOW-2 changes and publish the result.

### 1.1 Release invariants

- A differential refresh remains one atomic PostgreSQL transaction: target
  rows, downstream CDC rows, frontier advancement, history, and final status
  commit together or all roll back.
- No pipeline batch may advance a source frontier, delete consumed CDC rows,
  or finalize refresh history independently.
- A failed batch cannot leave a partially refreshed stream table visible.
- Committed source changes are never silently dropped to satisfy a memory,
  queue, or change-buffer limit.
- The pipeline holds at most one bounded fetch chunk and one bounded staging
  batch in its own code; PostgreSQL plan nodes are separately limited by the
  effective `work_mem` cap.
- Small, provably non-amplifying deltas retain the current direct single-MERGE
  path. Large or potentially amplifying deltas use the portal pipeline by
  default.
- Exactly one large-delta batching policy remains. QW-9's materialize-all
  branch is removed; `merge_batch_size` is only a one-release alias.
- Statement-level CDC remains the default. Row-trigger mode remains only as
  the existing compatibility fallback.
- Capture pruning is fail-open: incomplete lineage captures all source
  columns rather than risking an incomplete delta.
- An inactive-consumer short-circuit is installed only after every affected
  stream table is marked for FULL reinitialization on resume.
- Load shedding never delays IMMEDIATE maintenance, a correctness repair, or
  a source whose change buffer is at its budget guard.
- Scheduler-originated lock contention yields without incrementing permanent
  error/suspension counters.
- Specific existing limits may be stricter than `memory_budget_mb`, but none
  may make an effective component limit larger than the master budget policy.
- Benchmark gates compare paired configurations on the same runner and fail
  closed when results or budgets are missing.
- No new dependency is required for cursor execution, load sampling, hashing,
  percentile calculation, or benchmark result parsing.

### 1.2 Baseline facts that narrow the implementation

The roadmap describes several items as new that are already implemented on
`main` at v0.86.0. v0.87 must reuse and verify them rather than create parallel
systems:

| Roadmap statement | v0.86 foundation | v0.87 work |
|---|---|---|
| Statement-level batching | `cdc_trigger_mode = statement` creates per-event `FOR EACH STATEMENT` triggers with transition tables in `src/cdc/mod.rs` | Keep it default, close correctness/performance gaps, and gate the measured result. |
| Column pruning | `columns_used`, `source_columns_used()`, `union_referenced_columns_for_source()`, and `resolve_referenced_column_defs()` already select the union of consumer columns plus PK columns | Audit lineage completeness, shared-consumer changes, schema evolution, and wide-table overhead. |
| Unlogged buffers | `change_buffer_durability` already supports `logged`, `sync`, and opt-in `unlogged`; the old boolean alias already exists | Preserve logged default and crash-repair semantics; do not invent another durability mode. |
| Shrinking buffers | deferred cleanup, compaction, TRUNCATE, partition detach/drop, and auto-partitioning already exist | Feed them from the budget/load policy and measure that cleanup remains bounded. |
| Bounded concurrency | per-database and cluster worker limits plus shared worker reservations already exist | Make admission common to all scheduler paths, cap queued starts, and add fairness. |
| Lock etiquette | scheduled lock/statement timeouts, retry classification, and lock-timeout backoff shipped before v0.87 | Derive effective deadlines from the stream-table interval and classify yield separately from failure. |
| Cache/ring bounds | L0/L1/MERGE cache controls, byte tracking, cost-cache capacity, and the fixed invalidation ring exist | Make their effective limits derive from the master budget and expose comparable utilization. |
| CDC benchmarks | two Rust E2E CDC overhead benchmarks and a non-blocking weekly benchmark workflow exist | Consolidate their useful scenarios into the required `pgbench` harness and make the release budget blocking. |

### 1.3 PostgreSQL transaction semantics correction

The roadmap says “commit incrementally (one sub-transaction per batch)” and
lists progressive visibility and per-batch lock release as benefits. PostgreSQL
internal subtransactions do neither: their writes become visible and their
locks are released only when the outer transaction commits. A SQL function
also cannot commit the caller's transaction, and a non-holdable SPI portal
cannot survive a top-level commit.

v0.87 therefore uses one internal subtransaction per batch for bounded error
cleanup while retaining a single outer refresh transaction. This delivers the
memory bound and smaller individual MERGE statements without weakening the
frontier/finalization contract. It does **not** claim progressive visibility or
early row-lock release.

True cross-transaction progressive refresh would require a separate ADR and a
durable continuation/snapshot design. A holdable cursor materializes the whole
result; recreating a delta after every commit can change the snapshot; and
replaying partially applied aggregate deltas is not generally idempotent. None
of those mechanisms belongs in v0.87 or may be smuggled in as a “batch commit.”

The performance documentation and release notes must state this correction.
If actual progressive visibility remains a product requirement, schedule it as
post-1.0 work after a crash-safe multi-transaction protocol is approved.

## 3. Target Design

### 3.1 One differential execution decision

Keep `execute_differential_refresh_with_tuning()` as the one orchestration
entry point. After the existing admission/fallback checks resolve the delta SQL
and apply strategy, choose one of two execution modes:

1. `Direct`: the existing single MERGE/explicit-DML path; or
2. `Pipelined`: a portal over the resolved delta SQL and repeated batch apply.

The decision must be pure and unit-testable:

```text
pipeline disabled only for an explicit compatibility exclusion
OR
direct when pending input rows <= pipeline_batch_size
    AND the parsed operator tree proves output cardinality cannot amplify
otherwise pipelined
```

Do not use planner row estimates alone to prove a delta is small. Joins,
group-rescan, set operations, recursive/fixpoint execution, and other
amplifying shapes enter the portal path even when the input change count is
small. If proof is unavailable, choose the bounded path.

The decision value records a stable reason (`small_non_amplifying`,
`large_input`, `potential_amplification`, or `compatibility_fallback`) for
metrics and benchmark diagnosis. It is not a new user-configurable strategy
registry.

### 3.2 Portal and batch lifecycle

Add a focused refresh pipeline module rather than expanding the already large
MERGE module. The lifecycle is:

1. Resolve frontier placeholders once and produce the delta SELECT separately
   from the current MERGE shell.
2. Create an `ON COMMIT DROP` temporary batch relation from the delta tuple
   descriptor with no rows. Its name is derived only from `pgt_id` and backend
   identity.
3. Open a read-only SPI cursor with `try_open_cursor`, detach it by name, and
   close the opening SPI connection while leaving the portal alive in the same
   transaction.
4. In a fresh SPI session, find the cursor and fetch a small internal chunk.
   pgrx 0.18 retains fetched tuple tables until the SPI session ends, so each
   fetch/copy session must end before the next fetch.
5. Copy fetched tuples into the type-identical temporary relation through one
   narrow safe wrapper around PostgreSQL's table access method APIs. Prefer a
   bulk table insertion primitive; do not serialize arbitrary Datums to SQL or
   issue one SPI INSERT per field/row.
6. Stop filling a batch at the first of:
   - `pipeline_batch_size` rows;
   - the pipeline byte slice derived from `memory_budget_mb`; or
   - portal exhaustion.
7. Apply the batch inside an internal subtransaction using a batch-source
   variant of the existing MERGE/explicit-DML shell.
8. Capture downstream ST deltas for the batch before releasing the
   subtransaction, accumulate checked row counters, truncate the temp batch,
   and continue.
9. Close the portal, run the existing post-apply reconciliation/cleanup
   scheduling once, and return one normal refresh execution result.
10. Let the existing terminal finalizer advance frontiers and history once.

All unsafe tuple-copy code belongs behind a small API with tuple-descriptor
compatibility checks and a `// SAFETY:` comment for every unsafe block. The
wrapper must reject dropped columns, mismatched type OIDs/typmods, malformed
tuple descriptors, and a batch relation not owned by the current backend.

Use a fixed small internal fetch chunk (for example, 256 rows) rather than
adding another GUC. The public batch size controls apply granularity; the fetch
chunk exists only to release pgrx SPI tuple memory frequently and to enforce
the byte ceiling before 4,096 wide rows accumulate.

### 3.3 Batch correctness rules

Before the portal opens, normalize the delta result to the same semantic input
expected by the existing apply shell. Batch boundaries must not change the
result:

- preserve the current D+I ordering invariant;
- order by the stable row identity and action only where ordering is needed to
  keep one logical key group together;
- carry a one-group lookahead across fetches so a logical update pair is not
  split when downstream merged-output capture requires both sides;
- prove or enforce the existing deduplication contract before batching;
- keep user-trigger suppression active for the outer refresh and restore it
  through RAII/transaction rollback;
- run cross-cycle phantom reconciliation once after all batches, not once per
  batch;
- calculate partition range/pruning from the current batch when safe, while
  retaining the existing whole-refresh fallback for unsupported partition
  layouts;
- emit ST-to-ST change-buffer rows in the same outer transaction and preserve
  the existing `downstream_capture_complete` invariant; and
- accumulate inserted/updated/deleted counts with checked arithmetic and fail
  before finalization on overflow.

If one logical key group alone exceeds the byte ceiling, process that group as
one oversize batch, increment the oversize counter, and continue. Splitting a
semantic group or discarding rows is never an acceptable memory response.

### 3.4 Apply-path coverage and fallbacks

The pipeline should consume existing apply decisions rather than implement a
second strategy selector:

| Existing path | v0.87 behavior |
|---|---|
| Normal MERGE | Replace the delta subquery with the current batch relation and reuse generated target/WHEN clauses. |
| Append-only INSERT | `INSERT ... SELECT` from the current batch; preserve downstream capture. |
| Aggregate explicit DML | Reuse DELETE/UPDATE/INSERT templates against the batch relation. |
| User-trigger explicit DML | Keep trigger semantics and pre/post capture; batch only after equivalence tests prove the per-batch result. |
| Range/hash-partitioned ST | Reuse current partition helpers per batch; fall back only for a documented unsupported layout. |
| Citus distributed target | Retain the current Citus-safe DML choice; pipeline only after coordinator/worker equivalence is proven. |
| Fused chain/atomic group | Preserve group atomicity. Disable fusion for a pipelined member and execute the existing per-node path in the same group transaction. |
| Recursive CTE/SCC fixpoint | Do not split a fixpoint iteration until a bounded batch is proven semantically equivalent. Keep the existing path and record the compatibility fallback. |
| FULL/REINITIALIZE/Top-K recompute | Out of scope for LOW-1; these are not delta-MERGE pipelines. Existing memory/timeout guards remain. |
| IMMEDIATE | Already consumes transition tables in the caller transaction; LOW-1 does not replace that engine. |

Compatibility fallbacks must be counted and named. The release cannot claim
the pipeline is universal if a benchmark-relevant shape still bypasses it.
The exit gate requires the portal path to be the default for every large delta
shape supported by ordinary scheduled DIFFERENTIAL refresh; narrow exclusions
above must be documented and covered.

### 3.5 Failure and visibility semantics

Reuse/extract the existing internal subtransaction RAII guard rather than add a
second raw `BeginInternalSubTransaction` wrapper.

- Each batch starts and releases one internal subtransaction.
- A PostgreSQL ERROR rolls back the current batch and is converted through the
  existing scheduler/manual API error boundary.
- The caller then aborts the whole refresh transaction; earlier released
  subtransactions are also rolled back.
- The frontier remains unchanged, consumed buffers remain retained, and the
  retry sees the complete original delta.
- Temp relations and portals are closed by normal cleanup or outer transaction
  abort.
- No batch emits a terminal refresh-history record.

Rows applied by early batches are visible to later commands in the same outer
transaction but not to other sessions. Documentation and tests must use that
precise wording.

### 3.6 QW-9 replacement and GUC compatibility

Add `pg_trickle.pipeline_batch_size` as an integer `SUSET` GUC:

- default `4096`;
- minimum `1`;
- maximum `1,048,576`; and
- applied as the maximum logical rows in one batch, with the memory budget able
  to reduce the effective row count for wide tuples.

Remove the QW-9 branch that maps large deltas to full materialization through
PH-D1. Keep `pg_trickle.merge_batch_size` registered for v0.87 only as a true
alias of the canonical setting. Both names must read and update one effective
value; if pgrx cannot register two names over one setting safely, use a tiny
assignment-hook wrapper rather than an SPI lookup on every refresh.

The generated GUC catalog and `UPGRADING.md` mark the old name deprecated,
state that its semantics are now pipeline apply size rather than a
materialization threshold, and announce removal in v0.88. Diagnostics that
currently recommend `merge_batch_size` must recommend the canonical name.

### 3.7 LOW-1 observability

Extend the existing metrics/shmem surfaces with bounded counters/gauges:

- pipeline/direct refresh decisions by reason;
- batches completed;
- rows and bytes staged;
- largest observed batch rows/bytes;
- oversize logical-key batches;
- compatibility fallbacks by stable reason; and
- batch apply duration histogram inputs or summary counters using the existing
  metrics style.

Do not add a new catalog table. Add per-refresh pipeline fields to durable
history only if benchmark/operations work proves they are needed after the
in-memory metrics exist; the roadmap does not require a second telemetry store.

### 3.8 LOW-2: finish the existing capture fast path

#### Statement-level batching

Treat the current transition-table trigger builders as the implementation,
then harden them:

- verify INSERT, DELETE, keyed UPDATE, key-changing UPDATE, keyless UPDATE,
  TRUNCATE, generated columns, partitioned sources, and tables with user
  triggers;
- retain row mode as an explicit compatibility/testing fallback;
- keep one change-buffer heap open per bulk statement where PostgreSQL permits;
- preserve D-before-I `change_id` ordering and BIGSERIAL `CACHE 1` correctness;
- preserve synchronous-commit policy and one coalesced NOTIFY per transaction;
  and
- benchmark single-row and bulk statements separately so batching does not hide
  a single-row regression.

Do not introduce an in-memory “transition buffer”: PostgreSQL transition tables
already are the native per-statement buffer.

#### Capture-time column pruning

Keep `source_columns_used()` and the dependency catalog as the source of truth.
Audit every expression-bearing parser node so the stored set includes columns
used by projection, filters, joins, grouping, aggregate arguments/filters,
window clauses, subqueries, ORDER BY, row identity, and DVM correction terms.

The effective capture set for a source is:

```text
union(all active and catch-up-capable consumer columns)
+ primary/replica identity columns
+ mandatory CDC metadata
```

Rules:

- `SELECT *`, an unknown/raw expression, missing dependency metadata, or an
  unsupported lineage node forces full-column capture.
- Adding/altering a consumer expands the source trigger/buffer before the new
  consumer can become ACTIVE.
- Dropping or narrowing a consumer may stop populating unused columns, but
  physical column removal waits for existing frontiers and buffer cleanup; no
  blocking source-table rewrite is added merely to save nullable columns.
- Case-sensitive quoted identifiers compare exactly. Do not lowercase catalog
  identifiers for correctness decisions.
- New catalog reads cast `name` values to `text`.

Add a wide-table benchmark with a narrow projection and assert both fewer
captured bytes and equivalent stream-table results.

#### Inactive-consumer short-circuit

A catalog lookup in every DML statement would erase the intended saving.
Instead, reuse trigger generation and install one of two function bodies per
source:

- `capture`: the normal statement/row body; or
- `inactive`: sync guard plus immediate return, with no buffer INSERT or NOTIFY.

Recompute the source's body under the existing source/CDC advisory lock when a
consumer is created, dropped, paused, suspended, resumed, or repaired.

Transition ordering is correctness-critical:

1. When the last capture-requiring consumer becomes inactive, mark all of its
   affected consumers `needs_reinit = true`, commit their inactive state, then
   replace the source function with the no-op body in the same protected
   operation. Extra captured rows during a race are harmless.
2. Before the first consumer becomes active again, restore/synchronize the
   pruned buffer schema and capture body, then expose the consumer as ACTIVE.
3. The resumed consumer performs a FULL reinitialization because changes made
   during the no-op interval were intentionally not captured.

“Paused” must be defined consistently across the catalog pause API and the
shared-memory scheduler pause API. If a transient scheduler pause promises
differential catch-up today, keep capture enabled for that state and limit the
short-circuit to states whose resume path explicitly reinitializes. Do not
silently change pause semantics just to satisfy the fast path.

#### Durability and shrinking

Do not automatically switch logged buffers to UNLOGGED. `logged` remains the
default; `sync` and opt-in `unlogged` retain their current meanings. Verify that
an unlogged-buffer reset is detected and forces FULL repair before a
differential frontier can advance.

Reuse existing cleanup mechanisms in this order:

1. detach/drop fully consumed partitions;
2. TRUNCATE a fully consumed unpartitioned buffer when safe;
3. bounded DELETE/compaction otherwise; and
4. auto-promote hot buffers using the existing partitioning policy.

Cleanup stays after successful frontier finalization and respects the minimum
consumer frontier. No cleanup optimization may remove rows still needed by a
paused-but-catch-up-capable consumer.

### 3.9 LOW-4: scheduler admission under application load

#### One load snapshot per scheduler tick

Add a small `LoadSnapshot` assembled once per database scheduler tick:

- connected client backends / `max_connections`;
- active non-pg_trickle backends not waiting / available CPUs;
- backends waiting on `wait_event_type = 'Lock'`; and
- active pg_trickle refreshes from existing shared worker reservations.

Read PostgreSQL activity counts in one short SPI query. Use
`std::thread::available_parallelism()` as the portable CPU-capacity input; do
not add an OS metrics dependency. The runnable-backend ratio is explicitly a
CPU-pressure proxy, not measured CPU utilization.

Add one calibration GUC, `pg_trickle.load_shed_threshold`, a real `SUSET`
value with default `0.80`, range `0.0..=1.0`; `0` disables load-aware
deferral. Compute pressure as the maximum normalized connection, runnable, and
lock-wait ratios. Enter deferral at the threshold and leave only after two
consecutive samples below `0.75 × threshold`.

The pure pressure/hysteresis function receives all counts and capacities as
arguments and has unit tests without PostgreSQL.

#### Urgency and deferral

Never defer:

- IMMEDIATE work executing in the source transaction;
- a required reinitialization/repair needed to restore correctness;
- a stream table already beyond its declared freshness target; or
- a source whose change buffer reached its budget guard.

For other due work under pressure, multiply the effective interval by
`1, 2, 4, 8` on consecutive overloaded ticks and reduce it one step per healthy
tick. This is scheduler state only; do not rewrite the user's schedule or
target freshness in the catalog.

Increment `load_deferrals_total` and expose current pressure/deferral factor.
Do not record a refresh failure or increase `consecutive_errors` for an
admission deferral.

#### Deterministic jitter and rate limiting

For periodic schedules, derive a stable phase offset from the existing hash
dependency over `(database_oid, pgt_id, schedule_epoch)`:

```text
jitter_window = min(10% of interval, 5 seconds)
offset = hash % max(jitter_window, scheduler_tick)
```

The offset changes only when the schedule epoch changes, so restarts do not
re-synchronize the fleet. CALCULATED schedules use the resolved interval;
MANUAL/IMMEDIATE modes do not jitter. Cron schedules jitter only within a
window that cannot cross their next cron occurrence.

Start no more refresh units in one tick than existing shared worker/admission
permits allow. Do not enqueue durable job rows that cannot receive a permit;
leave those units due for the next tick.

#### Fair queue

Extend the existing priority sort, preserving dependency and consistency
constraints, with a fairness key:

1. correctness-critical/IMMEDIATE kind;
2. overdue ratio (`age / effective interval`), descending;
3. oldest last-dispatch attempt;
4. existing tier priority;
5. stable topological/pgt_id order.

Track last-dispatch attempts in the existing scheduler unit state. A failed or
deferred expensive table remains due but moves behind older eligible peers at
the same correctness priority. Add an aging test proving a cold/expensive unit
eventually runs under a continuous hot workload.

Sequential and parallel scheduler paths must call the same pure admission and
ordering helpers. Parallel execution remains the default; do not build a new
queue service.

#### Bounded concurrency

Use the existing shared worker reservation table as the source of truth for
scheduler-originated concurrency. Inline refreshes must reserve/release a slot
too, so changing worker-pool size cannot bypass `max_concurrent_refreshes` or
the cluster-wide dynamic-worker cap.

Manual refreshes keep their current per-table advisory lock semantics and do
not enter the scheduler queue. If later measurement shows concurrent manual
refreshes can violate the memory promise, add a shared permit at the common
refresh boundary in the same PR as the measured reproducer; do not speculate a
second semaphore before that evidence.

#### Interval-derived lock and statement deadlines

Keep the configured values as hard maxima and derive scheduled values from the
effective interval:

```text
lock_timeout = min(configured_lock_timeout, max(100 ms, interval / 10))
statement_timeout = min(configured_statement_timeout, max(1 s, interval * 4 / 5))
```

Correctness repairs may use the configured maximum because refusing repair can
leave the table unusable. A lock timeout/lock-not-available outcome is a yield:
release the scheduler job/slot, retain the frontier, apply existing exponential
retry backoff plus jitter, and do not count toward suspension. Other statement
timeouts retain the existing typed failure classification.

### 3.10 LOW-5: one sizing policy, five guarded components

Add `pg_trickle.memory_budget_mb` as integer `SUSET`, default `256`, minimum
`16`, maximum `1,048,576`. Implement a pure `MemoryBudget` value that performs
checked byte conversion and derives all effective limits.

The GUC is a master sizing input, not a promise that PostgreSQL's total RSS
equals the number. Shared buffers, executor internals, extensions, and multiple
backends remain PostgreSQL-managed. Documentation must say exactly what
pg_trickle-owned accumulations it bounds.

Divide the budget for in-process state:

| Component | Derived share/policy | Enforcement |
|---|---|---|
| Delta pipeline | 75% of the budget for staging plus executor `work_mem`; row count is additionally capped by `pipeline_batch_size` | End the batch on row or byte limit; set local work memory to the stricter existing/derived cap. |
| Template/plan caches | 15% per refresh backend, divided among existing L0/L1/MERGE caches | Existing entry/byte GUCs may lower the cap; LRU eviction enforces it. L2 catalog cache stays age/row bounded and is not counted as process memory. |
| DAG ready/job queue | 5% in the scheduler backend | Keep only the highest-priority eligible candidates that fit; the rest remain due and are reconsidered next tick. Durable jobs are created only when a permit exists. |
| DDL invalidation ring | 5% logical capacity, capped by the compile-time shared-memory array | Overflow retains the existing full-DAG-rebuild fallback; lowering logical capacity does not pretend to free the fixed preload allocation. |
| Change-buffer growth | One budget-sized byte guard per source, sampled from relation size | Treat as storage/backpressure, not process memory; prioritize drain/compaction and report overflow. Never drop committed rows. |

The shares are constants in one pure function, not five new GUCs. Existing
component settings remain compatibility overrides interpreted as stricter
caps. Add a validation test that derived in-memory shares sum to 100% and use
saturating/checked arithmetic at large values.

#### Change-buffer hard-bound exception

A lossless trigger-based change buffer cannot have a literal hard storage cap
unless pg_trickle rejects or blocks application DML when producers outrun
refresh. That would contradict the release's low-impact promise. v0.87 therefore
uses a byte guard with urgent drain, compaction, backpressure metrics, and an
ERROR health state, but does not discard rows or fail already valid source
writes solely to make the relation fit the GUC.

This is the one explicit exception to a hard ceiling and must be called out in
the docs and exit report. If product policy later prefers bounded storage over
write availability, add an opt-in hard backpressure mode with an ADR; do not
make it the v0.87 default.

#### Comparable utilization and `health_check()`

Add stable `MemoryComponent` values:

- `delta_pipeline`;
- `change_buffer`;
- `invalidation_ring`;
- `template_plan_cache`; and
- `dag_queue`.

Each component reports `used`, `limit`, unit, utilization basis points, high
water, and budget-hit count through internal metrics. Update the existing
component whenever it allocates/enqueues/samples; do not make `health_check()`
perform unbounded history work.

Keep the existing `health_check()` three-column SQL signature. Add one
`memory_budget` row whose detail names the closest component, current/high-water
utilization, and limit. Severity is `OK` below 80%, `WARN` at 80–99%, and
`ERROR` at or above 100%. If a live value cannot be collected cheaply, report
the observed high-water and label it as such rather than reporting zero.

### 3.11 LOW-6: versioned `pgbench` contract

Build one shell entry point plus small SQL/Python support files under a focused
benchmark directory. Reuse the E2E package/container setup and Python standard
library; do not add a benchmark framework.

Run three isolated, otherwise identical PostgreSQL 18 containers:

1. `absent`: stock PostgreSQL, pg_trickle neither preloaded nor installed;
2. `installed`: pg_trickle preloaded/installed, no stream tables; and
3. `active`: pg_trickle installed with a realistic projection, aggregate, and
   join over hot `pgbench` tables.

Use the standard `pgbench` initialization and transaction workload with fixed,
versioned defaults for scale, clients, jobs, warmup, duration, and seed. The
blocking CI profile should run at least three paired repetitions and compare
medians; a longer publication profile may run five or more.

Collect:

- TPS excluding connection establishment;
- transaction p50/p95/p99 from sampled pgbench transaction logs;
- per-command latency for INSERT/UPDATE-heavy statements where available;
- refresh count/duration and correctness after the run; and
- pg_trickle scheduler/refresh-worker CPU jiffies divided by total PostgreSQL
  container CPU jiffies during the sustained active run.

The CPU sampler may read Linux `/proc` in CI because it is benchmark tooling,
not extension runtime code. It must label unsupported local platforms and
fail the blocking Linux job if CPU share cannot be measured.

Produce one machine-readable JSON document containing environment, commit,
extension/PostgreSQL versions, all raw repetitions, medians, normalized ratios,
and pass/fail decisions. A parser validates finite/non-negative numbers and
sample counts before comparison.

Version the defended normalized budgets in the repository. The initial
v0.87 measurement sets:

- installed/no-ST TPS ratio, with the roadmap hard floor of `0.99`;
- active hot-table p99 latency ratio/budget; and
- refresh CPU-share budget.

The first two categories must distinguish product budget from CI noise
tolerance. A candidate may use a small documented statistical tolerance for
run variance, but the published product number remains unchanged. Missing
baseline, missing metric, malformed JSON, incorrect stream-table results, or a
budget regression fails the gate.

Wire the short paired profile into PR CI as a blocking job. Keep the long
weekly workflow for history, but remove `continue-on-error` from the LOW-6
overhead decision job. Do not make unrelated long refresh/TPC-H tracking jobs
blocking merely as part of this release.

Publish the first accepted result in `docs/` with hardware/runner details and
the exact command. Record the LOW-3 decision beside it: the ring stays deferred
unless measured post-LOW-2 capture overhead remains outside the accepted
budget.

## 4. Configuration, API, and Error Contract

### 4.1 GUC surface

| GUC | Type/default | Context | Contract |
|---|---|---|---|
| `pg_trickle.pipeline_batch_size` | integer / `4096` | `SUSET` | Maximum logical delta rows per pipeline apply batch. |
| `pg_trickle.merge_batch_size` | deprecated alias | same backing value | Accepted in v0.87 only; removed in v0.88. |
| `pg_trickle.memory_budget_mb` | integer / `256` | `SUSET` | Master sizing input for the five guarded components. |
| `pg_trickle.load_shed_threshold` | real / `0.80` | `SUSET` | Pressure threshold; `0` disables load-aware deferral. |

No per-component share, jitter, fair-queue, or fetch-chunk GUC is added. The
existing concurrency, cache, timeout, buffer, and partitioning settings remain
and can only make an effective limit stricter.

Every new `pub static PGS_*` setting needs a `///` doc comment so generated
catalog documentation includes it.

### 4.2 SQL surface

No new SQL function is required. Preserve the signature of
`pgtrickle.health_check()` and add the `memory_budget` row. Existing metrics
surfaces gain counters using their established naming/versioning policy.

If operators need exact component values after implementation, prefer one
bounded JSON field on an existing diagnostics function over a new family of
SQL functions. Add it only with an operational consumer/test.

### 4.3 Errors

Add contextual `PgTrickleError` variants only for genuinely new failure
boundaries:

- portal open/find/fetch failure with `pgt_id` and batch number;
- batch tuple-descriptor mismatch;
- batch apply failure with `pgt_id`, batch number, row count, and byte count;
  and
- refresh admission capacity failure if a non-scheduler caller eventually
  needs the shared permit.

Memory guard hits, load deferrals, jitter, and scheduler lock yields are not
errors. SQL-reachable paths must not `unwrap()` or panic; pgrx error conversion
stays at the API boundary.

## 7. Upgrade and Compatibility Plan

Add the direct `0.86.0 -> 0.87.0` upgrade edge and normal release metadata.
No persistent pipeline-progress table is needed because batches are not
top-level commits.

Migration/compatibility rules:

1. Existing stream-table rows, frontiers, change buffers, schedules, and
   refresh history are unchanged.
2. Existing `merge_batch_size` configurations continue to control the
   canonical pipeline batch size for v0.87 and receive deprecation docs.
3. The legacy setting's meaning changes from the QW-9 materialization trigger
   to the maximum pipeline apply size; document the operational difference.
4. Users with neither GUC configured receive the new default `4096`.
5. `change_buffer_durability`, old unlogged alias behavior, and logged default
   remain unchanged.
6. Existing per-component memory/cache settings remain accepted and become
   stricter effective caps under the master policy.
7. Existing pause/resume calls retain their documented catch-up behavior unless
   the implementation explicitly migrates that state to reinitialize-on-resume.
8. `health_check()` retains its SQL row type; clients see one additional named
   check row.
9. No history row is rewritten and no guessed benchmark result is generated
   during upgrade.
10. Fresh install, direct upgrade, and supported chained upgrade must expose
    identical GUC defaults, function signatures, privileges, and generated
    catalogs.

Because GUC registration is binary code, the SQL migration may contain only
the standard version-edge marker unless an existing SQL diagnostics view must
be updated. Do not add catalog columns merely to make the migration look busy.

## 9. Benchmark Method and Release Budget

The implementation PR that introduces the benchmark must commit a reproducible
profile before using it as a gate.

### 9.1 Workload controls

Version in source control:

- PostgreSQL major/minor container image;
- pgbench scale and initialization options;
- workload SQL and stream-table definitions;
- client/job counts;
- random seed;
- warmup and measurement durations;
- repetition count;
- scheduler/GUC settings;
- host/container CPU and memory limits; and
- percentile interpolation method.

Shuffle the order of the three configurations per repetition or rotate it
deterministically to reduce thermal/cache order bias. Recreate the database for
each configuration. Never compare a warmed active database with a cold absent
one.

### 9.2 Result validation

Before accepting metrics:

- pgbench exits successfully with the expected transaction count;
- no PostgreSQL/pg_trickle ERROR appears in logs;
- every active stream table equals its defining query;
- refresh history shows successful work during sustained load;
- CPU samples cover the measurement window; and
- JSON includes all repetitions and environment fields.

Use medians of per-run TPS and percentiles for the gate. Retain raw samples in
CI artifacts so a failure is diagnosable.

### 9.3 Budget bootstrap

The first accepted run on the release runner establishes active p99 and CPU
budgets. Review them against v0.86 and repeat on a second run/day before
committing. Do not pick a threshold from the best sample.

The committed result page must show:

| Configuration | TPS | p50 | p95 | p99 | pg_trickle CPU share |
|---|---:|---:|---:|---:|---:|
| Absent | measured | measured | measured | measured | n/a |
| Installed, no ST | measured + ratio | measured | measured | measured | idle overhead |
| Active STs | measured + ratio | measured | measured | measured + ratio | measured |

It also records the before/after LOW-2 microbenchmark and the explicit LOW-3
decision.

## 11. Risks and Mitigations

| Risk | Mitigation |
|---|---|
| Batch boundaries change D+I or aggregate semantics | Normalize once, keep logical key groups together, run batch-size-1/multi-cycle equivalence, and fall back by named shape until proven. |
| pgrx cursor fetches still accumulate memory | Detach the portal and fetch/copy in separate SPI sessions as required by pgrx 0.18 cursor documentation. |
| Generic Datum copying corrupts values | Type-identical temp relation, descriptor/OID/typmod checks, one reviewed safe wrapper, broad type E2E coverage. |
| Batch failure leaks partial target state | One outer transaction, frontier/finalization after all batches, crash/error E2E tests. |
| Planner materializes/sorts inside the cursor | Derive `work_mem` from the budget, measure temp files/RSS, and distinguish PostgreSQL spill from pg_trickle full-delta staging. |
| Small deltas regress from portal overhead | Retain direct path only when the OpTree proves non-amplification; benchmark the decision boundary. |
| Pipeline duplicates existing apply strategies | Reuse current apply decision/templates and add only a batch source, not another selector. |
| Pruning omits a semantic dependency | Fail-open on unknown lineage, union consumers, always keep identity, and compare against defining query. |
| No-op trigger misses changes needed on resume | Mark reinitialization before disabling capture and restore capture before reactivation. |
| Trigger body replacement blocks application DML | Serialize only infrequent lifecycle changes, benchmark lock duration, and retain capture if replacement cannot complete quickly. |
| Load proxy misclassifies hardware pressure | One documented calibration GUC, portable CPU-capacity input, hysteresis, metrics, and synthetic recovery tests. |
| Load shedding violates freshness | Exempt overdue/repair/buffer-critical work and report deferrals separately from failures. |
| Fairness breaks DAG ordering | Apply aging only after dependency-ready filtering and preserve stable topo order as final key. |
| Queue cap drops work | Do not persist jobs without permits; leave undispatched units due for the next tick. |
| Memory GUC is mistaken for total RSS | Document exact owned components and expose component use/limit; never market it as a PostgreSQL-wide cap. |
| Change buffer cannot obey a hard cap losslessly | Use urgent drain/health/backpressure, never drop rows, and document the explicit soft-storage exception. |
| Benchmark gate flakes on hosted runners | Paired isolated runs, medians, fixed container limits, raw artifacts, validation, and separately documented noise tolerance. |
| Existing non-blocking benchmark hides failure | Add a dedicated blocking LOW-6 job; keep unrelated long tracking non-blocking. |
| Alias semantics surprise operators | Same effective setting, generated deprecation notice, upgrade example, and removal date. |
| LOW-3 returns without durability design | Require the published LOW-2 result plus a new ADR before any ring implementation. |
