# v0.83.0 Implementation Plan — DVM Semantic Fidelity Gate

**Status:** Implemented
**Target:** v0.83.0
**Baseline:** v0.82.0
**Roadmap:** [roadmap/v0.83.0.md](../roadmap/v0.83.0.md)
**Last updated:** 2026-08-15

---

## 1. Outcome

v0.83.0 makes every accepted DIFFERENTIAL and IMMEDIATE query obey PostgreSQL
semantics across the existing DVM operator surface. Unsupported or unprovable
forms must be classified before storage or CDC setup: AUTO uses FULL, while an
explicit incremental mode fails with an actionable error.

The release is complete only when these invariants hold:

1. User-visible INTERSECT and EXCEPT results contain only PostgreSQL result
   columns and exactly the required duplicate multiplicity. Operator counts are
   durable private state, including while a tuple is temporarily invisible.
2. Set-operation branches bind by ordinal after PostgreSQL type coercion.
   Alias differences, NULLs, and composite rows cannot alter equality.
3. Every algebraically maintained non-DISTINCT SUM tracks whether any
   qualifying non-NULL input remains. Statistical maintenance performs
   products in the aggregate's accumulator arithmetic type.
4. Scalar subqueries preserve PostgreSQL cardinality errors. A failing refresh
   changes neither stream-table contents nor its canonical frontier.
5. LATERAL deltas account for every outer dependency and retain enough private
   identity to delete only affected rows. Unsupported IMMEDIATE inner-source
   mutations are rejected.
6. STABLE, VOLATILE, or uninspectable expressions never enter incremental
   maintenance without a specific proof. AST conversion and rewrite failures
   are controlled fallback/error outcomes, not synthetic SQL.
7. Circular admission rejects every operator that can remove or replace output
   as input grows. Only the explicitly proven monotone fragment is accepted.
8. Composite identity encoding is unambiguous for component boundaries, NULL,
   empty strings, arbitrary bytes represented by text, and separator-like user
   values. Persisted state never mixes encoding versions.
9. FULL remains a safe semantic fallback, not an approximation. Any
   unexplained DIFFERENTIAL-versus-FULL mismatch blocks release.

This release adds no SQL operator or aggregate family and does not widen the
documented DVM support matrix. Performance changes are limited to preventing
the correctness fixes from creating an unacceptable hot-path regression.

## 3. Target Design

### 3.1 One semantic admission result

All creation, ALTER QUERY, preview, initialization, reinitialization, and
refresh planning surfaces must consume the same structured semantic result.
Keep this in the existing parser validation module rather than introducing a
second capability framework.

The exact names may follow current types, but the result must distinguish:

```rust
enum IncrementalAdmission {
    Proven,
    FullOnly(Vec<ValidationIssue>),
}

struct ValidationIssue {
    code: &'static str,
    operator: &'static str,
    reason: String,
    hint: String,
}
```

An inspection/conversion error becomes `FullOnly`, not `Proven`. Reserve
`Result::Err` for failures that prevent even FULL execution, such as an invalid
PostgreSQL query or catalog access failure whose safety cannot be classified.

Mode resolution is fixed:

| Requested mode | Admission result | Outcome |
|---|---|---|
| FULL | Either | Accept FULL; report non-applicable incremental diagnostics only in preview/explain output |
| AUTO | Proven | Plan DIFFERENTIAL, subject to the existing runtime cost decision |
| AUTO | FullOnly | Plan FULL and persist/report the reason |
| DIFFERENTIAL | Proven | Accept |
| DIFFERENTIAL | FullOnly | Reject before creating or mutating objects |
| IMMEDIATE | Proven for both DVM and transition-table execution | Accept |
| IMMEDIATE | FullOnly for either capability | Reject before creating or mutating objects |

The same rule applies on ALTER. A rejected ALTER leaves the old defining query,
storage, dependencies, and CDC objects unchanged. `preview_stream_table()` and
explain/diagnostic surfaces must report the same effective mode, issue code,
operator, reason, and remediation hint.

Implement WP0 guardrails first so unsafe set operations, LATERAL IMMEDIATE
mutations, STABLE expressions, uninspectable expressions, and non-monotone
cycles cannot continue while their complete fixes are developed. Remove a
temporary guard only after the corresponding proof tests pass.

### 3.2 Versioned, framed row-identity encoding

Replace delimiter concatenation in `pg_trickle_hash_multi` with a canonical
byte framing:

```text
version | component_count |
    null_tag
  | value_tag | byte_length | UTF-8 bytes
  | ...
```

Requirements:

- The version and component count are fixed-width and endian-defined.
- NULL has a tag and no payload. It cannot collide with a user string.
- A non-NULL component includes its byte length before its exact UTF-8 bytes.
- Empty string is a non-NULL value with length zero.
- Component boundaries do not depend on a reserved user character.
- The implementation writes directly into the existing hasher; it need not
  allocate one concatenated buffer.
- SQL builders use one shared helper for the framed multi-column expression.
  Initial population, scan deltas, trigger CDC, transition tables, polling,
  set state, joins, and row-ID reconstruction may not hand-build variants.
- Single-column `pg_trickle_hash` remains byte-for-byte stable. Only composite
  encoding uses version 2, minimizing unnecessary compatibility changes.

The framing is collision-free as an encoding. The resulting fixed-width hash is
still an accelerator, not a proof of row equality. Every correctness-sensitive
state lookup compares all canonical components with `IS NOT DISTINCT FROM`.
Where a path currently retains only a hash, preserve the original key values
for collision resolution or classify that path as FULL-only; framing must not
be presented as eliminating finite-hash collisions.

Add an internal encoding constant and persist the version:

```sql
ALTER TABLE pgtrickle.pgt_stream_tables
    ADD COLUMN row_identity_version smallint;

ALTER TABLE pgtrickle.pgt_change_buffers
    ADD COLUMN row_identity_version smallint;
```

Fresh objects use version 2. Existing stream tables remain version 1 until a
successful protected FULL reinitialization atomically rewrites row IDs and sets
version 2. A change buffer is set to version 2 only after its writers are
rebuilt and its old rows are cleared under source locks. Differential and
IMMEDIATE preflight reject a stream table or required buffer whose version does
not equal the binary's current encoding.

### 3.3 Canonical positional set schema

Represent each set node with an explicit output mapping derived from the
analyzed PostgreSQL set-operation tree:

- output ordinal;
- left expression/column;
- right expression/column;
- PostgreSQL-selected common output type and collation;
- canonical internal alias such as `__pgt_set_c1`;
- user-visible output name, taken from PostgreSQL's result descriptor.

Do not infer this mapping from raw branch aliases. The right branch is projected
to canonical aliases by ordinal after PostgreSQL-inserted coercions. Nested set
operations use their analyzed child descriptors, not reparsed SQL text.

All grouping and matching SQL uses canonical ordinals. For a candidate state
row, use:

```sql
candidate.row_hash = state.row_hash
AND candidate.c1 IS NOT DISTINCT FROM state.c1
AND ...
AND candidate.cn IS NOT DISTINCT FROM state.cn
```

Value equality always decides the lookup. The hash may narrow candidates only
when the analyzed type/collation and canonical encoding guarantee that values
which PostgreSQL considers equal receive the same hash. Otherwise omit the hash
predicate and use NULL-safe value equality directly. Cover duplicate output
names without relying on name lookup.

### 3.4 Durable private set-operation state

Move set multiplicities out of the user-visible stream table. Add a focused
internal registry for set state; do not create a general-purpose operator-state
framework in this release:

```sql
CREATE TABLE pgtrickle.pgt_set_operation_states (
    pgt_id          bigint NOT NULL REFERENCES pgtrickle.pgt_stream_tables,
    node_ordinal    integer NOT NULL,
    operation       text NOT NULL CHECK (operation IN ('INTERSECT', 'EXCEPT')),
    is_all          boolean NOT NULL,
    state_relid     oid NOT NULL,
    schema_version  smallint NOT NULL,
    PRIMARY KEY (pgt_id, node_ordinal)
);
```

Each registered state relation is permanent/LOGGED and contains:

- canonical typed output columns `c1..cn`;
- a non-unique `row_hash` index accelerator;
- `left_count bigint NOT NULL CHECK (left_count >= 0)`;
- `right_count bigint NOT NULL CHECK (right_count >= 0)`.

Refresh is already serialized per stream table, so state creation/update does
not require a cross-session uniqueness protocol. Nevertheless, every update
must detect duplicate state rows for one null-safe tuple as corruption and fail
closed rather than updating an arbitrary row.

Visible multiplicity is pure logic:

| Operation | Visible multiplicity |
|---|---|
| INTERSECT | `1` when `left_count > 0 AND right_count > 0`, otherwise `0` |
| INTERSECT ALL | `least(left_count, right_count)` |
| EXCEPT | `1` when `left_count > 0 AND right_count = 0`, otherwise `0` |
| EXCEPT ALL | `greatest(left_count - right_count, 0)` |

For every branch delta:

1. Aggregate signed changes by the canonical positional tuple.
2. Lock or create the matching private state row using NULL-safe equality and,
   only where equality-consistency is proven, a hash prefilter.
3. Compute old and new left/right counts; reject either becoming negative.
4. Compute old and new visible multiplicity.
5. Emit `new_visible - old_visible` as the signed user-result delta.
6. Preserve the state row while either side count is nonzero, even if visible
   multiplicity is zero. Delete it only when both counts are zero.
7. Apply the private state and user-result delta in the same refresh
   transaction and finalize only after both succeed.

Positive multiplicity inserts use the existing z-set expansion or
`generate_series` to produce exactly that many physical result rows. Negative
multiplicity deletes exactly that many matching occurrences using NULL-safe
value comparison and transaction-local row selection; it must not require a
user-visible count or duplicate-ordinal column.

Initialization uses the same protected FULL snapshot as the target:

1. PostgreSQL materializes the defining set query directly into the stream
   table, preserving result aliases and ALL duplicates.
2. Each branch is grouped by its canonical positional tuple.
3. A NULL-safe FULL join constructs private left/right state.
4. State and target commit together.

Create, drop, ALTER QUERY, repair, and reinitialization own the registry and
state relations transactionally. ALTER builds new state under the new query,
then swaps metadata only after initialization succeeds. Missing, malformed, or
unlogged state sets `needs_reinit` and blocks incremental refresh.

DIFFERENTIAL and IMMEDIATE set operations remain guarded until initialization,
both branch delta paths, direct unfiltered reads, all four multiplicity rules,
and repeated zero-crossing tests pass. If IMMEDIATE transition-table parity
cannot be proven by the release gate, keep IMMEDIATE rejected while allowing
proven DIFFERENTIAL execution.

### 3.5 Nullable SUM state

Every algebraically maintained, non-DISTINCT SUM receives a non-NULL input
count, independent of join shape. DISTINCT SUM keeps its existing distinct
state and is not redesigned here.

For:

```sql
SUM(argument) FILTER (WHERE predicate)
```

the auxiliary state is equivalent to:

```sql
COUNT(argument) FILTER (WHERE predicate)
```

It counts only rows for which the filter is true and the argument is non-NULL.
Initialization, INSERT, DELETE, UPDATE old/new, group creation, group removal,
and HAVING transitions must update SUM and this count from the same delta.

Final SQL semantics:

- auxiliary count greater than zero: return the maintained SUM state;
- auxiliary count equal to zero: return NULL, even if the group itself is
  non-empty;
- group count equal to zero: remove the group under existing rules;
- `COALESCE(SUM(...), default)` applies COALESCE only after the SUM NULL result
  has been restored;
- FILTER false-to-true, true-to-false, NULL-to-value, and value-to-NULL updates
  are ordinary signed transitions.

Generalize `nonnull_aux_columns`, query initialization, merge SQL, ALTER column
reconciliation, and hidden-column validation. Deduplicate auxiliary state when
the same SUM expression is projected more than once, but do not merge SUMs with
different filters or coercions.

Existing algebraic SUM stream tables cannot backfill this count from their
current result alone. They must reinitialize from source data before
incremental refresh.

### 3.6 Statistical accumulator arithmetic

For the supported STDDEV, VAR, CORR, COVAR, and REGR families, resolve the
analyzed aggregate/operator signature to the existing supported accumulator
arithmetic type. Cast each operand before generating:

- `x * x`;
- `y * y`;
- `x * y`;
- sum-of-squares and cross-product delta terms.

Do not multiply in `smallint`, `integer`, or another narrower source type and
cast the overflowed result afterward. Preserve PostgreSQL's numeric versus
floating-point behavior for each supported signature.

Keep the supported aggregate whitelist closed. If the analyzed signature,
coercion, or arithmetic type cannot be resolved, admission is `FullOnly`; do
not guess from the textual type name and do not extend incremental support to a
user-defined aggregate as part of this work.

Cache catalog-derived metadata for one parse/plan operation and release the SPI
connection before SQL generation. Unit-test the pure expression/type decision
separately from catalog access.

### 3.7 Scalar subquery cardinality and atomicity

Remove both injected `LIMIT 1` clauses from scalar-subquery current and
reconstructed-old snapshots. Generate a true scalar subquery expression so
PostgreSQL raises SQLSTATE `21000` when it returns more than one row.

The cardinality-producing CTE/expression must be a required dependency of the
delta statement, not a planner-prunable side query. Do not catch `21000` and
convert it into an empty delta, first row, FULL fallback, or successful
no-change refresh.

v0.82.0 transaction/finalizer invariants provide atomicity:

- target mutation, auxiliary state, and frontier advancement are in one
  transaction;
- a cardinality error rolls them all back;
- scheduler failure recording occurs only after rollback in its existing fresh
  transaction;
- correction of the source allows the next refresh to replay from the unchanged
  frontier.

Tests must record the target contents, frontier, timestamps, private state, and
successful history before the violation; assert all remain unchanged after the
error; then correct the source and prove convergence.

### 3.8 Complete LATERAL dependency and identity proof

Extend LATERAL parser metadata with:

- every outer `Var` referenced at every nesting level;
- the owning outer relation/node for each reference;
- correlation equality predicates;
- complete outer identity columns for each mutable outer source;
- inner mutable dependencies;
- grouping/precomputation keys;
- whether each reference is directly grouped or functionally determined;
- the internal identity columns required through Project and storage.

Dependency collection walks the analyzed expression tree, including function
arguments, filters, join predicates, grouping, HAVING, ORDER BY, LIMIT/OFFSET,
and nested subqueries. An unresolved reference is `FullOnly`.

Precomputation is admitted only when every outer reference is:

1. present in the precomputation grouping key; or
2. functionally determined by that key through a proven whole-relation primary
   key or non-partial, non-expression UNIQUE NOT NULL constraint.

Partial indexes, expression indexes, nullable unique columns, and catalog
lookup failures do not prove functional dependency.

Carry complete outer identity through the existing internal identity path even
when the user projection omits it. Internal columns must not change the
user-visible result descriptor. Delta deletion joins require a non-empty exact
identity key and NULL-safe equality. SQL generation returns an error if that
key is empty; emitting `ON TRUE` is forbidden.

For duplicate projected outputs, retain enough internal occurrence/multiplicity
state to remove only rows belonging to affected outer identities. Prefer the
existing hidden row-ID/z-set machinery. Add a focused private side relation
only if the existing internal storage path cannot preserve identity without
exposing columns; do not weaken deletion matching.

IMMEDIATE admission:

- reject a LATERAL node when an inner source can mutate and there is no
  transition-table inner-change branch;
- allow only cases whose transition tables cover every mutable dependency and
  whose identity proof passes;
- AUTO may still select FULL; explicit IMMEDIATE receives an operator-specific
  error and remediation hint.

### 3.9 Complete volatility and rewrite validation

Incremental maintenance admits IMMUTABLE expressions only unless a named
operator-specific proof is implemented and tested. v0.83.0 adds no general
STABLE proof, so STABLE is `FullOnly`.

The existing volatility policy/GUC may continue controlling whether a FULL
stream table is allowed, but it cannot override incremental safety:

- AUTO plus STABLE/VOLATILE uses FULL;
- explicit DIFFERENTIAL/IMMEDIATE rejects;
- an uninspectable expression behaves the same as unsafe volatility;
- FULL execution retains PostgreSQL's normal expression semantics.

Complete inspection across:

- target list and nested expressions;
- WHERE and join quals;
- FROM functions and table functions;
- LATERAL expressions;
- GROUP BY and HAVING;
- ORDER BY;
- LIMIT and OFFSET;
- window partition/order/frame expressions;
- scalar and other subqueries;
- SQL/JSON and JSON_TABLE-like expressions;
- casts, collations, overloaded operators, and their resolved function OIDs.

Prefer OIDs from the analyzed PostgreSQL tree. Raw function/operator names are
not enough for overloaded resolution. Keep SPI catalog lookups short and batch
them where possible.

Change fallible AST conversion, expression deparsing, and rewrite helpers to
return a typed unsupported/error result. Audit especially branches that
currently use `if let Ok(...)`, skip SQL/JSON forms, or substitute `TRUE`/`NULL`.
Synthetic constants are allowed only for a proven semantic rewrite, never as
error recovery.

Add a small regression fixture for each inspected clause and each deliberate
conversion failure. Assert requested and effective modes as well as query
results.

### 3.10 Sound circular monotonicity admission

Define monotonicity as: adding input rows cannot remove an existing output row
or replace its value. Reuse one pure recursive decision in create, ALTER,
preview, and cycle validation.

v0.83.0 admission table:

| Operator | Circular admission |
|---|---|
| Scan / projection / filter | Admit when expressions are immutable and children are monotone |
| UNION ALL | Admit when both children are monotone |
| INNER JOIN | Admit when both children are monotone |
| INTERSECT / INTERSECT ALL | Admit only after set-state semantics are proven and both children are monotone |
| Semijoin / EXISTS | Admit only under the existing proven positive-membership form |
| DISTINCT | Admit only with an explicit set-semantics proof in the fixpoint harness |
| LEFT JOIN / FULL JOIN | Reject |
| Anti join / NOT EXISTS / EXCEPT | Reject |
| Scalar subquery | Reject |
| LATERAL subquery or function | Reject |
| Aggregate, window, TopK/LIMIT, or other value-replacing operator | Reject unless an existing specific proof says otherwise |

Return the first non-monotone operator path plus a concise reason and hint.
Do not infer monotonicity only from children when the parent operator can retract
or replace output.

At upgrade/reinitialization, revalidate every existing circular component
before scheduling it. Components that fail move to the repository's existing
non-runnable error/suspended state with the validation issue recorded. Do not
continue them under their old admission result and do not silently convert a
circular component to FULL.

## 4. Error Model

Extend `PgTrickleError` with typed variants, reusing an existing validation
variant where it already carries equivalent structured context:

```rust
IncrementalSemanticsUnsupported {
    mode: String,
    operator: String,
    reason: String,
    hint: String,
}

DvmInspectionFailed {
    clause: String,
    fragment: String,
    reason: String,
}

DvmStateInvalid {
    pgt_id: i64,
    node: String,
    relation: Option<String>,
    reason: String,
}

RowIdentityVersionMismatch {
    object: String,
    expected: i16,
    actual: Option<i16>,
}

NonMonotoneCycle {
    operator_path: String,
    reason: String,
}
```

PostgreSQL scalar cardinality SQLSTATE `21000` should propagate unchanged with
stream-table context added only if the repository's error boundary can preserve
the original SQLSTATE.

Classification:

| Error | AUTO behavior | Explicit incremental behavior | Frontier may advance | Requires FULL reinit |
|---|---|---|---:|---:|
| Proven unsupported semantics during creation/ALTER | FULL | Reject | N/A | No |
| Runtime/state inspection cannot prove semantics | FULL only before mutation; otherwise abort | Abort | No | Depends on state |
| Missing/corrupt private DVM state | Abort and mark for repair | Abort | No | Yes |
| Row-identity version mismatch | Protected FULL | Abort until reinit | No | Yes |
| Scalar cardinality violation | Abort | Abort | No | No; retry after source correction |
| Non-monotone circular component | Reject/suspend component | Reject/suspend component | No | Query redesign required |

Messages include stream-table name, requested mode, operator/clause, a short
query fragment where safe, and remediation: use AUTO/FULL, rewrite the query, or
run the documented repair/reinitialization path.

## 5. Implementation Work Packages

### WP0 — Install semantic guardrails

**Roadmap:** DVM-81-1, DVM-81-5, DVM-81-6, DVM-81-7
**Goal:** Stop known unsafe forms from entering incremental execution while the
complete implementations land.

Changes:

1. Introduce the shared structured admission outcome and one mode-resolution
   matrix for create, ALTER, preview, and reinitialization.
2. Temporarily classify INTERSECT/EXCEPT as FULL-only.
3. Reject IMMEDIATE LATERAL forms with mutable inner sources.
4. Classify all STABLE expressions and inspection failures as FULL-only.
5. Correct circular admission for LEFT/FULL join, scalar subquery, LATERAL,
   anti/EXCEPT, and other clearly non-monotone parents.
6. Replace fail-open rewrite/inspection branches encountered by these paths
   with controlled issues.
7. Add mode-resolution and no-object-on-rejection tests before deeper changes.

**Exit:** AUTO safely uses FULL for every known unproven form; explicit
DIFFERENTIAL/IMMEDIATE fails before storage or CDC mutation; unsafe circular
queries cannot be scheduled.

### WP1 — Version and replace composite identity encoding

**Roadmap:** DVM-81-8

Changes:

1. Extract a pure framed encoder and feed it incrementally into the existing
   production hasher.
2. Add exhaustive examples and proptests for component-boundary ambiguity,
   NULL, empty values, separator/control bytes, Unicode, and composite arity.
3. Centralize composite hash SQL generation and replace all DVM/CDC callers.
4. Add row-identity version catalog fields and runtime preflight.
5. Update trigger, polling, transition-table, initial-load, and scan delta
   builders to use version 2.
6. Add an upgrade fixture containing deliberately colliding version-1
   composites and pending CDC rows.
7. Add a Criterion comparison for single and multi-column hot paths.

**Exit:** No two distinct framed component sequences produce the same encoded
byte stream; every production composite caller uses the same helper; mixed
versions are rejected.

### WP2 — Positional set binding and private state

**Roadmap:** DVM-81-1, DVM-81-2

Changes:

1. Add analyzed positional output metadata to set `OpTree` nodes.
2. Normalize both branches to canonical typed aliases by ordinal.
3. Add the set-state registry and LOGGED per-node state relation lifecycle.
4. Implement pure visible-multiplicity transition logic and negative-count
   corruption checks.
5. Rework INTERSECT/EXCEPT delta SQL to update private state and emit signed
   visible deltas using NULL-safe value equality, with only proven-safe hash
   prefiltering.
6. Rework initialization to populate target and private state under one
   protected FULL snapshot.
7. Remove `__pgt_count_l/r` from user-visible set results and ALTER schemas.
8. Wire drop, repair, query alteration, and reinitialization cleanup.
9. Enable DIFFERENTIAL only after all distinct/ALL and zero-crossing tests pass;
   enable IMMEDIATE separately only after its transition-table matrix passes.

**Exit:** Direct unfiltered reads exactly equal PostgreSQL for all four set
operations, including aliases, NULL composites, duplicates, and repeated
visibility crossings.

### WP3 — Correct nullable and statistical aggregate state

**Roadmap:** DVM-81-3

Changes:

1. Allocate a non-NULL auxiliary count for every algebraic non-DISTINCT SUM.
2. Make initialization and delta maintenance FILTER- and expression-NULL-aware.
3. Restore SUM NULL before outer COALESCE or other projection expressions.
4. Update hidden-column discovery, merge/apply, state validation, and ALTER
   reconciliation.
5. Resolve supported statistical accumulator arithmetic types from analyzed
   signatures/catalog metadata.
6. Cast operands before square and cross-product expressions.
7. Classify unresolved signatures as FULL-only.
8. Add production-type boundary and overflow regressions.

**Exit:** Nullable SUM and all supported statistical families match a fresh
PostgreSQL query after every INSERT, UPDATE, and DELETE.

### WP4 — Restore scalar cardinality semantics

**Roadmap:** DVM-81-4

Changes:

1. Remove injected scalar `LIMIT 1` behavior from current and old snapshots.
2. Ensure generated SQL contains a required PostgreSQL scalar expression.
3. Preserve SQLSTATE `21000` through API/scheduler boundaries.
4. Verify v0.82 finalization leaves target, state, frontier, and successful
   metadata unchanged.
5. Add correction-and-retry convergence and randomized mutation tests.

**Exit:** A multi-row scalar result fails atomically and a later valid refresh
replays every unacknowledged source change.

### WP5 — Prove LATERAL dependencies and identity

**Roadmap:** DVM-81-5

Changes:

1. Collect complete analyzed outer references and mutable dependencies.

## 7. Upgrade and Compatibility Plan

Create `sql/pg_trickle--0.82.0--0.83.0.sql` and update the embedded/current
schema in the normal release workflow.

### 7.1 Migration order

1. Disable scheduler dispatch for the migration transaction and cancel or drain
   stale queued/running jobs through the existing v0.82 mechanism.
2. Add `row_identity_version` fields without falsely labeling existing state:
   add nullable columns, write version 1 to existing rows, then set version 2 as
   the default for new objects.
3. Create `pgt_set_operation_states` with extension dump/lifecycle treatment
   matching other durable internal catalogs.
4. Resolve every tracked local source and stream-table storage relation, sort by
   OID, and acquire locks that block DML before changing hash writers or
   buffers.
5. Rebuild base trigger functions, polling templates, and ST-to-ST capture with
   framed version-2 hashing.
6. Clear old data rows from registered change buffers while preserving or
   recreating the v0.82 sentinel, then mark each buffer version 2 in the same
   transaction. No version-1 `pk_hash` may survive in a version-2 buffer.
7. Mark every existing stream table `needs_reinit = true` and retain
   `row_identity_version = 1`. This intentionally conservative choice covers
   composite PKs, keyless all-column identities, transitive ST dependencies,
   set state, SUM auxiliary changes, and LATERAL identity without attempting an
   unsound textual-query classification.
8. Revalidate defining queries under the new admission rules. Persist AUTO
   fallback reasons; put explicit unsupported modes and non-monotone circular
   components into the existing non-runnable error/suspended state.
9. Commit the locked writer/buffer transition. New DML after commit is captured
   only with version 2.
10. Reinitialize eligible stream tables in topological order through v0.82's
    protected FULL path. Create set state and new aggregate/LATERAL auxiliary
    state in the same transaction, then set the stream table's identity version
    to 2 and clear `needs_reinit`.
11. Resume normal differential scheduling only for objects whose query
    admission, required private state, CDC buffers, and identity versions all
    validate.

The migration must never mix old pending hashes with new writers. If source
locks cannot be acquired, `ALTER EXTENSION UPDATE` fails and rolls back rather
than partially converting capture.

### 7.2 Compatibility behavior

- The persisted composite row-ID/CDC encoding change is intentionally breaking.
  Existing stream tables require one protected FULL reinitialization.
- Single-column hash output remains stable, but all stream tables are
  conservatively reinitialized because transitive/keyless classification is not
  a sufficient proof.
- Existing AUTO definitions that are no longer incrementally safe remain
  available through FULL and expose the fallback reason.
- Existing explicit DIFFERENTIAL/IMMEDIATE definitions that fail the new gate
  do not silently change requested mode. They are blocked with a remediation
  message until altered to AUTO/FULL or rewritten.
- Existing unsafe circular components are not executed after upgrade.
- Existing set-operation count columns are removed only during successful
  reinitialization/query-storage reconciliation. A failed reinit leaves the old
  table and catalog version intact.
- Existing algebraic SUM and LATERAL definitions receive new private/auxiliary
  state only from source data, never from guessed defaults.
- Downgrade after version-2 state creation is unsupported without restoring a
  pre-upgrade backup.

Upgrade fixtures must include:

- version-1 composite values that collide under delimiter encoding;
- NULL, empty, separator-like, and Unicode composite keys;
- pending base and ST-to-ST buffer rows;
- all four set operations with invisible one-sided state and ALL duplicates;
- nullable SUM state with an all-NULL group;
- LATERAL output that projects away the outer key;
- a STABLE AUTO definition and an explicit DIFFERENTIAL definition;
- accepted and newly rejected circular components;
- an interrupted/failed reinitialization followed by safe retry.

## 11. Risks and Mitigations

| Risk | Mitigation |
|---|---|
| Private set state and user rows diverge | Mutate both in one transaction, validate counts before finalization, crash-test, and force FULL reinit on missing/corrupt state |
| ALL variants require large duplicate expansion | Preserve exact semantics; batch physical inserts/deletes if needed, but never collapse user-visible multiplicity |
| Hash collision or framed-version mismatch selects the wrong state row | Use hash only as an accelerator plus `IS NOT DISTINCT FROM` on every canonical component; persist and validate encoding versions |
| Upgrade DML mixes old and new CDC hashes | Disable dispatch, lock every tracked source deterministically, rebuild writers, clear buffers, and version them in one migration transaction |
| Conservative upgrade reinitialization is expensive | Document and preflight the maintenance window; run protected FULL topologically. Do not attempt an unsound partial classifier |
| Universal SUM auxiliaries widen storage and delta SQL | Deduplicate identical auxiliaries and benchmark; never infer NULL state from SUM alone |
| Statistical casts alter numeric behavior | Resolve only supported PostgreSQL signatures and test production boundary values against direct aggregates |
| LATERAL identity is not representable without exposed columns | Use existing private identity plumbing or a focused private side relation; never emit broad deletion |
| Complete volatility inspection increases parse/catalog cost | Batch OID lookups and cache within one parse; unknown remains FULL-only |
| STABLE rejection breaks existing explicit incremental definitions | Preserve requested mode, block safely with an actionable error, and allow AUTO/FULL |
| Circular rules reject previously accepted pipelines | Suspend before execution and show the first non-monotone operator; correctness outranks availability |
| PostgreSQL planner prunes a scalar cardinality check | Make it a required dependency of the data-modifying statement and test real SQLSTATE/rollback |
| Property tests compare sets instead of bags | Use multiplicity-aware canonical bag comparison, including NULL tuples |

Safe operational fallback is AUTO/FULL plus protected reinitialization. Safe
development fallback is to keep an operator guarded. Never resolve a blocker by
filtering internal rows in tests, accepting hash-only equality, retaining
`LIMIT 1`, emitting `ON TRUE`, or converting inspection failure to success.

## 12. Suggested Pull Request Sequence

Keep each PR independently fail-closed and merge in this order:

1. **Semantic guardrails:** shared admission result, AUTO/FULL matrix, explicit
   rejections, corrected obvious cycle rules, red regressions.
2. **Identity framing:** version-2 encoder, shared callers, catalog versioning,
   migration skeleton, adversarial tests and benchmark.
3. **Set semantics:** positional mapping, private state, exact DISTINCT/ALL
   multiplicity, lifecycle, DIFFERENTIAL proof.
4. **Aggregate fidelity:** universal SUM non-NULL state and statistical
   accumulator casts.
5. **Scalar cardinality:** remove truncation and prove transaction/frontier
   rollback.
6. **LATERAL safety:** complete dependencies, functional determination,
   identity preservation, exact deletion, IMMEDIATE matrix.
7. **Validation completion:** every clause/expression/rewrite fails closed;
   finalize circular monotonicity proof.
8. **Upgrade and release gate:** conservative reinit, actual-binary upgrade,
   docs/ADRs, randomized oracle, full CI.

If set IMMEDIATE support is split from DIFFERENTIAL, the DIFFERENTIAL PR may
land with the IMMEDIATE guard intact. Do not remove a guard in a PR that lacks
its mutation-by-mutation PostgreSQL oracle.

## 13. Definition of Done

- [ ] Create, ALTER, preview, reinit, and refresh planning share one semantic
      admission result and mode-resolution matrix.
- [ ] AUTO uses FULL for every unsupported or uninspectable form; explicit
      DIFFERENTIAL/IMMEDIATE rejects it before object mutation.
- [ ] INTERSECT, INTERSECT ALL, EXCEPT, and EXCEPT ALL direct reads exactly
      match PostgreSQL result columns and bag multiplicity.
- [ ] Set branches bind by ordinal after PostgreSQL coercion and compare
      composite/NULL state with `IS NOT DISTINCT FROM`.
- [ ] One-sided set counts survive invisible intervals and repeated zero
      crossings; private state is LOGGED, validated, and transactional.
- [ ] Every algebraic non-DISTINCT SUM tracks qualifying non-NULL inputs,
      including FILTER and COALESCE-wrapped forms.
- [ ] Statistical squares and cross-products cast operands to the supported
      accumulator arithmetic type before multiplication.
- [ ] Scalar subqueries raise SQLSTATE `21000` on multiple rows without changing
      target data, private state, successful metadata, or frontier.
- [ ] Supported LATERAL queries have complete outer dependencies and exact
      deletion identity; no generated deletion join can degrade to `TRUE`.
- [ ] Unsupported IMMEDIATE LATERAL inner-source mutation is rejected.
- [ ] STABLE, VOLATILE, SQL/JSON, overloaded operator, and conversion-failure
      cases are fully inspected or fail closed in every clause.
- [ ] Circular LEFT/FULL joins, scalar/LATERAL subqueries, EXCEPT/anti joins,
      and other unproven non-monotone operators are rejected.
- [ ] The proven monotone circular fragment remains accepted and passes
      fixpoint property tests.
- [ ] Composite encoding is framed/versioned and all production DVM/CDC callers
      use the shared builder.
- [ ] Hash equality is never the sole correctness check for composite operator
      state.
- [ ] Upgrade from v0.82.0 cannot mix encoding versions and safely
      reinitializes every existing stream table in topological order.
- [ ] Existing explicit unsafe definitions and non-monotone circular components
      cannot run after upgrade.
- [ ] Property tests compare DIFFERENTIAL with PostgreSQL/FULL after every
      INSERT, UPDATE, DELETE, and relevant failure/recovery step.
- [ ] Unit, integration, light E2E, full E2E, upgrade, TPC-H, dbt, benchmark,
      CNPG, soak, and multi-database gates pass.
- [ ] Every release-gate direct source/query-versus-stream-table reconciliation
