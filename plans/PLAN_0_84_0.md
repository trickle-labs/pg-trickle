# v0.84.0 Implementation Plan — Catalog, Privilege, and Upgrade Integrity

**Status:** Planned
**Target:** v0.84.0
**Baseline:** v0.83.0
**Roadmap:** [roadmap/v0.84.0.md](../roadmap/v0.84.0.md)
**Last updated:** 2026-08-16

---

## 1. Outcome

v0.84.0 establishes one enforceable contract for fresh installation, extension
upgrade, SQL privileges, object ownership, logical restore, and published
artifacts. The release is complete only when these invariants hold:

1. A fresh v0.84.0 database and every supported database upgraded to v0.84.0
   have the same normalized extension catalog. Comparison is bidirectional:
   missing, extra, and changed objects all fail.
2. Supported migration-era catalogs and columns are present in the bootstrap
   schema. In particular, snapshot, subscription, and view-evolution surfaces
   work after both fresh installation and upgrade.
3. Every SQL function has an explicit API class and ACL policy. `PUBLIC`
   receives only the intentional read-only allowlist; mutating, global-control,
   event-trigger, and internal functions are revoked by exact identity
   arguments.
4. Stream-table lifecycle actions enforce ownership after resolving the
   canonical relation. Global administrative actions require superuser or
   extension-owner authority. Function ACLs are defense in depth, not a
   substitute for runtime authorization.
5. Every `SECURITY DEFINER` function is justified, has a pinned trusted
   `search_path`, preserves the outer caller for authorization, and executes
   user-provided SQL with invoker privileges. `write_and_refresh` remains
   `SECURITY INVOKER`.
6. User and catalog identifiers pass through one typed identifier path.
   Quoting, dots, Unicode, whitespace, quotes, comment markers, and semicolons
   cannot change SQL structure.
7. Snapshot restore and drop operate only on the exact cataloged snapshot
   relation, verify provenance and compatibility, and enforce ownership. An
   ordinary relation with a plausible name is never accepted.
8. Bulk alter and bulk drop call the same typed implementations as their
   single-object APIs. Their JSON/input schema is closed, bounded, and
   validated before mutation; failures are atomic and never warning-only.
9. Removing the final consumer of any supported source type leaves no managed
   change buffer, polling snapshot, sequence, trigger/function, replication
   slot, publication, registry row, or stale cleanup entry.
10. Logical restore never resumes differential maintenance with stale OIDs,
    frontiers, or CDC resources. Stable identities are rebound, capture is
    rebuilt, and each restored stream table receives a protected FULL baseline
    before differential refresh can resume.
11. The newest supported upgrade hop runs the actual released old shared
    library before switching to the new library. Pre-upgrade and post-upgrade
    DML both converge to the defining query.
12. Cargo, META, control, install SQL, `pg_extension`, runtime functions,
    release artifacts, OCI labels, OCI tags, and the Git tag report exactly one
    version. A mismatch stops publication.
13. `pgtrickle.migrate()` is read-only. Only `ALTER EXTENSION ... UPDATE` and
    packaged migration SQL may change extension schema or schema-version
    records.
14. Direct, preset, bulk-create, and alter APIs share finite/range validation
    and checked integer conversion. Invalid values fail before any catalog,
    storage, or CDC mutation, and catalog constraints provide defense in depth.
15. SQL reference metadata and supported upgrade hops are generated from
    packaged SQL or a live catalog, not inferred from Rust function names.

No schema or ACL drift may be waived for release. The plan does not introduce a
trusted-extension conversion, a new lifecycle API, a custom migration engine,
a new backup format, or an external control plane.

## 3. Target Design

### 3.1 Canonical live-catalog manifest

Add one deterministic catalog-manifest generator under `scripts/`. It should
connect to PostgreSQL and normalize the installed `pg_trickle` extension rather
than attempt to parse arbitrary SQL with regular expressions. A small SQL query
plus Python JSON normalization is sufficient; do not add a SQL parser.

The manifest must include:

| Object | Required normalized fields |
|---|---|
| Schemas | name, owner role identity, ACL |
| Relations | schema, name, relkind, persistence, owner, row security flags, ACL, extension membership |
| Columns | ordinal, name, rendered type including typmod, collation, nullability, default, identity/generated mode |
| Constraints | name, type, normalized definition, deferrability, initial deferral, validation state |
| Indexes | name, access method, uniqueness, primary/exclusion flags, key/include expressions, opclasses/collations/order, predicate, validity |
| Functions/procedures | schema, name, identity arguments, result type, language, volatility, strictness, parallel safety, security mode, leakproof flag, owner, `proconfig`, ACL |
| Views | schema, name, normalized definition, options, security invoker/barrier flags |
| Event triggers | name, event, enabled mode, tags, function identity, owner |
| Extension membership | object identity and dependency type |
| Config-dump policy | registered relation identity and dump filter |

The manifest must not include installation-specific OIDs, timestamps, sequence
positions, row counts, or role OIDs. Owners and ACL grantees are normalized to
role names, with the installing role represented by a stable
`<extension_owner>` token so two disposable databases compare cleanly.
Expression whitespace is normalized only through PostgreSQL-rendered
definitions; do not implement semantic SQL rewriting in Python.

Create two disposable PostgreSQL 18 databases in the parity test:

1. Fresh: install v0.84.0 directly.
2. Upgrade: install the supported old version, apply every required migration
   to v0.84.0, and restart on the v0.84.0 binary where required.

Extract both manifests and compare the full sorted JSON trees. Report JSON
paths for values found only on the fresh side, only on the upgrade side, and
changed on both sides. A checked-in expected manifest is useful for review, but
fresh-versus-upgrade equality is the release invariant and may not be replaced
by updating a golden file.

`check_upgrade_completeness.sh` remains as a fast file-presence smoke check only
if useful. It is no longer the schema truth gate. The live manifest gate covers
removals and altered definitions in both directions.

### 3.2 Bootstrap repair and migration-era objects

Make the bootstrap schema in `src/lib.rs` complete before generating the
v0.84.0 install SQL. At minimum it must include the currently missing objects:

- `pgtrickle.pgt_snapshots` and `idx_pgt_snapshots_pgt_id`;
- `pgtrickle.pgt_subscriptions`;
- `pgt_stream_tables.in_shadow_build`;
- `pgt_stream_tables.shadow_table_name`.

The manifest comparison determines whether other historical migration-only
objects are missing; do not stop after the four known gaps. Every discrepancy
must be classified as:

- supported and restored to bootstrap;
- intentionally removed through explicit migration SQL and documentation; or
- dynamic/runtime state excluded from the static extension manifest.

The `0.83.0 -> 0.84.0` migration is idempotent:

1. Create missing catalogs and indexes with their canonical definitions.
2. Add missing columns without rewriting valid existing rows unnecessarily.
3. Backfill new stable/provenance fields where the existing object can be
   proven.
4. Add new constraints as `NOT VALID` only when old data needs validation,
   validate them in the same migration after the repair/backfill, and finish
   with the same validation state as fresh install.
5. Recreate or alter function properties and exact ACLs after all functions
   exist.
6. Register the final config-dump policy.
7. Insert the `0.84.0` schema-version audit row only after all DDL succeeds.

Rows that cannot be repaired safely are not guessed or deleted. Leave the
affected feature unavailable, preserve the row/object, and emit an actionable
diagnostic identifying the object and required repair. The extension upgrade
itself may fail when continuing would expose an ambiguous privilege or schema
contract.

Fresh and repaired schemas must run snapshot, subscription, and view-evolution
smoke tests, not merely pass catalog inspection.

### 3.3 Explicit SQL API and privilege matrix

Maintain one checked-in API policy file consumed by the ACL migration, manifest
check, and generated reference. Each overload is keyed by schema, function
name, and identity arguments; function names alone are insufficient.

Use these classes:

| Class | Default ACL | Runtime authorization | Security mode |
|---|---|---|---|
| `public_read` | Explicit `GRANT EXECUTE TO PUBLIC` | Any caller with schema usage; functions must be side-effect-free | Invoker unless catalog privacy requires a narrowly justified definer |
| `owner_lifecycle` | Revoke from `PUBLIC`; documentation grants exact overloads to author/operator roles | Resolved stream-table owner or superuser | Invoker where possible; otherwise pinned definer preserving outer caller |
| `admin_global` | Revoke from `PUBLIC` | Superuser or extension owner | Pinned definer only when private catalog/global resources require it |
| `arbitrary_sql` | Revoke from `PUBLIC`; explicit operator grant | Existing target authorization plus normal SQL privileges | Always invoker |
| `trigger_entry` | Revoke from `PUBLIC` | PostgreSQL trigger/event-trigger invocation only | Pinned definer where required |
| `internal` | Revoke from `PUBLIC` and documented roles | Extension-owned callers only | Minimum required mode with pinned path |

The policy file must classify every generated SQL function, including overloads.
An unclassified function fails generation and CI. Removing a function from the
policy without removing it from packaged SQL also fails.

ACL installation is deny-first:

1. `REVOKE EXECUTE ON ALL FUNCTIONS IN SCHEMA pgtrickle FROM PUBLIC`.
2. Grant `PUBLIC` only the exact `public_read` signatures.
3. Revoke exact `trigger_entry` and `internal` signatures from all ordinary
   roles.
4. Leave owner/admin/arbitrary-SQL grants to documented operator role setup;
   the extension owner retains ownership privileges.

Do not use `ALTER DEFAULT PRIVILEGES` as the release contract: it does not fix
existing functions and depends on the creating role. Emit exact
`REVOKE/GRANT ... ON FUNCTION schema.name(identity_args)` statements from the
policy.

Runtime authorization must use the original SQL caller, not the effective
definer role:

- owner lifecycle: resolve the canonical storage relation and call the shared
  ownership helper;
- snapshots: require ownership of the target stream table and verify the
  cataloged snapshot relation;
- subscriptions/publications: resolve the stream table and require ownership;
- repair/restore: require target ownership, with superuser override;
- scheduler controls and `drain`: require superuser or extension owner;
- event-trigger/internal entry points: reject direct ordinary invocation even
  if ACLs were accidentally broadened.

Do not add a cluster-wide `pgtrickle_admin` role in extension SQL. The
documentation may use that role name as an example, but PostgreSQL roles are
operator-managed. Runtime superuser/extension-owner authority and explicit
function grants are sufficient; a new role framework would add lifecycle
problems without improving the boundary.

For every `SECURITY DEFINER` overload, CI asserts:

- `prosecdef = true` only when its policy permits it;
- `proconfig` pins `search_path` to trusted schemas, with `pg_temp` last;
- no user-controlled schema appears in `search_path`;
- authorization reads the outer caller;
- user-provided queries or write statements execute as the caller;
- `PUBLIC` has no direct access unless the explicit class allows it.

`write_and_refresh` is specifically asserted as invoker-only in source,
manifest, role tests, and generated documentation.

### 3.4 Typed identifiers and relation resolution

Replace lifecycle-local parsing/quoting variants with two small shared types in
the existing API helper module:

```rust
struct SqlIdentifier(String);

struct QualifiedName {
    schema: SqlIdentifier,
    object: SqlIdentifier,
}
```

The exact names may follow repository conventions. Avoid a generic SQL-builder
framework.

Rules:

- `SqlIdentifier` rejects NUL and renders by doubling `"` and surrounding the
  value with `"..."`.
- `QualifiedName` is constructed from two already-separated identifiers and
  never from string concatenation.
- User relation text is resolved through PostgreSQL (`to_regclass`,
  `parse_ident`, or an existing equivalent) with SPI parameters, then read back
  as `nspname::text` and `relname::text`.
- Unqualified API names follow the documented default/search-path rule for that
  API; all callers share one rule rather than hard-coding `public` in some
  modules and `current_schema()` in others.
- SQL values always use SPI parameters. Identifier quoting is not reused for
  literals.
- Cataloged OIDs are rendered only after resolving their current schema/name.
- Extension-controlled stable object names are constructed from typed
  components and length-checked against PostgreSQL's identifier limit.

Move create, alter, refresh, drop, snapshots, publications, scheduler control,
bulk operations, subscription lookup, and CDC cleanup onto this path. Other
unrelated SQL generation need not be refactored solely for aesthetic
consistency, but no touched lifecycle path may retain a local quote/parser.

Unit tests cover empty strings, embedded quotes, dots within quoted
identifiers, mixed case, Unicode, leading/trailing whitespace, comment markers,
semicolons, and NUL rejection. E2E tests create real relations with these names
and exercise create, alter, snapshot, restore, and drop.

### 3.5 Snapshot identity, provenance, and ownership

Extend `pgt_snapshots` with stable identity fields:

```sql
snapshot_relid       oid,
provenance_token     text,
created_by           oid,
```

Keep schema/table names for logical restore rebinding. The exact nullability is:

- fresh v0.84.0 snapshots: all fields populated;
- safely backfilled old snapshots: all fields populated;
- unresolved legacy rows: nullable fields remain NULL and all mutating snapshot
  operations reject them with a repair diagnostic.

Do not claim provenance from a naming convention. Snapshot creation:

1. Resolve and authorize the source stream table as the outer caller.
2. Resolve the target schema and verify caller `CREATE` privilege.
3. Generate a random provenance token using PostgreSQL-native facilities or
   existing dependencies; do not add a UUID crate solely for this.
4. Create the snapshot relation and metadata columns transactionally.
5. Store the token as a column default or equivalent table-level property so an
   empty snapshot remains verifiable.
6. Insert the exact relation OID, names, token, source `pgt_id`, and caller role
   into `pgt_snapshots`.
7. Transfer/retain relation ownership according to the documented snapshot
   ownership contract.

Restore and drop resolve the supplied name to an OID, then require one exact
catalog row whose `snapshot_relid` matches. They verify:

- schema/name and OID agree;
- provenance token agrees with the relation metadata;
- relation kind is an ordinary snapshot table;
- metadata/user columns are compatible with the target stream table;
- the snapshot belongs to the target `pgt_id` for restore;
- the caller owns the target stream table and is authorized for the snapshot.

Missing catalog rows, OID mismatch after drop/recreate, token mismatch, wrong
stream table, malformed metadata, and ordinary lookalike tables all fail before
locking or truncating the target. Catalog deletion and relation drop are one
transaction; neither is best-effort.

### 3.6 Typed bulk lifecycle semantics

Reuse the single-object implementation functions. Do not generate custom SQL
syntax or call public SQL wrappers from Rust.

Define one constant batch limit, initially `1_000`, shared by bulk create,
alter, and drop. This is high enough for intended administration while bounding
memory, lock count, and error size. Raising it later is a measured operational
decision, not a GUC in this release.

Bulk input rules:

- reject an empty array;
- reject a cardinality above the limit;
- reject NULL entries rather than silently skipping them;
- reject duplicate canonical targets;
- reject unknown JSON keys;
- reject wrong JSON types instead of treating them as absent;
- validate all identifiers, enum values, numbers, and authorizations before the
  first mutation.

Use typed serde input with `deny_unknown_fields` for JSON APIs. Keep the
existing SQL signatures and return types unless a signature is demonstrably
unusable; v0.84.0 changes behavior, not API count.

Bulk alter:

- deserialize once into the same `AlterStreamTableOptions`/validation path used
  by `alter_stream_table`;
- apply one coherent option set per stream table, not one generated statement
  per JSON key;
- reject unsupported fields explicitly;
- resolve and authorize every table first;
- execute atomically in input order after validation.

Bulk drop:

- resolve all targets first;
- enforce existing `RESTRICT` semantics;
- account for dependencies within the supplied set and drop in reverse
  topological order;
- reject external dependents not in the set;
- call `drop_stream_table_impl`/a factored typed inner helper directly;
- abort the transaction on the first error.

Bulk create already intends atomic behavior but must move to the same closed
schema, checked conversion, canonical-name, and prevalidation rules. Result
JSON must not contain success-shaped fallback IDs such as `-1`.

### 3.7 Complete lifecycle resource cleanup

Before deleting dependency/catalog rows, load one typed resource inventory for
each source from canonical metadata:

```text
source OID and stable name
source kind and CDC mode
buffer registry key and relation
polling snapshot relation
trigger and trigger-function identities
slot and publication identities
managed sequences
consumer pgt_ids
pending cleanup entries
```

Use `source_stable_name` and `pgt_change_buffers.buffer_key` as canonical
identities. OID-derived legacy names are a migration fallback only and must be
rebound or explicitly reported before cleanup.

The same cleanup function handles local tables, partitioned tables, materialized
views, foreign/polling tables, Citus-supported sources, and stream-table
sources. The final-consumer decision is made from validated dependency rows
under the stream-table lifecycle lock.

Cleanup ordering:

1. Prevent new use of the resources by removing/staging the consumer under the
   existing lifecycle transaction and locks.
2. Remove trigger capture or polling metadata only after another consumer is
   proven absent.
3. Drop managed buffer/polling snapshot relations and their registry rows.
4. Drop publication/slot resources using their cataloged names.
5. Remove tracking and pending-cleanup rows.
6. Verify no managed resource from the captured inventory remains.

Transactional DDL failures abort the lifecycle operation. Resources whose
PostgreSQL APIs cannot be rolled back safely use the existing persistent cleanup
status as an explicit retry record; the API must report that cleanup is pending
rather than logging a warning and returning normal success. Repair/startup
reconciliation retries such entries. It is acceptable to leak a proven
unused resource temporarily; it is not acceptable to delete active capture or
report complete cleanup while an orphan remains.

Tests cover shared sources, last-consumer deletion, ALTER removing a source,
trigger/WAL transition state, foreign-table polling snapshots, stream-table
buffers, partitioned sources, and injected cleanup failure followed by retry.

### 3.8 Durable configuration and logical restore

Document and encode this catalog classification:

| Catalog/state | Classification | Logical restore behavior |
|---|---|---|
| `pgt_stream_tables` | Durable user configuration plus rebuildable runtime fields | Dump rows; rebind storage OIDs by qualified name; reset frontier/runtime fields and require protected reinitialization |
| `pgt_refresh_groups` | Durable user configuration | Dump; migrate member references to stable `pgt_id` identities or rebind before use |
| `pgt_source_gates` | Durable operator configuration | Dump with stable source name; rebind source OID |
| `pgt_watermarks`, `pgt_watermark_groups` | Durable operator configuration/state | Dump; add/reuse stable source identities and rebind OIDs |
| `pgt_subscriptions`, `pgt_distance_subscriptions` | Durable user configuration | Dump; validate/rebind stream-table identity |
| `pgt_outbox_config` | Durable user configuration | Dump; validate referenced stream table and external extension availability |
| `pgt_snapshots` | Durable provenance/configuration | Dump; rebind exact snapshot relation and token |
| `pgt_dependencies` | Derived from defining query and live catalogs | Do not trust restored rows; rebuild |
| `pgt_change_tracking`, `pgt_change_buffers` | Derived CDC infrastructure | Exclude/reset; rebuild under source locks |
| `pgt_set_operation_states` | Derived DVM state | Exclude/reset; rebuild during protected FULL |
| `pgt_scheduler_jobs`, `pgt_st_locks`, `pgt_worker_slots` | Ephemeral runtime state | Exclude/reset |
| `pgt_template_cache` | Cache | Exclude/reset |
| `pgt_cleanup_status` | Retry state tied to old objects | Exclude/reset after reporting unresolved source cleanup before dump |
| `pgt_refresh_history`, `pgt_refresh_summary`, `pgt_cost_model_summary` | Operational history/derived summaries | Intentionally excluded from portable logical restore; document separate audit export if needed |
| `pgt_schema_version` | Migration audit for the installed extension | Never restore from the source cluster; migration SQL owns it |
| Dynamic change buffers and polling snapshots | Derived relations | Mark as extension-managed/excluded and rebuild |
| Stream-table storage and archival snapshot tables | User data relations | Dump normally; validate before rebinding |

Configure `pg_extension_config_dump` from this classification. Existing
registrations for derived tables must be changed to an exclusion filter or
otherwise removed using PostgreSQL-supported extension metadata behavior; do
not leave stale rows dumpable and merely hope later code discards them. Add a
test that inspects `pg_extension.extconfig`/`extcondition` and a real dump to
prove the policy.

Add one internal reconciliation function reused by launcher startup,
scheduler preflight, repair, and logical-restore tests. It is not a new public
lifecycle API.

Reconciliation runs under a database-local advisory lock and:

1. Detects catalog rows whose stored OIDs do not resolve to their stable names.
2. Resolves storage relations, snapshots, sources, and group members by stable
   identity, requiring exact relation kind and expected structure.
3. Rebinds `pgt_relid`, snapshot OIDs, and other durable OID fields.
4. Discards/rebuilds dependency and runtime registries rather than mapping stale
   OIDs heuristically.
5. Sets every restored stream table to `needs_reinit = true`, clears invalid
   frontiers and row-identity/runtime state, and prevents differential,
   immediate, fused, or TopK execution.
6. Acquires source locks in deterministic OID order.
7. Recreates trigger/polling capture from stable names while writes are blocked.
8. Runs the existing protected FULL baseline, rebuilding private state and
   establishing a new-cluster frontier in the same transaction.
9. Clears `needs_reinit` only after data, CDC, frontier, and catalog validation
   all succeed.

If pg_restore is still loading objects, reconciliation returns a typed
incomplete result and the scheduler remains fail-closed; it does not treat
missing relations as deletion or zero changes. The next startup/tick retries.
Documentation should still recommend `pg_trickle.enabled = off` during a
logical restore to avoid wasted retries, but correctness must not depend on
timing.

The real restore test must deliberately change relation OIDs by creating filler
objects before restore. It then inserts new source DML after restore and proves
that capture works because reconciliation rebuilt it, not because post-data
trigger restoration happened to recreate old trigger definitions.

`pg_trickle_dump` remains an optional declarative export. Update it to use
shared contract metadata where practical, but do not present it as the mechanism
that makes standard `pg_dump` correct.

### 3.9 Real old-binary upgrade verification

Replace the current “old SQL with new `.so`” upgrade image for the newest
supported hop. The harness must use the immutable released v0.83.0 artifact:

1. Obtain the old package from a project-controlled GitHub release/GHCR artifact
   and verify its published checksum, or build the exact signed/tagged commit in
   a separate Docker stage when an artifact is unavailable.
2. Install the old control, SQL, and shared library together.
3. Start PostgreSQL with the old library.
4. Create populated FULL, DIFFERENTIAL, IMMEDIATE, aggregate, snapshot,
   subscription, and supported polling/WAL fixtures using old SQL APIs.
5. Commit pre-upgrade INSERT, UPDATE, DELETE, and TRUNCATE/INSERT changes and
   verify old-version refresh.
6. Stop PostgreSQL cleanly.
7. Install the new library, control, full SQL, and upgrade SQL without replacing
   the data directory.
8. Restart on the new binary. Before `ALTER EXTENSION`, version mismatch
   protection must prevent scheduler mutation.
9. Run `ALTER EXTENSION pg_trickle UPDATE TO '0.84.0'`.
10. Verify the normalized manifest, migrated ACLs, catalog data, snapshots,
    subscriptions, CDC infrastructure, and stream-table results.
11. Commit post-upgrade mutations, refresh, and compare every stream table with
    its defining query.

Historical upgrade tests may retain the lightweight current-binary approach as
a compatibility smoke test, but must be labeled accordingly. The release gate
for the newest supported hop cannot use it.

### 3.10 Version and publication integrity

Expand `check_version_sync.sh` into one reusable version assertion invoked by
all release workflows. It accepts an optional expected tag version and checks:

- `Cargo.toml` package version;
- the package entry in `Cargo.lock`;
- `META.json.version` and `META.json.provides.pg_trickle.version`;
- `pg_trickle.control.default_version`;
- current archive SQL filename;
- newest upgrade SQL target;
- packaged install SQL filename and extension header where applicable;
- `pgtrickle.version()` from the built library;
- `pg_extension.extversion` after installing the built package;
- release archive directory/filename;
- OCI `org.opencontainers.image.version`, immutable tag, and platform tags;
- the triggering Git tag exactly equals `v<Cargo version>`.

The release, GHCR, Docker Hub, and PGXN workflows call the same script before
building or publishing. They do not independently reimplement partial version
logic. After artifact creation, inspect the archive/image contents rather than
trust workflow variables.

Make workflow outputs explicit; do not rely on a nonexistent
`needs.<job>.outputs.version` fallback. Stable releases may publish `latest`
only after the immutable version tag/image exists and passes runtime smoke
tests. Prereleases never move stable aliases.

Convert `pgtrickle.migrate()` in place to a read-only diagnostic for API
compatibility. It reports:

- library version;
- `pg_extension.extversion`;
- latest migration audit row;
- whether the live catalog matches the packaged expected manifest/version;
- the exact `ALTER EXTENSION ... UPDATE` remediation when mismatched.

It performs no INSERT, UPDATE, DDL, or version-ledger advancement. Migration SQL
alone inserts `pgt_schema_version` rows.

### 3.11 Shared API validation and catalog constraints

Keep validation in the existing API module hierarchy. Add small pure helpers,
not a validation framework:

```rust
fn finite_fraction(name: &str, value: f64) -> Result<f64, PgTrickleError>;
fn checked_i32(name: &str, value: i64) -> Result<i32, PgTrickleError>;
fn nonnegative_i32(name: &str, value: i64) -> Result<i32, PgTrickleError>;
```

Share them across direct create, create-or-replace, presets, bulk create,
alter, and query-derived TopK storage.

Required contracts:

| Value | Contract |
|---|---|
| `max_delta_fraction` | NULL or finite `0.0..=1.0`; `0.0` retains the documented disable meaning |
| TopK limit | positive and representable as `i32` before catalog storage |
| TopK offset | non-negative and representable as `i32`; checked addition for offset + limit |
| `max_differential_joins` | NULL or non-negative/within documented bound and representable as `i32` |
| storage fillfactor | NULL or `10..=100` |
| fuse ceiling/sensitivity and timeout/count inputs | finite/non-negative/checked according to existing documented types |
| batch cardinality | `1..=1_000` |

NaN, positive/negative infinity, negative values, overflow, fractional JSON
where an integer is required, unknown keys, duplicate fields/targets, and
wrong-typed values fail before mutation.

Add matching catalog `CHECK` constraints for persisted values. PostgreSQL
float constraints must explicitly reject `NaN` and infinities as well as apply
the numeric range. Migration validates existing rows before validating the
constraint; it does not coerce or clamp user configuration.

Separate parse/validation from SPI mutation so unit tests cover every boundary.
All narrowing uses `TryFrom`; no `as i32` remains on user/query-derived values
stored in catalogs.

### 3.12 Generated SQL contracts and reference

Replace `gen_sql_reference.py`'s source regex/grace-list model with packaged SQL
or live-manifest input. Preserve hand-written examples and explanations in
`docs/SQL_REFERENCE.md`, but generate a delimited contract block containing:

- schema/name and full identity arguments;
- argument names, types, and defaults;
- return type or table shape;
- volatility;
- strictness;
- parallel safety;
- security invoker/definer mode;
- pinned `search_path` where applicable;
- API/ACL class and default grantees;
- deprecation/internal status.

Generate the supported-upgrade-hop table from actual migration filenames plus
the documented support policy. The docs check fails if a migration exists but
is omitted, or documentation claims an unsupported hop.

The API policy file supplies intentional classification only. PostgreSQL
catalog/package output supplies mechanical facts. CI compares them and fails
when, for example, policy says invoker but `prosecdef` is true, a default
changes, an overload is undocumented, or an internal function becomes public.

Remove the grace list as part of this release. Existing public functions must
be documented or explicitly internal; “pre-existing gap” is not a valid
v0.84.0 state.

## 4. Error Model

Add focused `PgTrickleError` variants where existing variants cannot carry the
required context:

| Condition | Required context and behavior |
|---|---|
| Catalog parity failure | object identity, manifest path, fresh value, upgrade value |
| Function not classified | full function identity arguments |
| Authorization failure | caller, operation, target, required owner/admin rule |
| Invalid identifier | original input and reason; never include generated SQL |
| Snapshot provenance failure | supplied relation, resolved OID, cataloged OID/token mismatch, remediation |
| Bulk schema failure | zero-based item index, field, expected type/range |
| Bulk operation failure | item index and canonical target; abort all |
| Resource cleanup incomplete | source identity, remaining resource, retry status |
| Restore rebind failure | durable object, stored identity, resolved candidate, reason |
| API contract violation | parameter, supplied value, accepted range/type |
| Version mismatch | each compared surface and expected version |

Rules:

- No broad catches or ignored SPI results on correctness/security paths.
- Iterator/list APIs do not turn catalog permission or corruption into empty
  successful output.
- Cleanup warnings do not become success.
- Invalid input is rejected before subtransactions, DDL, catalog inserts, CDC
  setup, or storage mutation.
- SQLSTATE should distinguish invalid argument, insufficient privilege,
  undefined/corrupt object, and internal invariant failures using the existing
  error classification.
- Error messages contain canonical object names and remediation, but do not
  echo secrets or arbitrary SQL bodies.

## 7. Upgrade and Compatibility Plan

### 7.1 Migration order

The `0.83.0 -> 0.84.0` script runs transactionally in this order:

1. Create missing supported catalogs and indexes.
2. Add missing view-evolution and stable identity/provenance columns.
3. Repair/backfill rows that can be proven from live catalog identity.
4. Add finite/range and referential constraints, validate repaired data.
5. Update config-dump registrations/filters.
6. Create/replace changed SQL function definitions.
7. Apply canonical owners, security mode, pinned `search_path`, and exact ACLs.
8. Mark runtime OID/CDC state for reconciliation where binary/schema semantics
   changed.
9. Insert the v0.84.0 migration audit row.
10. Signal launcher/catalog invalidation only after successful migration.

The script is rerunnable after a failed attempt. Dynamic DDL uses catalog
checks, not exception swallowing.

### 7.2 Breaking behavior

This is intentionally a minor release because:

- mutating APIs lose default `PUBLIC EXECUTE`;
- documentation no longer grants all functions indiscriminately;
- bulk alter/drop become strict and atomic;
- unknown JSON keys and previously truncated numeric values are rejected;
- invalid persisted configuration blocks constraint validation;
- snapshot lookalike tables and unresolved legacy snapshots are rejected;
- logical restore forces safe reinitialization instead of trusting old
  frontiers/CDC;
- `migrate()` no longer claims to migrate or changes its private ledger.

Provide an upgrade guide with exact preflight queries:

- list roles relying on `PUBLIC` function privileges;
- generate grants for documented author/operator roles;
- list out-of-range/NaN/infinite persisted values;
- list unresolved snapshot rows;
- list unstable legacy CDC resource names;
- estimate stream tables requiring restore/reinitialization.

Do not automatically grant broad replacement privileges or clamp invalid data.

### 7.3 Rollback

Catalog/ACL changes are not safely reversible by copying the old shared library.
The runbook requires:

1. logical/physical backup before upgrade;
2. preflight remediation;
3. `ALTER EXTENSION ... UPDATE`;
4. manifest/role/API smoke verification;
5. restore from the pre-upgrade backup for rollback.

Do not ship a down-migration that reopens `PUBLIC` mutation or discards
provenance/restore metadata.

## 10. Risks and Mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| Revoking `PUBLIC` breaks existing operator scripts | High | Minor-release treatment, generated preflight/grants, exact migration guide, role E2E |
| Fresh/upgrade parity normalizer hides a real difference | High | Normalize only installation-specific values; retain PostgreSQL-rendered definitions; test normalizer with intentional drift |
| `SECURITY DEFINER` broadens user query privileges | Critical | Outer-caller authorization, invoker execution for arbitrary SQL, pinned path, manifest policy, negative role tests |
| Legacy snapshots cannot prove provenance | Medium | Preserve rows/data, mark unresolved, reject mutation, provide repair diagnostic; never infer from name alone |
| Logical restore races scheduler or application writes | Critical | Fail-closed preflight, database advisory lock, deterministic source locks, install capture before protected FULL baseline |
| Config-dump policy still emits derived rows/objects | High | Inspect extension metadata and a real dump archive; restore into changed OIDs and assert absence/reset |
| Cleanup failure removes live capture | Critical | Decide final consumer under lock, order capture teardown safely, persistent retry for non-transactional cleanup, shared-source tests |
| Atomic bulk operations hold many locks | Medium | Fixed 1,000-item cap, deterministic ordering, document transaction cost |
| Actual old artifact is unavailable or mutable | High | Project-controlled immutable tag/artifact, checksum verification, exact-tag Docker build fallback |
| Added constraints reject existing invalid rows | Medium | Preflight queries, actionable failure, no silent clamp/coercion |
| Generated reference overwrites hand-written guidance | Low | Generate only delimited contract blocks; preserve prose/examples |
| Manifest tests make CI slow | Medium | Keep regex smoke check on PR if useful; run one disposable fresh/upgrade pair, cache old artifact; full historical matrix remains scheduled |

Correctness, durability, and privilege safety take precedence over upgrade
convenience or retained-WAL/resource cleanup speed.
