# v0.89.0 Implementation Plan: Incremental Window Functions

> **Status:** Needs roadmap alignment
> **Target:** v0.89.0
> **Baseline:** v0.88.0
> **Roadmap:** [roadmap/v0.89.0.md](../roadmap/v0.89.0.md)
> **Last updated:** 2026-08-30

> **Roadmap change:** The bounded state framework remains mandatory, but
> algorithm breadth is now evidence-gated and does not block v1.0. Treat the
> family-specific implementation detail below as research input until this plan
> is revised around the admission gate.

## 1. Outcome

v0.89.0 replaces unconditional partition recomputation for common window
functions with bounded, crash-safe incremental maintenance. Each admitted
window node keeps private ordered state beside the stream table. A refresh
updates that state and the stream-table result in the same PostgreSQL
transaction.

The work lands in this order:

1. Freeze PostgreSQL frame semantics, stable row identity, fallback codes, and
   the v0.88 performance baseline.
2. Add analyzed window metadata and a pure strategy planner.
3. Add the LOGGED state registry, typed side relations, lifecycle handling,
   budget enforcement, and state validation.
4. Add rank-family algorithms.
5. Add offset and boundary algorithms.
6. Add SUM and COUNT window algorithms.
7. Add the measured crossover selector, diagnostics, upgrade handling, and the
   release benchmark gate.

The existing partition-recompute SQL in `src/dvm/operators/window.rs` remains
the correctness fallback. v0.89 does not add another refresh transaction or a
second frontier finalizer.

### 1.1 Release invariants

- PostgreSQL window semantics remain the oracle. NULL ordering, peer groups,
  frames, collations, aggregate result types, and errors must match PostgreSQL.
- The target rows, window state, downstream CDC rows, frontier, refresh
  history, and state generation commit together or roll back together.
- An incremental strategy starts only after the planner proves the function,
  frame, argument shape, ordering, type, collation, and child row identity.
- An unknown function OID, type OID, collation, frame option, expression, or
  state format fails closed to partition recomputation.
- Missing or corrupt state never produces a best-effort delta. It marks the
  stream table for protected reinitialization.
- Budget exhaustion never drops source changes or window state that is needed
  for correctness. The affected partition uses recomputation and remains
  replayable from the same frontier on failure.
- The engine chooses incremental maintenance or partition recomputation before
  it mutates target or state. A runtime error after mutation starts aborts the
  transaction; it does not replay the interval through another strategy.
- State relations are permanent and LOGGED. They are not temporary, UNLOGGED,
  or stored in user-visible result columns.
- PostgreSQL compares and aggregates SQL values. Rust code does not reimplement
  collation, NULL ordering, numeric overflow, or polymorphic return types.
- A window node remains one-to-one with its child. The state preserves the
  child's exact identity even when the defining query does not project the
  identity columns.
- One semantic window specification shares one ordered state set. Functions
  with the same partition keys and ordering reuse that state.
- If one function in a window node cannot use incremental maintenance for an
  affected partition, the engine recomputes that whole node and partition.
  v0.89 does not splice independently evaluated window functions into one row.
- Deferred DIFFERENTIAL mode receives the new algorithms. IMMEDIATE mode keeps
  the existing statement-local partition recomputation until a later release
  proves state lifecycle and trigger recursion for that mode.
- FULL remains the result oracle and rebuild path. A FULL refresh of an
  incrementally eligible window table also rebuilds its private state from the
  same protected snapshot.

### 1.2 Roadmap ambiguities resolved

| Roadmap wording | v0.89 contract |
|---|---|
| "Side table keyed by stream table and partition key" | Add one focused registry, `pgtrickle.pgt_window_states`, and typed LOGGED relations per semantic window specification. Do not add a general operator-state framework. |
| `window_strategy JSONB` | Store a versioned plan in `pgt_stream_tables.window_strategy`. Each function entry records its semantic node, strategy, state registry key, eligibility, and static fallback reason. Dynamic state OIDs remain in the relational registry. |
| "Sorted index" | Use a PostgreSQL btree with the exact ORDER BY direction, NULL placement, collation, and a stable identity tie-breaker. PostgreSQL remains responsible for ordering. |
| "Ring buffer" | Keep ordered rows durably in the side relation. For each delta, read only the changed rows plus the required N neighbors into a bounded ring. Do not persist N neighbor copies on every row. |
| "Track min/max by sort key" | Track the first and last row identity under the PostgreSQL ordering. Do not apply SQL `MIN()` or `MAX()` to the value argument. |
| "Indexed array" | Keep the first `max(N)` row identities needed by admitted `NTH_VALUE` calls in partition state. The full ordered row relation remains the source of truth. |
| "Prefix-sum tree" | Maintain ordered peer or row prefix summaries and update only the output suffix that must change. Add a deeper tree only if the benchmark shows that finding the prefix seed dominates mandatory suffix writes. A tree that cannot reduce the result-delta lower bound does not ship. |
| Default frame | Normalize it explicitly. With ORDER BY, PostgreSQL's default is `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`. Without ORDER BY, all rows are peers and the default covers the partition. |
| Multiple functions | Group functions by a canonical partition, order, and frame key. A node-level partition fallback wins over mixed partial execution for that refresh. |
| Ties in ORDER BY | Preserve the original order terms as the peer key. Add stable child identity only to choose a deterministic row inside a peer group. Never add the tie-breaker to `RANK` or `DENSE_RANK` peer equality. |
| State ceiling | Use the effective `pg_trickle.memory_budget_mb` total as a per-stream-table persistent-state guard. This is a size ceiling, not a claim that the whole relation stays in memory. No new GUC is added. |
| Alert | Reuse refresh history, `pgtrickle.explain()`, `explain_json()`, `health_check()`, logs, and existing metrics. Do not add an alert subsystem. |
| Crossover | Choose per affected partition from measured family-specific costs and estimated emitted rows. Do not claim that a one-row input delta always has a one-row result delta. |
| Existing window tables | Detect them by parsing the defining query after upgrade. Mark them for automatic protected reinitialization on the next refresh. Report an actionable error if reinitialization cannot complete. |

### 1.3 Non-goals

- New PostgreSQL window functions or changed SQL syntax.
- Incremental IMMEDIATE window state.
- Incremental `MIN()` or `MAX()` window aggregates with deletions.
- `GROUPS` frames, `EXCLUDE` clauses, or arbitrary bounded and following
  frames.
- User-defined window functions or aggregates.
- A public state-management API.
- A general balanced-tree library, custom PostgreSQL access method, or new
  third-party dependency.
- A new memory, offset, frame, or crossover GUC.
- Parallel state mutation across one stream table. Existing per-stream-table
  refresh serialization remains the concurrency boundary.
- Replacing the existing partition-recompute implementation.

## 3. Target flow

```text
defining query
    -> PostgreSQL analysis and DVM semantic tree
    -> normalize window functions, frames, types, collations, and identities
    -> build versioned WindowStrategyPlan
    -> create or validate LOGGED typed state

refresh interval
    -> differentiate child and normalize its net row changes
    -> identify old and new affected partitions
    -> validate state generation and budget
    -> estimate affected result rows per partition
    -> choose before mutation
         -> incremental rank, neighbor, boundary, nth, sum, or count
         -> existing partition recomputation with a reason code
    -> materialize one ordinary delta relation
    -> existing target apply and downstream capture
    -> mutate state in the same transaction
    -> existing frontier and history finalizer
```

The semantic planner decides what can be maintained. The runtime selector
decides what is cheaper for one refresh. Missing runtime evidence can only
select partition recomputation; it cannot widen semantic eligibility.

## 4. Semantic plan and stable identity

### 4.1 Analyzed window metadata

Replace string-only strategy decisions with analyzed metadata. Keep the
existing SQL rendering fields where they remain useful, but add enough typed
data to make admission fail closed.

`WindowExpr` or an adjacent resolved record must carry:

- a stable semantic node ordinal and function ordinal;
- the resolved built-in function or aggregate OID;
- the function kind from a closed `WindowFunctionKind` enum;
- argument type OIDs, typmods, and collations;
- the result type OID and SQL type name;
- partition expression types and collations;
- ORDER BY expression types, collations, direction, and NULL placement;
- a typed `WindowFrameSpec` with mode, start, end, and exclusion;
- whether the frame was implicit or explicit;
- a constant offset or N value when required;
- the FILTER expression, when present, so admission can reject it in v0.89;
- the original parse location for diagnostics;
- the output alias.

Reuse the analyzed-tree walker pattern that annotates statistical aggregates
in `src/dvm/parser/sublinks/mod.rs`. Collect all window metadata during one
PostgreSQL analysis, then release the SPI connection before pure strategy
planning and SQL generation.

Resolve by OID, not by `func_name`. A user function named `rank` is not the
built-in rank function. If PostgreSQL analysis cannot resolve a node, AUTO and
DIFFERENTIAL retain partition recomputation and record
`WINDOW_METADATA_UNRESOLVED`.

### 4.2 Typed frame normalization

Add these pure types in the parser layer:

```text
WindowFrameMode = Rows | Range | Groups
WindowFrameBound = UnboundedPreceding | OffsetPreceding(Const) |
                   CurrentRow | OffsetFollowing(Const) |
                   UnboundedFollowing
WindowFrameExclusion = None | CurrentRow | Group | Ties
WindowFrameSpec = { mode, start, end, exclusion, was_implicit }
```

Normalize an omitted frame before strategy selection:

- With ORDER BY, use RANGE from unbounded preceding through current row.
- Without ORDER BY, treat the whole partition as one peer group.
- Ranking and offset functions still record the frame, even where PostgreSQL
  ignores it, so diagnostics can explain the decision.

Do not parse the deparsed frame string to recover semantics. Keep `to_sql()` as
a renderer from the typed form. Unit tests must round-trip every PostgreSQL 18
frame flag used by the parser.

### 4.3 Canonical semantic specifications

Group window functions by a `WindowSpecKey` built from:

- normalized partition expressions;
- normalized ORDER BY expressions, direction, NULL placement, and collation;
- the normalized frame where the function observes it;
- child semantic identity.

Assign ordinals by a deterministic preorder walk of the semantic tree before
v0.88 physical reordering. Use the defining-query hash, parser strategy
version, node ordinal, and specification ordinal as the durable state identity.
Do not use a pointer address, generated CTE name, or output alias as a durable
key.

### 4.4 Stable child-row identity

Incremental maintenance requires one durable identity for each child row.
Extend the window plan to request the child's exact identity columns and the
existing framed row hash.

Admission requires all of these facts:

- the child is one-to-one at the window boundary;
- `row_id_key_columns()` or an equivalent v0.88 identity proof returns a
  complete key;
- the key expressions are available in the child delta and current snapshot,
  even if the user projection omits them;
- duplicate exact identities are impossible under PostgreSQL constraints or
  detected during state build;
- UPDATE can identify both the old and new identity when partition or order
  keys change.

The side row relation stores both the framed hash and the typed identity tuple.
Hash equality narrows a lookup; `IS NOT DISTINCT FROM` on the identity tuple
confirms it. A duplicate exact identity or a hash collision between distinct
identities fails closed. It must not update an arbitrary target row.

For admitted nodes, derive the target `__pgt_row_id` from the stable child
identity and semantic node ordinal. Use that formula in:

- initial population;
- protected FULL and reinitialization;
- incremental output;
- cost-selected partition recomputation;
- invariant validation.

Existing window stream tables use the old positional hash and must
reinitialize before the new algorithms run.

### 4.5 Deterministic ordering without changing peers

Append the stable identity as an internal tie-breaker for row-position
operations. The original ORDER BY tuple alone defines peer equality for
`RANK`, `DENSE_RANK`, and RANGE frames.

This split gives two keys:

- `peer_key`: the original ORDER BY values with PostgreSQL collation and NULL
  semantics;
- `row_key`: `peer_key` plus the stable identity, used only to choose one row
  inside a peer group.

For ROW_NUMBER, LAG, LEAD, NTH_VALUE, and ROWS frames, the internal tie-breaker
chooses one valid PostgreSQL row order among peers. FULL, fallback, and
incremental paths must use the same effective row order.

Do not append that tie-breaker to the SQL ORDER BY of a RANGE frame. Doing so
would split PostgreSQL peer groups and change the frame. RANGE strategies group
by the original peer key, then use stable identity only for functions such as
FIRST_VALUE or LAST_VALUE that must select one row inside a peer. FULL and
fallback rendering must use the same two-level calculation.

## 5. LT-7a: State model, persistence, and bounds

### 5.1 Focused registry

Add this catalog table to fresh-install and upgrade SQL:

```sql
CREATE TABLE pgtrickle.pgt_window_states (
    pgt_id              bigint NOT NULL
                        REFERENCES pgtrickle.pgt_stream_tables(pgt_id)
                        ON DELETE CASCADE,
    node_ordinal        integer NOT NULL,
    spec_ordinal        integer NOT NULL,
    partition_relid     oid NOT NULL,
    row_relid           oid NOT NULL,
    peer_relid          oid,
    schema_version      smallint NOT NULL,
    strategy_version    smallint NOT NULL,
    query_hash          bigint NOT NULL,
    state_generation    bigint NOT NULL,
    status              text NOT NULL
                        CHECK (status IN
                               ('BUILDING', 'READY', 'STALE', 'OVER_BUDGET')),
    estimated_bytes     bigint NOT NULL DEFAULT 0
                        CHECK (estimated_bytes >= 0),
    last_validated_at   timestamptz,
    updated_at          timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (pgt_id, node_ordinal, spec_ordinal)
);
```

Use the next available state and strategy version constants at implementation
time. Store stable, deterministic relation names in `window_strategy`; use OIDs
in the registry for fast live lookup. Cast every catalog `name` value to text
when Rust reads it.

The registry is private derived state. Revoke PUBLIC access. Include it in
extension ownership and lifecycle cleanup, but exclude its rows from logical
restore. Do not reuse `pgt_set_operation_states`; its multiplicity contract is
unrelated.

### 5.2 Versioned `window_strategy`

Add nullable `window_strategy JSONB` to `pgt_stream_tables` and
`StreamTableMeta`. The JSON shape is versioned and deterministic:

```json
{
  "schema_version": 1,
  "strategy_version": 1,
  "query_hash": 123,
  "identity_version": 1,
  "nodes": [
    {
      "node_ordinal": 0,
      "spec_ordinal": 0,
      "state_name_prefix": "pgtrickle.__pgt_window_42_0_0",
      "partition_keys": ["dept"],
      "order": ["salary DESC NULLS LAST"],
      "functions": [
        {
          "function_ordinal": 0,
          "alias": "rn",
          "kind": "row_number",
          "strategy": "ordered_suffix",
          "eligible": true,
          "fallback_reason": null
        }
      ]
    }
  ]
}
```

The production JSON also records type OIDs, typmods, collations, normalized
frames, constant offsets, and state readiness. It must not store raw argument
values, source data, transient CTE names, or only a relation OID.

Serialize and deserialize through typed Rust structs. Unknown schema or
strategy versions return a controlled state mismatch. Tests compare the full
JSON contract so accidental field removal is visible.

### 5.3 Typed side relations

Create up to three LOGGED relations per semantic specification. Create only
the relations required by the chosen functions.

The partition relation contains one row per tracked partition:

- typed partition key columns `p1..pn`;
- a framed `partition_hash` accelerator;
- `row_count bigint`;
- first and last row identities;
- the NTH identity array up to the largest admitted N;
- whole-partition SUM and COUNT state where required;
- `state_generation bigint`;
- estimated logical bytes and last-use time;
- a primary or unique identity based on the hash plus exact NULL-safe key
  validation.

The ordered row relation contains one row per child row:

- `input_row_hash bigint` and typed exact identity columns;
- typed partition keys;
- typed original ORDER BY keys;
- the stable internal tie-breaker;
- typed function argument and default-expression values needed by admitted
  strategies;
- current materialized window outputs needed to seed suffix updates;
- `state_generation bigint`.

Create a btree that matches the complete effective row order. Add a separate
peer-key index only when rank or RANGE strategies need it.

The peer relation exists for RANK, DENSE_RANK, or cumulative RANGE aggregates.
It contains one row per exact peer tuple:

- typed partition and ORDER BY keys;
- `peer_count bigint CHECK (peer_count > 0)`;
- current `rank_value` and `dense_rank_value` when required;
- peer-local SUM input state and non-NULL COUNT state when required;
- cumulative prefix SUM and COUNT state when required;
- `state_generation bigint`.

Use exact typed equality for every state lookup. Hashes and indexes are
accelerators only. Dynamic DDL must quote identifiers through the existing
helpers and use `format_type()` results from analyzed OIDs.

### 5.4 Initialization and rebuild

Build target data and state from one protected source snapshot:

1. Acquire the existing stream-table and source locks.
2. Create shadow state relations with `BUILDING` registry rows.
3. Materialize the window child's current snapshot once, including internal
   identity, partition keys, order keys, arguments, and pass-through values.
4. Reject duplicate exact identities or unresolved types.
5. Populate ordered rows, partitions, peers, and prefix values with PostgreSQL
   window and aggregate SQL.
6. Populate the user stream table with the same deterministic effective order
   and stable target row IDs.
7. Validate row counts, exact identities, partition totals, peer counts, and
   selected window outputs.
8. Replace old state registry entries and relations only after the new state
   validates.
9. Set `window_strategy`, registry status `READY`, and one shared generation.
10. Let the existing finalizer commit target, state, metadata, and frontier.

If any step fails, PostgreSQL rolls back the target, registry, and shadow state.
Do not leave a READY registry row that points at a partially built relation.

### 5.5 State validation and mismatch handling

Validate cheap structural facts before incremental execution:

- JSON schema, strategy, identity, and query-hash versions match;
- every expected registry row exists exactly once;
- OIDs resolve to the deterministic name and an ordinary permanent LOGGED
  table in `pgtrickle`;
- extension ownership and owner are correct;
- column type OIDs, typmods, collations, nullability, and checks match the plan;
- required indexes exist, are valid, and have the expected order definition;
- registry and relation generations match;
- registry status is READY.

Do not count every state row on every refresh. Run exact data validation during
build, explicit repair, optional delta-invariant validation, upgrade tests, and
diagnostic health checks. Cache a successful structural validation under the
same DDL generation used by v0.88 template caching.

On a structural mismatch:

1. Stop before reading the child delta for mutation.
2. Set `needs_reinit = true` with `WINDOW_STATE_MISMATCH` and an actionable
   detail naming the missing or invalid object.
3. Invalidate delta templates and state validation caches.
4. Run the existing protected reinitialization path on the next eligible
   refresh.

Do not silently rebuild one table while concurrent source writes are allowed.

### 5.6 Budget enforcement

Extend `MemoryBudget` with `window_state_bytes = total_bytes`. This guard does
not reduce the existing delta-pipeline, template-cache, DAG, or invalidation
shares. It also does not promise that PostgreSQL caches the whole state in RAM.

Apply the guard per stream table:

- Estimate a new partition from analyzed row width and actual first-batch row
  width before admitting it.
- Refresh `estimated_bytes` from `pg_total_relation_size()` after a material
  change, state build, relation rewrite, or ANALYZE. Avoid that catalog call per
  input row.
- At 80 percent, add a health warning and expose utilization in diagnostics.
- Before a write can cross 100 percent, choose partition recomputation for the
  affected partition.
- If an already tracked partition grows past the hard bound, recompute it,
  delete its private rows transactionally, and leave it untracked. Absence of a
  tracked partition always means recomputation.
- Never create one marker row per rejected partition. Millions of untracked
  partitions must not grow metadata.
- When later deletes free enough state, a recomputed partition may be admitted
  and rebuilt during that refresh.

Use the v0.87 delta-pipeline byte slice for the in-process neighbor ring and
temporary affected-row sets. Page those sets through the existing bounded
portal pipeline. A page limit cannot truncate a result delta.

Record `WINDOW_STATE_BUDGET_EXCEEDED` when any partition recomputes because of
the guard. Include current bytes, allowed bytes, and affected partition count
in the detail. Emit at most one warning per stream table per refresh.

### 5.7 Lifecycle ownership

One lifecycle helper owns create, validate, rebuild, and drop for window state.
Reuse it from:

- `create_stream_table` initial population;
- protected FULL refresh;
- `ALTER STREAM TABLE ... ALTER QUERY`;
- refresh-mode changes that newly require incremental state;
- `repair_stream_table`;
- reinitialization;
- logical-restore reconciliation;
- stream-table drop and failed-create cleanup.

Schedule-only ALTER leaves state untouched. A semantic query change builds
shadow state and swaps it transactionally. Do not mutate the old READY state in
place before the new query validates.

## 6. LT-7b: Rank-family algorithms

### 6.1 Shared affected-partition normalization

Normalize the child delta to one net old and new image per exact child
identity. An UPDATE may affect two partitions and two order positions.

For each partition, derive:

- the earliest old row key touched;
- the earliest new row key touched;
- peer groups whose counts change;
- the old and new partition row counts;
- the lower row key from which output can change;
- an estimated count of output rows that must be emitted.

Coalesce overlapping affected suffixes. Process partition keys in a stable
NULL-safe order so generated SQL and lock acquisition are deterministic.

### 6.2 `ROW_NUMBER()`

Use the ordered row relation as the sorted index.

For each affected partition:

1. Apply child DELETE and old UPDATE images to a transaction-local proposed
   state.
2. Apply child INSERT and new UPDATE images.
3. Find the first surviving row before the affected suffix through the btree.
4. Use its stored row number as the prefix seed, or zero at partition start.
5. Compute row numbers only for the new suffix.
6. Compare each computed value with the stored output and emit only changed,
   inserted, or deleted target rows.
7. Update the stored suffix values and partition count.

The work is proportional to the mandatory output suffix plus index lookups.
An insert at the front can still emit the whole partition. The crossover
selector may choose partition recomputation for that case.

### 6.3 `RANK()` and `DENSE_RANK()`

Use the peer relation to avoid treating tied rows as separate ranks.

For each affected peer group:

1. Apply its signed row-count change.
2. Reject a negative count as state corruption.
3. Delete the peer row only when the count reaches zero.
4. Find the preceding surviving peer.
5. Seed `rank_value` from preceding rank plus preceding count.
6. Seed `dense_rank_value` from preceding dense rank plus one.
7. Recompute only the affected peer suffix.
8. Join changed peer results to ordered rows and emit changed target rows.

Apply these family-specific shortcuts:

- Adding or removing a row inside an existing peer changes later RANK values
  but not later DENSE_RANK values.
- Creating or removing a peer changes later values for both functions.
- Rows inside one peer always receive the same rank and dense rank.
- With no ORDER BY, the partition is one peer and both results remain one.

Tests must cover ties containing NULLs, descending order, explicit NULLS FIRST
and LAST, collations, peer creation, peer removal, and simultaneous changes to
several peers.

## 7. LT-7c: Offset and boundary algorithms

### 7.1 `LAG()` and `LEAD()`

Admit only built-in LAG and LEAD calls whose offset is an immutable non-negative
integer constant. The omitted offset is one. Offset zero is valid. The value
and default expressions must be immutable row-local expressions with resolved
types. A dynamic, negative, NULL, unresolved, or oversized offset uses
partition recomputation with a specific reason.

The ordered row relation is durable state. The refresh uses a bounded ring:

- LAG needs changed rows and at most N following rows from both the old and new
  ordering.
- LEAD needs changed rows and at most N preceding rows from both orderings.
- An order-key or partition-key UPDATE contributes both a removal interval and
  an insertion interval.
- Merge overlapping intervals before reading rows.
- Load N context rows beyond each interval so PostgreSQL can evaluate the
  offset correctly, then discard context-only outputs.

Use PostgreSQL LAG or LEAD over this bounded ordered slice. Do not implement
polymorphic datum copying or default-expression coercion in Rust. Compare the
new values with state and emit only changed rows.

If `N * estimated_value_width` cannot fit one bounded pipeline page, select
`WINDOW_OFFSET_EXCEEDS_BUDGET` before mutation.

### 7.2 `FIRST_VALUE()` and `LAST_VALUE()`

Admit these frame shapes:

| Function | Frame | Incremental state |
|---|---|---|
| FIRST_VALUE | default cumulative RANGE | first row identity for the partition |
| FIRST_VALUE | ROWS or RANGE, unbounded preceding to current row | first row identity for the partition |
| FIRST_VALUE | ROWS or RANGE, unbounded preceding to unbounded following | first row identity for the partition |
| LAST_VALUE | default cumulative RANGE | last row identity in each peer group |
| LAST_VALUE | ROWS, unbounded preceding to current row | current row value; only the changed row is affected |
| LAST_VALUE | ROWS or RANGE, unbounded preceding to unbounded following | last row identity for the partition |

No admitted shape has an EXCLUDE clause. Other bounds use
`WINDOW_UNSUPPORTED_FRAME`.

When a tracked boundary row changes or moves, find its replacement with one
ordered-index lookup. Emit all rows whose admitted frame observes the changed
boundary. If the boundary identity and argument value do not change, emit no
unrelated rows.

### 7.3 `NTH_VALUE()`

Admit built-in NTH_VALUE with a positive immutable integer N and one of these
frames:

- default cumulative RANGE;
- ROWS or RANGE from unbounded preceding through current row;
- ROWS or RANGE over the whole partition.

Track the first `max(N)` stable row identities required by all NTH_VALUE calls
that share a specification. Rebuild only this bounded prefix after an insert,
delete, partition move, or order-key change that touches it.

For whole-partition frames, a changed Nth identity or value affects the whole
partition. For cumulative frames, it affects rows whose frame membership or
Nth value changes. Use the ordered and peer indexes to find that boundary; do
not scan rows before it.

If the indexed prefix cannot fit the state budget, use
`WINDOW_NTH_INDEX_EXCEEDS_BUDGET` for that partition.

## 8. LT-7d: Aggregate-over-window algorithms

### 8.1 Admitted shapes

v0.89 admits built-in COUNT and a closed built-in SUM type matrix for:

- the whole partition, including the default frame without ORDER BY;
- `ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`;
- default or explicit `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`;
- `ROWS` or `RANGE` from unbounded preceding to unbounded following.

Reject FILTER, DISTINCT, GROUPS, EXCLUDE, bounded preceding or following,
CURRENT ROW starts, and other following bounds in v0.89. The parser still
accepts them; the strategy planner records partition recomputation.

COUNT supports `COUNT(*)` and `COUNT(expr)`. SUM supports only analyzed
built-in signatures whose transition and inverse arithmetic preserve exact
PostgreSQL results. Start with exact integer and numeric signatures. Add
interval, money, or floating-point signatures only after an operator-specific
proof and exact oracle tests. Textual type names do not widen the matrix.

### 8.2 Whole-partition SUM and COUNT

Keep these values in partition state:

- physical partition row count;
- COUNT result state, respecting COUNT(*) versus COUNT(expr);
- SUM transition value;
- SUM non-NULL input count, so an all-NULL partition returns NULL.

Apply the signed child delta with PostgreSQL arithmetic. If the final row count
is zero, delete the partition state. If an aggregate output changes, every row
in the partition receives a new value; this mandatory output amplification is
part of the crossover estimate.

An overflow or PostgreSQL arithmetic error aborts the refresh. Do not catch it
and substitute partition recomputation after state mutation starts.

### 8.3 Cumulative ROWS frames

Store the current prefix SUM and COUNT result on each ordered row. For an
affected partition:

1. Find the row before the earliest changed row key.
2. Read its stored prefix state as the seed.
3. Apply PostgreSQL SUM and COUNT over the new ordered suffix.
4. Stop emitting when both the row membership and every maintained prefix
   value converge with stored state, if the implementation can prove that
   early stop for the admitted exact type.
5. Update state and emit the changed target suffix.

The stable identity tie-breaker defines row order inside peers. The algorithm
does not use peer summaries for ROWS semantics.

### 8.4 Cumulative RANGE frames

Aggregate at peer granularity:

1. Maintain peer-local SUM, non-NULL count, and physical count.
2. Find the peer before the earliest changed peer.
3. Seed from its stored cumulative values.
4. Recompute cumulative values only for the new peer suffix.
5. Assign one cumulative result to every row in each peer.

The peer relation is the prefix-sum index required by the output. A deeper
balanced tree is optional only after profiling proves that prefix seed lookup
or peer traversal dominates the mandatory target updates. Do not add one for a
theoretical logarithmic claim when every changed suffix row still must be
written.

### 8.5 Non-invertible aggregate fallback

`MIN()` and `MAX()` window aggregates with DELETE or UPDATE-old input remain on
partition recomputation unless an implementation PR includes a proof that
covers duplicate extrema, NULLs, collations, and replacement lookup.

The static strategy may admit an INSERT-only case only if source append-only
status is durable and the runtime verifies that the delta contains no DELETE or
UPDATE-old rows. The first violating delta chooses
`WINDOW_NON_INVERTIBLE_DELETE` before state mutation. v0.89 does not trust an
advisory append-only setting after contradictory CDC is observed.

## 9. LT-7e: Fallback, cost, reasons, and diagnostics

### 9.1 One fallback implementation

Extract the current partition-recompute CTE construction into a helper that can
accept a relation of selected partition keys. Both static and runtime fallback
use that helper.

For an admitted window table, fallback recomputation must:

- use the same stable child identity and deterministic effective order as the
  incremental path;
- rebuild state for the recomputed partition when it fits the budget;
- delete state and leave the partition untracked when it does not fit;
- produce the same ordinary delta relation consumed by existing apply code;
- remain inside the same refresh transaction and frontier interval.

Do not maintain two partition-recompute SQL implementations.

### 9.2 Stable reason codes

Generalize `FullRefreshReasonCode` and `FullRefreshReason` to refresh reasons
that also describe a DIFFERENTIAL partition fallback. Preserve every existing
string value and existing `was_full_fallback` behavior.

Add these stable v0.89 codes:

| Code | Meaning |
|---|---|
| `WINDOW_METADATA_UNRESOLVED` | PostgreSQL analysis did not produce the OID, type, collation, or frame metadata required for proof. |
| `WINDOW_UNSUPPORTED_FUNCTION` | The function OID is outside the v0.89 matrix. |
| `WINDOW_UNSUPPORTED_FRAME` | The normalized frame, GROUPS mode, or EXCLUDE clause is outside the admitted matrix. |
| `WINDOW_UNSUPPORTED_ARGUMENT` | Offset, N, FILTER, default, or argument expression is not admitted. |
| `WINDOW_UNSUPPORTED_TYPE` | The analyzed type or collation lacks an exact algorithm. |
| `WINDOW_NO_STABLE_IDENTITY` | The child cannot provide one exact stable identity per row. |
| `WINDOW_STATE_INITIALIZATION_REQUIRED` | An upgraded or newly eligible table has no READY state. |
| `WINDOW_STATE_MISMATCH` | State relations, schema, version, generation, or query hash do not match. |
| `WINDOW_STATE_BUDGET_EXCEEDED` | Tracking the affected partition would cross its state ceiling. |
| `WINDOW_OFFSET_EXCEEDS_BUDGET` | The required LAG or LEAD neighbor ring cannot fit the working bound. |
| `WINDOW_NTH_INDEX_EXCEEDS_BUDGET` | The required NTH prefix cannot fit the state bound. |
| `WINDOW_NON_INVERTIBLE_DELETE` | A deletion invalidates a window aggregate without a proven inverse. |
| `WINDOW_RECOMPUTE_CHEAPER` | The measured cost model selects partition recomputation. |
| `WINDOW_IMMEDIATE_RECOMPUTE` | IMMEDIATE mode uses the retained partition path. |

If one refresh has several reasons, store the highest-priority code and a
deterministic detail list of every node, function, and partition count. The
priority order is state mismatch, semantic unsupported, budget, non-invertible
delete, cost crossover, and mode fallback.

`pgt_refresh_history.action` remains DIFFERENTIAL for partition recomputation,
and `was_full_fallback` remains false. Do not repurpose
`merge_strategy_used`; it continues to describe the target apply method. A
fully incremental window refresh has no window fallback reason. A recompute or
mixed refresh records its reason and node-level counts in
`refresh_reason_detail`.

### 9.3 Crossover selector

Add one pure decision function to the v0.88 cost-planning layer. Inputs are:

- function family and strategy version;
- partition row and peer counts;
- normalized child delta counts;
- earliest affected row or peer position;
- estimated emitted target rows;
- estimated state rows and bytes written;
- measured family coefficients;
- whether the state is already warm and valid.

Compare incremental work with partition recomputation. Choose incremental only
when the versioned evidence predicts a material win. Missing counts,
unversioned coefficients, NaN, overflow, or a tie selects recomputation.

Do not add a crossover GUC. Commit the selected constants with the benchmark
raw summary and strategy version. Require the hybrid selector to stay within 5
percent of the faster measured strategy across the release matrix. Publish the
actual crossover by family, partition size, delta position, and delta shape.

### 9.4 Explain and monitoring contract

Extend `pgtrickle.explain(name)` and `explain_json(name)` with:

- each window node and function ordinal;
- normalized function, frame, partition, and ordering;
- static strategy and static fallback reason;
- state status, schema version, generation, bytes, budget, and utilization;
- current partition and peer counts when the query can fetch them cheaply;
- last actual strategy and fallback reason;
- estimated emitted rows and crossover evidence;
- whether reinitialization is required.

Add the same semantic strategy section to v0.88 `explain_delta_plan()` without
executing the defining query, consuming change rows, touching state, or

Extend `health_check()` with one warning row per over-80-percent or invalid

## 10. Transaction, crash, restore, and ALTER behavior

### 10.1 Differential transaction order

Keep the v0.87 pipeline and v0.88 apply contract. Within one transaction:

1. Lock the stream table through the existing refresh lock.
2. Validate state and choose strategies.
3. Materialize or page the child delta.
4. Build proposed state and the result delta.
5. Apply target DELETE, UPDATE, and INSERT operations.
6. Apply state changes.
7. Capture downstream CDC and run existing user-trigger policy.
8. Advance the shared state generation.
9. Finalize frontier, history, status, and notification.

The implementation may swap steps 5 and 6 for a measured batching reason
because PostgreSQL rolls back both. It must keep them in one transaction and
must not expose a READY generation until both complete.

### 10.2 Crash recovery

LOGGED state plus the existing atomic finalizer is the crash-recovery model.
Test these interruption points:

- after proposed state is materialized but before target apply;
- after target apply starts but before state generation advances;
- after state writes but before frontier finalization;
- during a cost-selected partition rebuild;
- during shadow-state initialization for ALTER.

Use a test trigger that blocks a state statement, then terminate the backend or
kill and restart the full E2E PostgreSQL container. Do not ship a production
failpoint GUC only for these tests.

After recovery, assert that target rows, state generation, state contents,
frontier, successful history, and downstream buffers are either all old or all
new. The next refresh must replay and converge from the unchanged frontier.

### 10.3 Physical backup and replication

Physical backups, PITR, and physical standbys include the LOGGED state
relations. Add a recovery test that restores or restarts from a physical copy,
then applies INSERT, UPDATE, and DELETE changes and verifies exact convergence.

State tables must produce WAL like any other LOGGED relation. Benchmark and
publish that WAL overhead. Do not offer an UNLOGGED performance option in
v0.89.

### 10.4 Logical dump and restore

Treat window state as derived:

- dump `pgt_stream_tables.window_strategy` as durable diagnostic metadata;
- exclude `pgt_window_states` rows and dynamic state contents;
- on restore, ignore stale live OIDs and mark window tables for protected
  reinitialization;
- resolve stream storage and sources by the existing stable-name process;
- rebuild target state, CDC, frontier, and window state under source locks;
- clear `needs_reinit` only after exact validation succeeds.

Extend `tests/e2e_pg_dump_tests.rs` with changed relation OIDs. Create filler
objects before restore so the test cannot pass by accidental OID reuse.

### 10.5 ALTER and mode changes

- Schedule, freshness, and unrelated option changes preserve READY state.
- A query change compares semantic plan fingerprints, not raw whitespace.
- A partition, order, frame, function, argument, result type, collation,
  identity, or parser-strategy change builds shadow state.
- A compatible output-column change may reuse state only when the semantic
  fingerprint and all stored value columns remain exact.
- A change to configured FULL may retain READY state, but every subsequent
  FULL refresh must rebuild it if AUTO or DIFFERENTIAL can later reuse it.
- A change from FULL-only to DIFFERENTIAL builds state through protected
  reinitialization before accepting the first incremental interval.
- DROP removes registry and dynamic relations transactionally. Failed cleanup
  uses the existing retry mechanism.

## 16. Risks and mitigations

| Risk | Mitigation |
|---|---|
| A shifted rank changes most of a partition | Estimate emitted rows before mutation and choose partition recomputation at the measured crossover. Publish output amplification. |
| Ties make row order unstable | Separate peer equality from a stable identity tie-breaker and use the same effective order in FULL, fallback, and incremental paths. |
| Child identity is absent or duplicated | Require an exact identity proof and fall back before state build. Validate exact tuples, not only hashes. |
| Parser text loses PostgreSQL semantics | Collect OIDs, types, collations, FILTER, and frame flags from the analyzed tree. Unknown metadata fails closed. |
| State and target diverge on crash | Keep LOGGED state, target apply, generation, frontier, and history in one transaction; kill the backend and postmaster in E2E tests. |
| Logical restore retains stale OIDs | Exclude derived registry/state rows, resolve stable names, mark `needs_reinit`, and rebuild under source locks. |
| Millions of partitions exhaust state | Enforce a per-stream-table byte ceiling, keep rejected partitions untracked, and expose health warnings without marker rows. |
| State size checks become a hot-path query | Use width estimates per batch and refresh `pg_total_relation_size()` only after material changes. |
| LAG or LEAD copies too much context | Merge intervals, page through the existing bounded pipeline, and reject offsets whose ring cannot fit. |
| SUM inverse arithmetic differs from PostgreSQL | Use analyzed built-in OIDs and PostgreSQL arithmetic, start with exact types, and keep unproved signatures on recomputation. |
| RANGE treats peers like ROWS | Maintain peer-local and peer-prefix state separately; use the original ORDER BY tuple for peer equality. |
| A mixed-function node produces partial rows | Let any function fallback choose node-level partition recomputation for that refresh. |
| Runtime fallback applies changes twice | Select before mutation. Any later failure aborts and replays from the unchanged frontier. |
| Dynamic state relations leak on ALTER or DROP | Use one lifecycle owner, shadow builds, extension membership, and the existing cleanup retry path. |
| State maintenance adds more WAL than it saves in CPU | Measure WAL and total refresh time. Disable an incremental region that misses the performance gate. |
| A deep prefix tree adds complexity without reducing work | Start with stored row and peer prefixes. Add a deeper tree only from profiling evidence and an isolated proof. |
| v0.88 planner changes invalidate state ordinals | Derive semantic ordinals before physical planning and include strategy version in cache and state validity. |

## 17. Recommended pull-request sequence

Keep each PR deployable and correctness-complete:

1. **Semantic contracts.** Add typed frames, analyzed metadata, semantic
   ordinals, identity proof, reason strings, and unit tests. Do not route
   runtime execution yet.
2. **State foundation.** Add catalog schema, typed LOGGED relations, lifecycle,
   stable FULL identity, exact validation, budget, crash tests, and upgrade SQL.
   Runtime still uses partition recomputation.
3. **Rank family.** Add ROW_NUMBER, RANK, and DENSE_RANK with mutation property
   tests and fallback routing.
4. **Offsets and boundaries.** Add LAG, LEAD, FIRST_VALUE, LAST_VALUE, and
   NTH_VALUE with bounded-state and mutation tests.
5. **SUM and COUNT.** Add whole-partition, cumulative ROWS, and cumulative RANGE
   algorithms with exact type and NULL tests.
6. **Crossover and diagnostics.** Extract one fallback helper, add measured cost
   routing, refresh reasons, explain output, health checks, and metrics.
7. **Recovery and upgrade closure.** Add backend/postmaster crash, physical and
   logical restore, ALTER, repair, and old-table automatic reinitialization.
8. **Performance and release closure.** Commit the benchmark evidence, support
   matrix, documentation, generated artifacts, version bump, and full CI run.

Do not split state mutation from its rollback and frontier tests. Do not enable
a function family in a PR that lacks its DIFFERENTIAL-versus-FULL property
oracle and explicit fallback cases.
