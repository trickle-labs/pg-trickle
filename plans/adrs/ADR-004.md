# ADR-004: Frontier Durability Model — Single-Phase Canonical Path

**Status:** ✅ Accepted (v0.72.0), strengthened by the v0.82.0 visibility gate
**Date:** 2026-05-26  
**Authors:** pg_trickle maintainers  
**Replaces:** DUR-1 tentative-frontier design (never shipped, removed in v0.72.0)

---

## Context

Every pg_trickle refresh cycle advances a *frontier* — a per-stream-table
JSON map of source OID → WAL LSN that records the highest change-buffer
position consumed by the last successful refresh. The frontier is the sole
durability signal used by the differential engine to avoid re-processing
already-consumed changes and to detect new work on each scheduler tick.

A crash between the MERGE commit and the frontier catalog update produces
a window where the data change is committed but the frontier was not
advanced. On restart, the scheduler would re-process the same change-buffer
rows and produce double-counted results.

### DUR-1 (Rejected Design)

Between v0.20 and v0.71, the codebase contained a two-phase tentative-frontier
design (catalogued as DUR-1) with three functions:

- `prepare_frontier(pgt_id, frontier)` — writes the proposed frontier to a
  `tentative_frontier` column before MERGE.
- `finalize_frontier_and_complete_refresh(pgt_id, rows)` — promotes
  `tentative_frontier → frontier` after MERGE commits.
- `reconcile_tentative_frontiers(change_schema)` — called on scheduler
  startup to detect and resolve stale tentative frontiers.

**DUR-1 was never wired**: no production call site existed for any of the
three functions. The v0.71 assessment (PLAN_OVERALL_ASSESSMENT_14.md)
confirmed this and flagged two additional defects:

1. The recovery query in `reconcile_tentative_frontiers` contained invalid
   SQL (`FROM {schema}.changes_ || s.pgt_relid::text` is not valid
   relation-name concatenation syntax — it would always fail at runtime).
2. The scheduler hot-path used `store_frontier()` (the single-phase call)
   and treated failure as log-only, giving no durability guarantee
   regardless of which design was intended.

---

## Decision

**Use the canonical single-phase frontier path and make failure fatal.**

The v0.82.0 release adds a prerequisite to that single write: the frontier
must come from a fresh, fail-closed visibility probe covering active writer XIDs,
backend XMINs, and prepared transactions. FULL baselines acquire deterministic
source `SHARE` locks before capturing their bound. A transactionally committed
frontier is therefore both atomic with the refresh data and proven not to skip
an invisible CDC row.

The chosen design:

1. **Single write**: `store_frontier()` or `store_frontier_and_complete_refresh()`
   is the only mechanism for advancing the frontier. Both run in the same
   SPI transaction as the MERGE/INSERT, so PostgreSQL's WAL guarantees
   atomicity: either the data change **and** the frontier are committed, or
   neither is.

2. **Failure = transaction abort**: All scheduler refresh paths now
   propagate `store_frontier` errors (using `?`) instead of logging and
   continuing. This means a frontier-store failure aborts the transaction,
   rolling back both the data change and the frontier update. The ST is
   retried on the next scheduler tick with the old frontier, so no changes
   are skipped and no double-counting occurs.

3. **DUR-1 removed**: `prepare_frontier`, `finalize_frontier_and_complete_refresh`
   (DUR-1 variant), and `reconcile_tentative_frontiers` are deleted. The
   `tentative_frontier` column is retained in the schema for operator
   visibility but is never written.

4. **Documentation**: The decision is recorded here and referenced from
   `src/catalog.rs`.

---

## Rationale

### Why not implement DUR-1?

DUR-1 would provide crash-safety for the window between the MERGE commit
and the frontier catalog update — a real but very narrow race. However:

- **PostgreSQL WAL already provides this guarantee** when the frontier
  update runs in the same transaction as the MERGE (the current design).
  A crash between MERGE and `COMMIT` rolls back both. A crash after
  `COMMIT` means the frontier is also committed.

- **The race only exists between** `COMMIT` of one SPI sub-transaction
  and the `UPDATE` to `frontier` in a *separate* subsequent call. In the
  current implementation, `store_frontier_and_complete_refresh` is a
  single UPDATE that commits atomically with the MERGE by design (both
  are in the same outer transaction).

- The DUR-1 design attempted to protect against a problem that the
  current single-transaction design already prevents. Implementing it
  would add complexity without correctness gain.

### Why not a two-phase commit?

PostgreSQL does not natively support 2PC between two catalog UPDATE
statements in the same backend. Any two-phase design requires the
tentative column, which requires correct recovery logic, which had
invalid SQL. The single-transaction guarantee is simpler and correct.

---

## Consequences

### Positive

- **Correctness**: Frontier advancement is atomic with the data change.
  No crash window exists between them.
- **Simplicity**: One canonical API instead of two competing designs.
- **Test confidence**: All frontier paths are now tested by the same
  test infrastructure (TEST-003 unit tests, integration/E2E refresh tests).

### Neutral

- The `tentative_frontier` column in `pgt_stream_tables` is retained
  (removing a catalog column in a patch would require a migration). It
  will always be NULL after v0.72.0.

### Negative

- If a future use case requires cross-transaction durability (e.g.
  external coordinator), a new ADR will need to be written.

---

## Alternatives Considered

| Alternative | Verdict |
|-------------|---------|
| Implement DUR-1 with corrected SQL | Rejected — adds complexity for a problem the single-tx design already prevents |
| Remove `tentative_frontier` column | Deferred — catalog column removal is a migration concern; column is retained but unused |
| Two-phase commit via `PREPARE TRANSACTION` | Rejected — requires `max_prepared_transactions > 0`, not guaranteed in all deployments |
