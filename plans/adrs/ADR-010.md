# ADR-010: PostgreSQL owns physical delta-query planning

| Field | Value |
|-------|-------|
| **Status** | Accepted |
| **Date** | 2026-08-31 |
| **Deciders** | pg_trickle core team |
| **Category** | DVM performance / planning |

## Context

v0.88.0 needs smaller intermediate delta relations. A pg_trickle-specific
cost planner could reorder joins and filters before SQL generation, but
PostgreSQL already estimates relational expressions and chooses join order,
join algorithms, and build sides. Duplicating that optimizer would require a
second statistics model that can drift from the server executing the query.

Some DVM operators still hide useful facts. Change-buffer ranges, row
multiplicity, and semantic barriers are pg_trickle concepts. PostgreSQL cannot
select a rewrite that pg_trickle never expresses as relational SQL.

## Decision

Express safe alternatives as ordinary relational SQL and let PostgreSQL choose
the physical plan. pg_trickle records its source estimates, semantic barriers,
candidate rewrites, validation state, and observed execution data. New rewrite
classes start in shadow mode.

pg_trickle may select a rewrite only after exact-result tests and the frozen
benchmark corpus meet that class's regression budget. It never overrides
PostgreSQL's physical join algorithm or hash build side. Missing or unreadable
statistics preserve the current SQL.

## Consequences

The v0.88.0 planner is small. It owns DVM semantic admission, evidence, and
rewrite validation, while PostgreSQL remains the cost optimizer. The engine
diagnostic reports both the pg_trickle decision and the PostgreSQL plan so an
operator can inspect either layer.
