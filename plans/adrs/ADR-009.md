# ADR-009: Dependency-free aggregate pages

| Field | Value |
|-------|-------|
| **Status** | Accepted |
| **Date** | 2026-08-31 |
| **Deciders** | pg_trickle core team |
| **Category** | DVM performance / dependencies |

## Context

v0.88.0 adds a vectorized path for built-in aggregates over one source scan.
The executor needs owned, column-oriented pages for `COUNT`, `SUM`, `AVG`,
`MIN`, and `MAX`. One option was to restore `arrow-array` and
`arrow-compute`, which v0.76.0 removed with the DuckLake sink.

The supported v0.88.0 types fit in a small set of concrete `Vec<T>` columns.
SPI reads and PostgreSQL apply statements remain part of every refresh, so an
array library cannot remove those costs. Restoring Arrow would add compile
time, transitive dependencies, and an audit obligation without expanding the
accepted SQL surface.

## Decision

Use dependency-free typed Rust columns. Keep the page size at 1,024 source
rows and use checked scalar loops that LLVM can auto-vectorize. PostgreSQL
continues to own final result types, `AVG` division, collation behavior, and
`MIN` or `MAX` repair after an extremum deletion.

Do not add a generic dataframe or architecture-specific SIMD intrinsics. Add
Arrow only after an end-to-end benchmark shows at least 20 percent more
throughput than the typed-column path on the frozen v0.88.0 workload.

## Prototype evidence

Measurements used the same Apple M1 Pro host (10 cores, 32 GB, arm64 macOS
26.6.2), Rust 1.98.0, 1,024-row nullable `int8` pages, one warmup, and five
measured repetitions. The Arrow candidate used `arrow-array` and the current
`arrow-arith` aggregate kernels at 58.4.0; Arrow no longer publishes the
originally proposed `arrow-compute` crate as one unit.

| Measurement | Typed `Vec` | Arrow candidate |
|---|---:|---:|
| Clean debug build | 0.29 s | 9.43 s |
| Clean release build | 0.50 s | 23.75 s |
| Incremental release build | 0.29 s | 0.48 s |
| Release prototype binary | 453,536 bytes | 502,912 bytes |
| Normal dependency packages | 1 | 40 |
| COUNT/SUM/AVG/MIN/MAX page throughput | 1,370,880 pages/s | 438,681 pages/s |
| Median time for 20,000 pages | 14.589 ms | 45.591 ms |
| Five-run range | 13.105–15.871 ms | 45.550–46.246 ms |

The owned representation used by the extension stores one value vector and
one byte-per-row NULL vector. On the frozen SUM/COUNT/AVG workload,
`VectorPage::bytes()` caps the three copied columns, NULL maps, and actions at
16 KiB for a full page. Arrow's bitmap is smaller, but its prototype kernel was
68 percent slower and its fixed build and dependency costs are much larger.

The end-to-end gate includes SPI copy and PostgreSQL apply, which neither
representation removes. The committed benchmark artifacts in
`benchmarks/vector-aggregate-v0.88/` record that result against v0.87.17. The
Arrow page prototype already misses the 20 percent acceptance threshold before
those shared costs are added, so integrating the losing prototype into the
extension could not reverse the decision.

Commands and raw prototype source were intentionally not added to the product
tree. The reproducible shape was:

```text
cargo build [--release] --offline
cargo build [--release] --features arrow --offline
cargo tree --no-default-features --prefix none
cargo tree --features arrow --prefix none
```

The repository's `cargo deny check` remains the license and advisory gate for
the accepted dependency set. It passes without restoring any Arrow crate.

## Consequences

`Cargo.toml` and `Cargo.lock` gain no production dependency. Eligibility stays
narrow because each supported PostgreSQL type needs an explicit owned
representation and equivalence test. Unsupported types use the existing SQL
producer.
