# v0.86.0 Implementation Plan — Product UX and Transparency

> **Status:** Planned
> **Target:** v0.86.0
> **Baseline:** v0.85.0
> **Roadmap:** [roadmap/v0.86.0.md](../roadmap/v0.86.0.md)
> **Last updated:** 2026-08-20

## 1. Outcome

v0.86.0 turns existing refresh, cost, CDC, and scheduling state into one
coherent user-facing diagnostic surface. A user must be able to determine:

1. how a stream table is refreshed;
2. what work the next refresh is likely to perform;
3. why a FULL refresh occurred;
4. whether the declared freshness target is plausible;
5. how the table is behaving over time; and
6. whether reading the stream table is returning recently verified data.

The release adds:

- `pgtrickle.explain(regclass-or-name)` and `pgtrickle.explain_json(...)`;
- a complete, durable reason contract for FULL refreshes;
- a shared creation/preview warning engine;
- `pgtrickle.pg_stat_pgtrickle` and reset functions;
- opt-in annotations in PostgreSQL `EXPLAIN` output; and
- `target_freshness` on the function-based create/alter APIs.

The implementation must reuse the v0.82–v0.85 refresh finalizer, history,
cost summary, ownership, dependency, and CDC contracts. It must not create a
second refresh state machine, execute a user's defining query merely to
estimate cost, or introduce the v0.90 closed-loop freshness controller early.

### 1.1 Release invariants

- Every FULL refresh started by v0.86 code has a stable machine-readable
  reason code and a human-readable detail sentence.
- Refresh history, catalog state, statistics, and diagnostics are finalized
  from the same typed refresh result.
- The text and JSON explain functions are two renderers of one data model.
- Creation and preview use one analysis result and therefore return the same
  warnings for the same inputs.
- `pg_stat_pgtrickle` is bounded by the number of stream tables; scraping it
  does not rescan unbounded refresh history per row.
- With `pg_trickle.explain_annotations = off`, the EXPLAIN hook performs no
  SPI or catalog work.
- `target_freshness` is translated once into existing controls. No background
  loop continuously retunes those controls in this release.
- Estimates explicitly report missing evidence. Planner cost units, wall-clock
  milliseconds, and CDC microseconds must not be presented as interchangeable.
- Existing public APIs and views remain available unless an overload must be
  replaced to remove PostgreSQL default-argument ambiguity.
- Committed refresh data and refresh-history durability are never weakened for
  diagnostic convenience.

### 1.2 Roadmap ambiguity resolved

The roadmap example displays eight explain fields, while its exit criterion
says “all seven fields.” The implementation will return all eight displayed
fields and treat “seven” as a counting typo:

1. refresh mode;
2. estimated changed rows;
3. dominant cost;
4. expected refresh time;
5. current lag;
6. next scheduled refresh;
7. FULL fallback threshold/reason; and
8. write-path overhead.

## 2. Current-State Gap Map

| Roadmap item | Existing foundation | Gap to close |
|---|---|---|
| UX-2 explain | `api::explain_stream_table`, `monitor::explain_st`, `api::diagnostics::{explain_refresh_mode, explain_delta}`, `diagnostics.rs`, `pgt_cost_model_summary` | Diagnostics disagree, use string heuristics, and do not share a stable result model. No JSON counterpart exposes the flagship eight-field contract. |
| UX-3 FULL reasons | Some fallback paths call `set_refresh_reason`; an older upgrade migration adds `refresh_reason` | Fresh bootstrap omits the column, the thread-local reason is not consumed by production finalization, and many FULL paths have no reason. |
| UX-4 warnings | Create warns about source identity, RLS, `SELECT *`, and volatile functions; preview performs separate parsing | Warning decisions and formatting are duplicated, HINTs are inconsistent, and preview cannot evaluate requested scheduling/freshness inputs. |
| UX-5 statistics | `pgt_refresh_history`, `pgt_refresh_summary`, `pgt_cost_model_summary`, `pg_stat_stream_tables`, and monitoring functions | The requested counters/percentiles are not maintained together, the existing view performs history work while scraped, and reset APIs do not exist. |
| UX-6 EXPLAIN | PostgreSQL 18 exposes per-plan and per-node EXPLAIN hooks in the generated pgrx bindings | No hook is registered and no session GUC controls annotations. |
| UX-7 target freshness | `freshness_deadline_ms`, schedule parsing, IMMEDIATE mode, tier selection, and `set_stream_table_sla` | Create/alter do not accept the target, special values are not represented, MANUAL is not an explicit scheduling state, and current SLA adjustment risks acting like a controller. |

Two existing inconsistencies must be repaired as part of the release rather
than hidden behind the new APIs:

- fresh installs and upgraded installs must agree on the refresh-history
  reason columns; and
- requested `AUTO` intent must be stored separately from the current concrete
  execution mode. Today AUTO is resolved at creation and then lost.

## 3. Target Design

### 3.1 One diagnostic snapshot, two renderers

Add a single internal `StreamTableExplanation` value assembled for one stream
table. It is not a second monitoring store; it joins bounded catalog/summary
state with live estimates. Both SQL functions render this same value:

- `pgtrickle.explain(stream_table) RETURNS text` uses a stable, readable
  eight-line layout; and
- `pgtrickle.explain_json(stream_table) RETURNS jsonb` preserves numeric,
  timestamp, nullable, source, confidence, and sample-count information.

Each JSON field should be an object when evidence metadata matters, for
example:

```json
{
  "expected_refresh_time": {
    "milliseconds": 40.2,
    "source": "observed_differential_history",
    "sample_count": 18
  }
}
```

Do not invent parallel top-level “confidence” columns for every measurement.
Unknown values remain `null` in JSON and read as “not enough history” or
“unavailable” in text.

Resolve the input through the existing canonical stream-table resolver and
apply the established public diagnostic visibility policy. The snapshot must
read catalog rows in short SPI blocks and perform plan inspection outside any
unnecessarily long-lived SPI connection.

#### Field derivation

| Field | Derivation | Cold/exception behavior |
|---|---|---|
| Refresh mode | Stored requested mode plus current concrete/effective mode | Show `AUTO → DIFFERENTIAL` or `AUTO → FULL`; show the concrete mode for explicitly configured tables. |
| Estimated changed rows | Existing CDC pending-change estimator across sources | Return `null` plus an explanation if a buffer/state cannot be inspected safely. |
| Dominant cost | Plan the applicable FULL or delta SQL with `EXPLAIN (FORMAT JSON, ANALYZE false)`; choose the node with the largest exclusive cost (`Total Cost` minus child costs) and label its relation/operator | Fall back to the OpTree classifier when PostgreSQL cannot produce a safe plan. Never run the defining query. |
| Expected refresh time | Existing cost-model summary: FULL observed average, or differential observed cost per delta row multiplied by pending rows and adjusted by existing OpTree complexity data | Return unknown until compatible samples exist; do not convert arbitrary planner cost units into milliseconds. |
| Current lag | `now() - last_refresh_at`, with creation time as the pre-first-refresh reference | Label this as “time since last successful verification.” It is not the v0.90 commit-to-visible freshness measure. |
| Next scheduled refresh | Shared duration/cron/tier due-time helper used by the scheduler itself | `on_commit`, `manual`, disabled, or unknown are explicit states rather than fabricated timestamps. |
| FULL fallback threshold | Per-table AUTO threshold or the relevant GUC default, plus the most recent FULL reason code/detail | For non-AUTO tables, state whether FULL is configured or not applicable. |
| Write-path overhead | Aggregate sampled time for pg_trickle-generated CDC trigger functions from PostgreSQL function statistics when available | Return unknown when `track_functions` or sample counts do not support a defensible estimate. |

The text renderer may format approximate units (`~40 ms`, `2,400`, `3.1 µs`),
but JSON keeps base numeric units: rows, milliseconds, microseconds per call,
and UTC timestamps.

Extract next-due-time calculation from the scheduler into a pure helper used by
both scheduling and diagnostics. This prevents explain output from describing
a time the scheduler would not use and avoids a parallel cron implementation.

### 3.2 Persist requested mode separately from execution mode

Add `requested_refresh_mode` to `pgt_stream_tables` with values `AUTO`, `FULL`,
`DIFFERENTIAL`, and `IMMEDIATE`. Keep the existing `refresh_mode` as the
concrete mode consumed by execution and scheduling code.

- New creates store the user's request before AUTO admission resolves it.
- Existing rows are backfilled from their concrete mode; historic AUTO intent
  cannot be reconstructed and must not be guessed.
- Altering mode updates both requested and concrete values through the existing
  validation/admission path.
- Diagnostics say “AUTO chose …” only when `requested_refresh_mode = 'AUTO'`.

This is intentionally one new catalog column rather than widening the runtime
`RefreshMode` enum to let unresolved AUTO leak into executor branches.

### 3.3 Typed, durable FULL-refresh reasons

Replace the thread-local reason side channel with a typed result that flows
through the existing refresh finalization boundary.

Add an internal `FullRefreshReason` composed of:

- a closed `FullRefreshReasonCode` enum with a stable SQL string;
- a one-sentence detail assembled from measured/contextual values; and
- optional structured evidence retained in memory for diagnostics/logging when
  useful, without requiring an open-ended JSON catalog column.

Make a FULL executor entry point require a non-optional reason. Differential
fallback returns the same typed execution result as an explicitly selected
FULL run. The finalizer consumes that result once and updates history,
statistics, last-known catalog fields, and metrics. Remove
`LAST_REFRESH_REASON`, `set_refresh_reason`, and `take_refresh_reason` after all
callers have migrated.

At minimum, the code enum must cover these semantically distinct paths:

| Stable code | Used for |
|---|---|
| `FIRST_REFRESH` | Initial population |
| `CONFIGURED_FULL` | User explicitly selected FULL |
| `AUTO_QUERY_FULL_ONLY` | AUTO admission found no valid differential plan |
| `DELTA_RATIO_EXCEEDED` | Changed/base row ratio exceeded the selected threshold |
| `COST_MODEL_PREFERRED_FULL` | Observed cost model selected FULL |
| `CORRELATED_SUBQUERY_DELTA_QUADRATIC` | Correlated-subquery differential cost is unsafe |
| `CASE_IN_LIST_DVM_DRIFT_FULL_FALLBACK` | Existing CASE/IN-list drift safeguard |
| `REGEX_COMPLEXITY_CLASSIFIER_UNCERTAIN` | Existing conservative regex/classifier safeguard |
| `SOURCE_TRUNCATED` | Truncate invalidated row deltas |
| `SCHEMA_CHANGED` | A referenced schema shape requires rebuild |
| `FUNCTION_CHANGED` | A referenced function change requires rebuild |
| `ROW_IDENTITY_UPGRADE` | Row-identity migration/rebuild |
| `CDC_STATE_RECOVERY` | Missing/inconsistent CDC state requires rebuild |
| `FRONTIER_MISSING` | Required frontier state is unavailable |
| `FORCE_FULL_REFRESH` | Authorized force-full API/repair operation |
| `BUFFER_ROW_LIMIT_EXCEEDED` | Configured change-buffer safety limit |
| `JOIN_LIMIT_EXCEEDED` | Differential join safety limit |
| `AGGREGATE_SATURATION` | Aggregate safety/cost threshold |
| `DELTA_ESTIMATE_EXCEEDED` | Estimated delta work threshold |
| `WORK_MEM_CAP_EXCEEDED` | Memory estimate forced recomputation |
| `TEMP_SPILL_THRESHOLD_EXCEEDED` | Spill prediction/observation forced recomputation |
| `RECURSIVE_CTE_RECOMPUTE` | Recursive CTE semantics require recomputation |
| `SCC_FIXPOINT_RECOMPUTE` | Cyclic/fixpoint refresh executes as recomputation |
| `TOP_K_RECOMPUTE` | Top-K maintenance requires recomputation |
| `MANUAL_IMMEDIATE_REBUILD` | Explicit immediate-mode/manual rebuild path |
| `STREAM_TABLE_SOURCE_MANUAL_REBUILD` | Dependent stream table requires a manual rebuild |

During implementation, audit every caller of the FULL executor, every
`RefreshAction::Full`/reinitialize construction, initial-population history
write, scheduler action, manual API, SCC/fused path, and repair path. Add a code
only when a genuinely different existing path is found; do not build a
configurable reason registry.

Persist:

- `refresh_reason` as the stable code, preserving the name introduced by the
  old upgrade migration;
- `refresh_reason_detail` as the sentence shown to users; and
- `last_full_reason`/detail in bounded per-table state so the statistics view
  does not search history on every scrape.

If a schema/function change is detected before execution, store its typed
pending rebuild reason with the stream-table row. The eventual refresh
consumes it; this avoids reducing all delayed reinitializations to a generic
reason.

Pre-v0.86 historical FULL records may retain `NULL` because their exact causes
cannot be reconstructed honestly. The non-null invariant applies to new
v0.86 execution results and is enforced by the typed API plus tests, not by
lying during migration.

`refresh_history` exposes both code and detail. For explicitly configured FULL
tables the code is still required (`CONFIGURED_FULL`); the AUTO-focused explain
sentence is shown only for requested AUTO.

### 3.4 Shared warning analysis

Introduce one `CreationAnalysis` produced by the existing query validation and
source-inspection path. It contains the parsed OpTree/admission result and a
list of `CreationWarning` values:

- stable code;
- primary WARNING message;
- optional DETAIL/evidence;
- concrete HINT; and
- fields needed by preview JSON.

`create_stream_table()` renders the list with PostgreSQL WARNING/DETAIL/HINT.
`preview_stream_table()` serializes the same list, preserving all warnings
rather than a semicolon-delimited summary. Existing validation remains in its
current shared function; do not add a second parser or source walk.

Implement the six roadmap conditions:

| Warning code | Evidence | Required HINT direction |
|---|---|---|
| `ALWAYS_FULL` | AUTO admission or requested FULL means no differential execution | Identify the blocking query shape and suggest a supported rewrite or explicitly accepting FULL. |
| `REFRESH_COST_EXCEEDS_INTERVAL` | Compatible observed/initial cost is greater than the derived requested interval | Increase the target/interval, simplify the query, or choose manual/on-commit where valid. |
| `SOURCE_RLS_ENABLED` | Existing catalog RLS inspection | Review owner/role semantics and policies before relying on maintained results. |
| `SOURCE_IDENTITY_INADEQUATE` | Existing PK and replica-identity inspection | Add a stable primary key or suitable replica identity. |
| `WRITE_PATH_OVERHEAD_HIGH` | Sampled generated CDC trigger time exceeds the configured threshold | Inspect CDC trigger cost/batching and adjust the threshold only after measurement. |
| `JOIN_SOURCE_COUNT_HIGH` | Distinct joined source count is greater than `pg_trickle.warn_join_sources` | Reduce/split the join graph or accept the measured refresh/write cost. |

Add only the two configuration values needed by the roadmap contract:

- `pg_trickle.warn_join_sources` (integer, default `6`); and
- `pg_trickle.warn_write_path_overhead_us` (real, documented default chosen
  from repository benchmark evidence during implementation; `0` disables the
  warning).

Do not emit cost/overhead threshold warnings without compatible evidence.
Creation with initial population can compare its observed duration before
returning. Preview and cold-start creation report the estimate as unavailable
unless exact-query history or PostgreSQL function statistics provide samples.

Extend `preview_stream_table` just enough to accept the same relevant inputs
as creation (`schedule`, `refresh_mode`, `target_freshness`) with defaults. If
the new defaulted signature conflicts with the existing defaulted overload,
drop/replace that exact SQL signature in the upgrade script while preserving
ordinary one-argument calls.

### 3.5 Bounded cumulative statistics and reset semantics

Create `pgtrickle.pg_stat_pgtrickle` as the canonical per-stream-table
monitoring view. Retain `pg_stat_stream_tables` for compatibility in v0.86 and
document the new view as preferred.

Extend the existing summary tables rather than adding a third statistics
store:

- `pgt_refresh_summary` owns cumulative counters, reset boundary, last
  success/error, and last FULL reason;
- `pgt_cost_model_summary` owns observed duration aggregates and percentiles;
  and
- `pgt_stream_tables` owns identity/configuration and the declared freshness
  target.

Required output columns:

```text
pgt_id, schema_name, table_name,
total_refreshes, total_full_refreshes, total_diff_refreshes,
total_delta_rows_processed,
avg_refresh_duration_ms, p95_refresh_duration_ms, p99_refresh_duration_ms,
last_refresh_at, current_lag_ms, target_freshness_ms,
last_full_reason, last_error, last_error_at
```

Add `stats_reset_at` to the view as a useful PostgreSQL-style boundary marker.
Keep `last_full_reason` machine-readable and add
`last_full_reason_detail` so monitoring can display the sentence without
another lookup.

The existing once-per-refresh terminal summary upsert increments exactly one
of `total_full_refreshes` or `total_diff_refreshes` and adds processed delta
rows. Failed refreshes update error state but do not increment successful
refresh counters.

Compute average/p95/p99 in the existing batched cost-summary maintenance pass,
filtered by each table's reset boundary. Do not use an unbounded lateral
history percentile query in the view. Preserve the immutable audit history;
resetting statistics never deletes refresh records.

Reset behavior:

- `stat_reset(pgt_id)` checks stream-table ownership, serializes with terminal
  finalization using the established catalog lock order, zeroes counters, sets
  `stats_reset_at`, and clears derived duration samples/percentiles;
- `stat_reset_all()` is extension-owner/superuser only and performs the same
  operation for every stream table in one transaction; and
- operational `last_error` state is not erased by a statistics reset.

Reuse v0.84 ownership helpers and public-read/mutating API policy categories.

### 3.6 Opt-in PostgreSQL EXPLAIN annotations

Add `pg_trickle.explain_annotations` as a `USERSET` boolean GUC, default
`false`. Register a focused PostgreSQL 18 EXPLAIN hook module during
`_PG_init`, save existing hook pointers, and chain them in a stable order.

Use the native structured EXPLAIN property API, not raw text concatenation, so
TEXT, JSON, YAML, and XML formats remain valid. The property value is compact:

```text
lag 620 ms, last refresh 2026-06-04 10:31:02+00, mode DIFFERENTIAL
```

Implementation shape:

1. The per-plan hook exits after a single GUC branch when disabled.
2. When enabled, inspect the planned statement/range table, collect relation
   OIDs scanned by plan nodes, and fetch matching stream-table annotations in
   one short SPI query.
3. Hold that bounded map only for the duration of formatting the plan.
4. The per-node hook maps `scanrelid` to the cached entry and emits one native
   `pg_trickle` property for stream-table scan nodes.
5. Clear per-plan state on normal completion and error; never leak state into
   the next EXPLAIN in a pooled session.

The hook must validate pointers/node tags before dereference, annotate only
actual stream-table relations, avoid duplicate annotations, and give every
`unsafe` block a `// SAFETY:` explanation. It must not query catalogs once per
plan node. No new dependency is needed: pgrx's PostgreSQL 18 bindings expose
the per-plan/per-node hooks and `ExplainPropertyText`.

### 3.7 Declared `target_freshness`

Add optional `target_freshness => text` to create and alter. Accepted values:

- a positive PostgreSQL interval;
- `on_commit`; or
- `manual`.

Use PostgreSQL's interval input/conversion through parameterized SPI rather
than implementing another interval grammar. Reject zero/negative values,
overflow, and values whose calendar-month component cannot be translated to a
stable millisecond schedule without ambiguity.

Reuse `freshness_deadline_ms` for the numeric interval. Add one small
`target_freshness_mode` discriminator (`INTERVAL`, `ON_COMMIT`, `MANUAL`) to
represent the special values and declaration state. Do not duplicate the
numeric target in another column.

One-time translation rules:

| Declared target | Stored declaration | Existing controls set once |
|---|---|---|
| Positive interval | mode `INTERVAL`, `freshness_deadline_ms = interval` | Canonical duration schedule, bounded by existing minimums; the normal requested-mode admission result remains in effect. |
| `on_commit` | mode `ON_COMMIT`, numeric target `NULL` | Existing IMMEDIATE mode and no periodic schedule; reject query shapes/options that cannot use IMMEDIATE safely. |
| `manual` | mode `MANUAL`, numeric target `NULL` | Scheduler hard-skips the table; authorized manual refresh remains available. |

When a target is supplied in the same call as an explicit non-default schedule,
reject the ambiguous request with a HINT to choose one control. ALTER likewise
rejects simultaneous schedule and target changes. On ALTER,
`target_freshness => ''` clears the declaration but intentionally leaves the
last derived concrete schedule/mode unchanged; the HINT/docs explain that the
caller may alter those separately.

The MANUAL check belongs at the start of scheduler eligibility and must not
depend on optional tier scheduling being enabled. `set_stream_table_sla`
becomes a compatibility wrapper around the same declaration/one-time
translation helper. Disable or retire continuous SLA-tier retuning for rows
using the v0.86 declaration, because automatic retuning belongs to v0.90.

Emit, but do not reject for, obvious infeasibility:

- the target is below the effective scheduler/minimum cadence;
- compatible observed refresh p95/average or the just-completed initial
  refresh already exceeds the target; or
- the query is FULL-only and its compatible observed cost exceeds the target.

`manual` is not evaluated as a time SLA. `on_commit` is validated against
IMMEDIATE eligibility instead. Explain and the statistics view report the
declaration, not a claim that v0.86 continuously enforces it.

### 3.8 Compatibility boundaries and non-goals

This release does not:

- add `CREATE STREAM TABLE ... WITH (...)` grammar;
- build a feedback controller, adaptive scheduler, or SLA compliance status;
- add CDC timing instrumentation solely for diagnostics;
- add a dependency for JSON, percentile, interval, cron, or plan parsing that
  the repository/PostgreSQL already supplies;
- execute `EXPLAIN ANALYZE` against a user's defining query during preview;
- delete refresh history when resetting statistics;
- remove the existing diagnostic functions or `pg_stat_stream_tables`; or
- promise commit-to-visible lag semantics before the v0.90 frontier controller.

## 4. SQL and Error Contract

### 4.1 SQL surface

Finalize exact argument types against the existing name resolver during
implementation, while keeping ordinary name calls unambiguous:

```sql
pgtrickle.explain(stream_table text) RETURNS text
pgtrickle.explain_json(stream_table text) RETURNS jsonb

pgtrickle.preview_stream_table(
    query text,
    schedule text DEFAULT 'calculated',
    refresh_mode text DEFAULT 'AUTO',
    target_freshness text DEFAULT NULL
) RETURNS TABLE(property text, value text)

pgtrickle.stat_reset(pgt_id bigint) RETURNS void
pgtrickle.stat_reset_all() RETURNS void
```

Create/alter retain their existing result contracts and add only the optional
`target_freshness text` parameter. Preview returns `warnings` as a JSON array
inside its existing property/value shape plus `warning_count`; a future typed
preview API is not needed for v0.86.

### 4.2 Errors

Add contextual `PgTrickleError` variants in `src/error.rs` for:

- invalid or ambiguous freshness targets;
- incompatible `on_commit` targets;
- simultaneous schedule/target controls;
- stream table not found/ambiguous under the existing resolver; and
- EXPLAIN diagnostic planning failure when no safe fallback exists.

Unknown evidence is normally a nullable diagnostic value, not an error.
Warning conditions remain warnings. SQL-reachable Rust must not `unwrap()` or
panic; pgrx conversion remains at the API boundary.

The implementation should prefer these existing modules; add a focused module
only where hook safety or diagnostics would otherwise make an existing file
less coherent.

| Area | Expected files | Planned change |
|---|---|---|

## 7. Upgrade and Compatibility Plan

Add `sql/pg_trickle--0.85.0--0.86.0.sql` and the corresponding version/archive
metadata. The migration must:

1. add `requested_refresh_mode` and backfill it from concrete mode;
2. add `target_freshness_mode`, preserving existing
   `freshness_deadline_ms` values as interval declarations where appropriate;
3. add `refresh_reason` if absent, add `refresh_reason_detail`, and repair fresh
   bootstrap parity;
4. add pending-rebuild reason fields only if the caller audit proves delayed
   rebuilds otherwise lose cause;
5. add reset-aware cumulative counter and percentile columns;
6. add indexes that support batched post-reset history aggregation and bounded
   last-state reads;
7. create/replace the statistics view and affected history/catalog functions;
8. replace ambiguous defaulted preview/create/alter signatures safely;
9. apply grants/revokes through the established API policy; and
10. leave pre-v0.86 history reasons nullable and documented as legacy unknown.

Migration SQL must use `IF [NOT] EXISTS` only where repository upgrade policy
requires rerun safety; constraints and backfills still need explicit validation.
Fresh install, direct upgrade from v0.85, and the supported chained upgrade
path must produce equivalent catalogs, function signatures, views, defaults,
and privileges.

Compatibility decisions:

- Existing create/alter calls without `target_freshness` behave unchanged.
- Existing one-argument preview calls behave unchanged apart from richer
  warning output.
- Existing `set_stream_table_sla` calls retain a supported compatibility path.
- Existing monitoring views/functions remain; docs direct new integrations to
  `pg_stat_pgtrickle`.
- Existing history rows are not rewritten with guessed reasons.
- EXPLAIN output is byte-for-byte unaffected while the new GUC is off, aside
  from any unavoidable prior-hook behavior that is always chained.

## 10. Risks and Mitigations

| Risk | Mitigation |
|---|---|
| A fallback bypasses the reason contract | Make FULL execution require a typed reason; audit all callers; add a CI/static source guard and representative E2E coverage. |
| New diagnostics report false precision | Carry evidence/sample metadata, preserve nulls, and never equate planner cost units with elapsed time. |
| Statistics scraping becomes history-bound | Maintain counters/percentiles in existing bounded summaries; benchmark against fixed table count with growing history. |
| Reset races with refresh completion | Use the established catalog lock order and one terminal upsert transaction; test concurrent reset/finalize. |
| EXPLAIN hook breaks other extensions or formats | Chain prior hooks, use native structured properties, default off, and test text/structured formats plus pooled reuse. |
| Hook cache survives an error | Scope state per plan and install explicit normal/error cleanup; add an error-followed-by-success test. |
| AUTO reporting is wrong for upgraded rows | Store requested mode going forward and backfill only known concrete mode; never infer historic AUTO. |
| Target freshness silently becomes a controller | Perform one-time translation, hard-code the v0.90 boundary in docs/tests, and bypass existing continuous SLA retuning for declared targets. |
| MANUAL tables refresh in the background | Check the declaration before every scheduler eligibility path, independent of tier GUCs. |
| Warning logic drifts between create and preview | Return one `CreationAnalysis` and test equality of stable warning codes. |
| Write-overhead warning is unavailable on default PostgreSQL stats settings | Report unknown without warning; document how to enable compatible function statistics and gather samples. |
| Fresh and upgraded schemas diverge again | Add schema/API/ACL parity checks to the upgrade suite before feature wiring lands. |

## 11. Recommended Pull-Request Sequence

Keep each PR deployable and its migration edits synchronized with bootstrap SQL:

1. **Catalog contracts and typed FULL reasons** — requested mode, reason/detail
   parity, typed execution result, exhaustive caller migration, history output.
2. **Shared analysis and warnings** — create/preview unification, six warnings,
   HINTs, warning GUCs.
3. **Explain functions** — shared snapshot, estimators, schedule helper, text and
   JSON renderers.
4. **Statistics and reset** — counters, reset-aware duration summaries, view,
   authorization.
5. **Target freshness** — declaration, one-time translation, special values,
   infeasibility warnings, scheduler boundary.
6. **EXPLAIN annotations** — hook registration/chaining, bounded plan cache,
   format and safety tests.
7. **Upgrade, documentation, and release verification** — final migration/API
   parity, generated artifacts, guide, performance gates, full CI.

PRs 2–6 may be rebased/stacked after PR 1 defines the durable reason and
catalog contracts. Avoid splitting fresh bootstrap and upgrade migration for
the same schema change across different PRs.
