# v0.90.0 Implementation Plan: Freshness Controller and Self-Tuning

> **Status:** Implemented for the v0.90.0 advisory scope; authority-specific rollout remains gated
> **Target:** v0.90.0
> **Baseline:** v0.89.0
> **Roadmap:** [roadmap/v0.90.0.md](../roadmap/v0.90.0.md)
> **Last updated:** 2026-08-30

> **Roadmap change:** v0.90.0 now requires authoritative freshness measurement
> and advisory controller decisions. Each automatic decision class must earn
> authority separately. Treat the authority-specific implementation detail
> below as research input until this plan is revised to match that rollout.

## 1. Outcome

v0.90.0 makes an interval `target_freshness` the primary control for deferred
stream tables. The scheduler uses exact commit-to-visible observations,
measured refresh costs, pending change rate, memory pressure, and instance load
to decide when and how to refresh. Users can still override a decision, but
`pgtrickle.explain()` identifies every override and its effect.

The work lands in this order:

1. Repair and prove the commit-to-visible evidence path.
2. Freeze the controller, status, override, and worker contracts as pure types.
3. Add bounded controller state and freshness summaries.
4. Make target freshness drive due time, refresh mode, batch size, and queue
   priority.
5. Add cluster-wide adaptive worker sizing through the existing worker-token
   authority.
6. Add continuous infeasibility detection, SQL reporting, health checks,
   alerts, Prometheus metrics, and OpenTelemetry metrics.
7. Audit and reduce the configuration surface.
8. Close upgrade, soak, performance, documentation, and release gates.

The controller extends the scheduler and refresh finalizer delivered by
v0.85 through v0.89. It does not add another scheduler, worker pool, refresh
transaction, or frontier finalizer.

### 1.1 Release invariants

- A committed source change is never discarded, skipped permanently, or moved
  past the durable frontier to improve an SLA number.
- The target table, downstream CDC rows, private operator state, frontier,
  refresh history, and controller evidence commit or roll back under the
  transaction contracts established by earlier releases.
- Only exact, settled commit-to-visible samples count toward p50, p95, p99,
  breach, or infeasibility status. Refresh duration is not relabeled as data
  freshness.
- An interval target requires PostgreSQL commit timestamp tracking and a source
  path that preserves commit provenance. Missing evidence disables SLA claims
  and produces an actionable health error.
- `on_commit` remains IMMEDIATE maintenance. `manual` remains outside scheduler
  dispatch. Neither special value enters the deferred controller.
- A table without `target_freshness` keeps the v0.89 scheduling and refresh
  behavior.
- A targeted table uses measured cost only after compatible evidence exists.
  Missing or stale evidence keeps the current safe strategy and records a
  bootstrap reason.
- The controller chooses DIFFERENTIAL or FULL before target, private-state, or
  frontier mutation. It never retries a partly executed interval through a
  different strategy.
- Explicit overrides win over controller preferences, but not over durability,
  memory, worker, deadline, or semantic safety limits.
- Derived values live in controller state. The controller does not overwrite
  the user's target or turn derived values into apparent user configuration.
- One stream table still has at most one refresh transaction in flight.
  Adaptive concurrency changes how many independent execution units may run,
  not the serialization boundary of one stream table.
- Every worker admission passes through the v0.85 authoritative reservation
  table and effective cluster limit. Shrinking capacity never kills a running
  refresh.
- A tuning change needs three consecutive observations in the same direction.
  Correctness actions, a due deadline, and the existing hard overload guard do
  not wait for tuning hysteresis.
- Scheduler work is set-based and bounded. The controller does not scan
  unbounded history or open one SPI query per stream table on every tick.
- Controller restart loses only pending hysteresis streaks. It reconstructs
  due time from durable frontiers and pending commit provenance, so restart
  cannot lose or postpone committed changes indefinitely.
- Diagnostics use one typed snapshot for text and JSON. Missing inputs remain
  missing rather than becoming zeros or guessed milliseconds.
- No new third-party dependency is required.
- The release does not introduce either retired name
  `pg_trickle.max_workers` or `pg_trickle.max_parallel_refresh_workers`.

### 1.2 Roadmap ambiguities resolved

| Roadmap wording | v0.90 contract |
|---|---|
| "p95 age of the data visible" | One sample is the commit time of the oldest source transaction consumed by a successful frontier interval to the commit time that made that interval visible. p95 is computed from settled samples, not from `last_refresh_at`. |
| Metric "shipped in v0.81.0" | The current v0.86 tree exposes a duration fallback and does not persist enough provenance for the promised metric. Exact provenance and settlement are a blocking v0.90 work package. |
| `track_commit_timestamp` is unavailable | New interval targets are rejected with a restart hint. Existing targets upgraded into this state keep their legacy schedule but report `EVIDENCE_UNAVAILABLE`; the controller does not claim enforcement. |
| Multiple source transactions in one refresh | Use the oldest commit time in the protected frontier interval. This gives a conservative age for that refresh and includes queueing and execution time. |
| Stream-table chains | Propagate the oldest base-source commit time through stream-table change buffers. A downstream SLA measures end-to-end age, not only the delay after its immediate parent refreshed. |
| Foreign or polling sources | An interval target is accepted only when every dependency supplies exact commit provenance. A polling source without such provenance remains usable with ordinary schedules. |
| "when to refresh" | A targeted table is due when the oldest pending change age plus predicted queue delay and predicted refresh cost reaches the target. No pending changes means no time-driven no-op refresh. |
| "DIFFERENTIAL vs FULL" | Explicit FULL or DIFFERENTIAL is a mode override. AUTO lets the controller compare compatible measured p95 costs. Static delta-ratio logic is bootstrap evidence only. |
| "batch size" | Reuse the v0.87 pipeline and `MemoryBudget`. The controller changes its effective row batch, not transaction or frontier semantics. |
| "concurrency per stream table" | A per-table decision contributes urgency and worker demand. The cluster controller sets the number of independent refresh workers. It never runs concurrent refreshes for the same table. |
| "priority" | Use predicted deadline slack inside the existing dependency-ready, fair queue. Execution-unit readiness and consistency constraints remain mandatory. An infeasible target cannot monopolize the queue. |
| "whether to defer" | Reuse the v0.87 overload decision. Defer only while enough positive slack remains. Record the load reason and reconsider on the next tick or wake-up. |
| Three consecutive measurements | Apply hysteresis independently to mode, interval direction, batch direction, feasibility, and worker direction. Deadline slack and queue ordering are live inputs, not persistent tuning changes. |
| Numeric tuning changes | After three matching directions, change one bounded step. Mode changes use the same candidate for three compatible samples. This prevents large jumps and oscillation. |
| Explicit override | Record per-table provenance for schedule and refresh mode. Treat a non-default global batch or concurrency GUC as an advanced override. Explain reports the requested and safety-capped effective values. |
| Target changes | Keep compatible cost evidence, recompute status against the new target, and reset breach, infeasibility, and pending hysteresis streaks. Do not delete refresh history. |
| p50, p95, and p99 window | Use the latest 128 settled samples within the existing `pg_trickle.sla_window_hours` window. Report `INSUFFICIENT_DATA` until 20 samples exist. The cap is internal, not another GUC. |
| `sla_status` | Stable values are `MEETING`, `AT_RISK`, `BREACHING`, `INFEASIBLE`, `INSUFFICIENT_DATA`, and `EVIDENCE_UNAVAILABLE`. Tables without an interval target return `NOT_APPLICABLE`. |
| Sustained breach | After each newly settled sample, recompute the bounded p95. Enter `BREACHING` after three consecutive new-sample evaluations whose p95 exceeds the target. Recover after three whose p95 meets it. Scheduler ticks with no new sample do not advance either streak. |
| SLA at risk | A feasible target is at risk when predicted completion consumes at least 80 percent of the target or has non-positive slack. This signal affects priority and worker demand before a recorded breach. |
| Infeasible target | Require at least five compatible cost samples. If the fastest observed eligible refresh still exceeds the target for three new observations, mark the target infeasible. Continue at a sustainable fair cadence, but stop using that table to demand more workers. |
| CPU above 70 percent conflicts with SLA pressure | CPU protection wins for that worker decision. Three consecutive high-CPU samples reduce the admission target by one. SLA pressure can grow the target only after CPU pressure clears. |
| Adaptive worker "pool" | Adjust the cluster admission target used by dynamic workers. Do not add a second persistent-worker implementation. |
| OTel metrics | Add a bounded OTLP metrics batch to the existing endpoint. Span attributes alone do not satisfy the metrics requirement. |
| Internal knobs are "hidden" | Remove a GUC only after proving that no supported workflow needs it. Otherwise classify it as an advanced override and remove it from the normal setup path. Do not add a new configuration-registry framework. |

### 1.3 Non-goals

- A new SQL grammar for stream tables.
- A controller for tables without `target_freshness`.
- Changes to IMMEDIATE or manual refresh semantics.
- Multiple simultaneous refresh transactions for one stream table.
- A replacement for the v0.87 pipeline, memory budget, load sampler,
  backpressure policy, fair queue, or deadline handling.
- A replacement for the v0.88 and v0.89 cost planner or fallback paths.
- A general control-theory framework, configurable controller gains, or a PID
  controller.
- User-defined controller plugins.
- Automatically changing the user's declared target.
- Treating a missed target as permission to drop data, skip frontier ranges,
  use unlogged correctness state, or bypass worker limits.
- Host CPU guessing on platforms where v0.87 cannot provide a valid CPU
  sample. Missing CPU evidence is reported and the CPU resize signal is idle.
- A new alert transport. Use health rows, logs, existing NOTIFY alerts,
  Prometheus, and OpenTelemetry.
- Removing a control whose replacement remains advisory. Unproven replacements
  keep their override through the v0.94 feature freeze.

## 3. Target flow

```text
base-table transaction
    -> CDC row stores source transaction ID
    -> source transaction commits
    -> PostgreSQL exposes its commit timestamp

stream-table transaction
    -> downstream CDC row propagates oldest source commit time
    -> refresh transaction stores its own transaction ID in history
    -> transaction commits target, state, frontier, CDC, and history
    -> next bounded settlement pass resolves exact visibility commit time
    -> one exact commit-to-visible sample becomes eligible

scheduler tick
    -> batch-load active metadata, summaries, pending-source evidence, and load
    -> build pure ControllerInputs per targeted stream table
    -> propose due time, mode, batch, urgency, deferral, and feasibility
    -> apply three-observation hysteresis to tuning changes
    -> aggregate execution-unit urgency and cluster worker demand
    -> existing fair dispatcher reserves through WorkerCapacity
    -> existing refresh executor and finalizer run once

diagnostics or metrics request
    -> read the bounded summary and last applied decision
    -> build one typed explanation snapshot
    -> render SQL, text, JSON, Prometheus, or OTLP output
```

No controller step advances a frontier. Only a successful refresh finalizer
does that.

## 4. Exact freshness evidence

### 4.1 Source transaction provenance

Add commit provenance to every durable CDC shape used by a deferred targeted
table.

Base-table change buffers add a nullable `source_xid xid` control column. New
row, statement, and TRUNCATE trigger bodies write the top-level current
transaction ID. The WAL decoder writes the transaction ID supplied by logical
decoding. Sentinel rows keep the column NULL.

Stream-table change buffers add both nullable fields:

- `source_xid xid`, for compatibility with direct locally generated changes;
- `source_commit_at timestamptz`, for provenance propagated from an upstream
  refresh.

The refresh input collector resolves base `source_xid` values through
`pg_xact_commit_timestamp()` after the source transaction is visible. It takes
the minimum of those timestamps and any propagated `source_commit_at` values in
the protected frontier interval. That minimum becomes the interval's
`source_commit_at`.

The downstream CDC writer copies the same `source_commit_at` into every output
change row produced by that interval. A chain therefore retains the oldest
base-source commit. Fused and atomic execution units take the minimum provenance
across their members before writing downstream changes.

Requirements:

- Query transaction IDs in one set-based lookup over distinct IDs, never once
  per change row.
- Bound each lookup by the old and proposed frontier that the refresh already
  protects.
- Treat a missing commit timestamp as unavailable evidence. Do not substitute
  trigger time, WAL insert time, scheduler wake time, or refresh start time.
- Include INSERT, UPDATE, DELETE, TRUNCATE, trigger CDC, WAL CDC, and
  stream-table CDC.
- Preserve provenance through CDC compaction. The compacted first and last row
  for a key must retain the oldest contributing commit time.
- Add the new control columns to reserved-name handling, buffer validation,
  schema rebuilds, partition creation, dump and restore validation, and column
  pruning.
- Measure the extra write-path bytes and trigger CPU in the v0.87 overhead
  harness. Exactness is mandatory, but the implementation must still use one
  bulk expression per statement trigger.

An interval target is not supported for a dependency whose commit provenance
cannot be recovered. This includes polling sources unless an earlier release
has added an exact source-commit contract. Creation and ALTER return a typed
error naming the source and suggest an ordinary schedule. Upgraded tables keep
refreshing under their legacy schedule and report evidence unavailable.

### 4.2 Exact visibility settlement

Add these fields to `pgtrickle.pgt_refresh_history` if v0.89 does not already
provide equivalent typed fields:

| Column | Type | Meaning |
|---|---|---|
| `duration_ms` | `double precision` | Monotonic elapsed execution duration persisted by the finalizer. |
| `source_commit_at` | `timestamptz` | Oldest exact source commit consumed by this frontier interval. |
| `visibility_xid` | `xid` | Transaction that commits the refreshed target and history row. |
| `visible_at` | `timestamptz` | Exact commit timestamp resolved after `visibility_xid` commits. |
| `commit_to_visible_ms` | `double precision` | `visible_at - source_commit_at` in milliseconds. |
| `plan_identity` | `bigint` | Defining-query and strategy identity used to reject incompatible cost samples. |

Use `std::time::Instant` for `duration_ms`. Keep `start_time` and `end_time` for
human-readable history, but write `clock_timestamp()` rather than relying on
transaction-stable `now()` for elapsed wall time.

The refresh finalizer writes `source_commit_at` and its current
`visibility_xid` in the same transaction as the target and frontier. The row
cannot know its own commit time before commit. A bounded settlement pass on the
next scheduler tick resolves `visible_at` with
`pg_xact_commit_timestamp(visibility_xid)` and calculates
`commit_to_visible_ms`.

Settlement rules:

1. Select at most the existing scheduler maintenance batch size of completed,
   unsettled rows.
2. Resolve all transaction IDs in one query.
3. Update only rows whose commit timestamp is available.
4. Leave an unavailable value NULL and record the evidence reason in the
   controller summary. Never write a duration fallback into the field.
5. Make the update idempotent. A crash before or after settlement is harmless.
6. Exclude failed, rolled-back, no-data, manual-rebuild-without-provenance, and
   unsettled rows from freshness percentiles.
7. Run settlement outside a refresh's SPI block and before the controller
   summary refresh for that tick.

`pg_trickle.commit_timestamp_tracking` no longer controls correctness for a
targeted table. The controller automatically uses exact tracking when an
interval target exists. WP8 decides whether to remove the old GUC or keep it as
an advanced control for untargeted diagnostics, but it cannot disable evidence
for an active interval target.

### 4.3 PostgreSQL setting gate

Before accepting a new interval target, check
`current_setting('track_commit_timestamp')` through one typed SPI query.

- If it is `on`, validate source provenance and continue.
- If it is `off`, return `FreshnessEvidenceUnavailable`. The DETAIL names the
  PostgreSQL setting. The HINT tells the operator to set
  `track_commit_timestamp = on` and restart PostgreSQL.
- `on_commit` and `manual` do not require this setting.
- Do not change a postmaster setting from extension code.

On upgrade, do not abort `ALTER EXTENSION` because the setting is off. Mark the
controller state `EVIDENCE_UNAVAILABLE`, keep the existing schedule active, and
surface the required restart in `health_check()`. After restart, the scheduler
detects the setting, begins collecting exact samples, and activates the
controller without a table rebuild.

### 4.4 Bounded freshness summary

Create one focused table, `pgtrickle.pgt_freshness_controller_state`, keyed by
`pgt_id`. Do not add freshness fields to every shared-memory slot or update the
core stream-table row on every tick.

The table stores:

- `controller_version` and `plan_identity`;
- schedule and mode override provenance;
- `last_settled_refresh_id` and exact sample count;
- p50, p95, and p99 freshness in milliseconds;
- the last exact freshness sample;
- `sla_status`, breach streak, recovery streak, and `breach_started_at`;
- infeasibility streak, recovery streak, start time, reason, and minimum
  compatible observed cost;
- the last applied interval, mode, and batch size;
- a bounded versioned JSON object containing the last input snapshot and
  decision;
- `last_decision_at` and `updated_at`.

Use typed columns for values used by scheduling, SQL views, or indexes. The JSON
object is diagnostic evidence only. Validate its controller version before
rendering it. An unknown version yields an unavailable diagnostic and a
conservative controller reset.

Refresh the summary only when one of these events occurs:

- a new history row settles;
- the target, query, or override changes;
- breach or infeasibility status changes; or
- an applied controller decision changes.

Percentiles use at most the latest 128 settled samples inside
`pg_trickle.sla_window_hours`. Calculate summaries for all changed tables in
one set-based query. Do not issue one history scan per table.

The table is derived operational state. Physical backup preserves it. Logical
dump and restore may rebuild it from retained history and current metadata, so
do not register it as user configuration with `pg_extension_config_dump`.

## 5. Pure per-table controller

### 5.1 Types and ownership

Add `src/scheduler/controller.rs` as the one new Rust module. Keep SPI loading
in the scheduler and catalog layers. The controller module owns pure values and
decisions:

```text
FreshnessDistribution = { samples, p50_ms, p95_ms, p99_ms, last_ms }
ModeCostEvidence = { mode, samples, min_ms, p50_ms, p95_ms, updated_at }
PendingEvidence = { rows, oldest_commit_age_ms, inflow_rows_per_ms }
LoadEvidence = { cpu_percent, queue_depth, lock_waits, overloaded }
OverrideSet = { interval, mode, batch_size, concurrency_ceiling }

ControllerInputs = {
    target_ms,
    freshness,
    differential_cost,
    full_cost,
    pending,
    row_width_bytes,
    memory_budget,
    queue_delay_ms,
    load,
    semantic_modes,
    overrides,
    current_decision,
}

ControllerDecision = {
    due,
    next_due_in_ms,
    action,
    batch_size,
    deadline_slack_ms,
    priority_class,
    defer,
    feasibility,
    worker_demand,
    reason_code,
    reason_detail,
}
```

Use finite integer milliseconds and checked arithmetic at the pure boundary.
Reject or mark unavailable negative counts, NaN values, timestamps from the
future beyond clock-skew tolerance, stale cost generations, and impossible
override values.

`ControllerDecision` is a proposal. A small in-memory `ControllerHysteresis`
map in the database scheduler compares proposals and emits an applied decision.
The map is keyed by `pgt_id`, pruned with the existing catalog snapshot, and
cleared when the target or plan identity changes.

### 5.2 Input collection

Build one immutable controller snapshot near the start of each scheduler tick.
Keep SPI blocks short:

1. Batch-load active stream metadata and controller summaries.
2. Reuse the v0.87 source fanout inventory to query each unique change buffer
   once for pending rows and oldest provenance.
3. Fan source evidence out to dependent stream tables in memory.
4. Reuse the v0.88 and v0.89 cost summaries. Reject a sample whose plan
   identity does not match the current defining query and strategy version.
5. Read the v0.87 load snapshot once per database tick.
6. Read worker capacity and queue state once from shared memory.
7. Read global override provenance once from `pg_settings`, not once per table.

Use an exponentially weighted inflow rate updated from settled frontier
intervals. Seed it from `delta_row_count` divided by the exact interval between
source commits. A missing rate stays missing. The controller can dispatch
already pending work without inventing a rate.

Cache PostgreSQL row-width statistics by relation and statistics generation.
Prefer v0.87 observed pipeline bytes per row. Fall back to `pg_stats.avg_width`
without sampling user rows. If both are unavailable, use the v0.87 conservative
memory estimate and report its source.

### 5.3 Override provenance and precedence

For targeted tables, distinguish user configuration from derived state.

- A non-`calculated` schedule supplied at create or ALTER marks an interval
  override.
- Explicit FULL or DIFFERENTIAL marks a mode override. AUTO leaves mode under
  controller ownership.
- Reapplying AUTO clears a prior mode override.
- Reapplying `schedule => 'calculated'` clears a prior interval override.
- A non-default pipeline batch GUC is a global batch override. Detect it from
  `pg_settings.source` and keep the requested value in diagnostics.
- A non-default concurrency cap remains a hard advanced ceiling. It does not
  grant capacity beyond PostgreSQL or pg_trickle worker limits.
- If v0.87 added typed per-table batch or concurrency options, store their
  provenance beside schedule and mode rather than adding a second mechanism.

Precedence is fixed:

1. semantic, durability, memory, deadline, and hard worker limits;
2. explicit per-table override;
3. explicit global advanced override or ceiling;
4. controller decision;
5. conservative bootstrap default.

When safety caps an override, keep both values. Explain reports
`requested_override`, `effective_value`, and the cap reason. Do not silently
pretend that the controller selected the capped value.

For interval targets, stop writing derived schedules to
`pgt_stream_tables.schedule`. The controller state's effective interval is the
runtime value. If the user clears a target, preserve the v0.86 compatibility
contract by materializing the last effective interval as an ordinary schedule.

### 5.4 Due time and interval

For a pending change, calculate:

```text
predicted_completion_age = oldest_pending_age
                         + predicted_queue_delay
                         + predicted_refresh_p95

deadline_slack = target_freshness - predicted_completion_age
```

The table is due when `deadline_slack` is no greater than the scheduler wake
and dispatch guard from v0.87. If slack is positive, expose it as the next due
delay and let LISTEN or the normal latch wake recompute it. If no changes are
pending, the table is not due merely because wall-clock time passed.

If rows are pending but their oldest commit provenance is unavailable, dispatch
them conservatively without delay and mark the evidence unavailable. Never
defer an unknown-age change or let it block newer exact rows. The completed
refresh remains correct but does not create a freshness sample.

Use pending rows and inflow rate to estimate the delta at the proposed start.
Evaluate the estimate and cost at most twice to account for new rows arriving
during the wait. A fixed two-pass calculation is bounded and avoids a general
solver.

An interval override routes due-time calculation through the existing shared
schedule helper. The target still evaluates status and feasibility, but explain
marks timing as overridden.

### 5.5 Measured mode choice

Build candidates only for semantically valid modes. FULL is always the result
oracle. DIFFERENTIAL is a candidate only when the v0.83, v0.88, and v0.89
admission contracts allow it for the current plan and state.

For each candidate, estimate p95 completion cost at the predicted delta size:

- use compatible observed p95 and the landed cost model when enough samples
  exist;
- use current pending rows and the measured inflow rate;
- include output amplification and operator-state costs from v0.88 and v0.89;
- keep planner cost units separate from elapsed milliseconds.

Selection rules:

1. A mode override selects its mode unless correctness requires a documented
   fallback.
2. If only one mode has compatible evidence, retain the current valid mode.
3. If neither mode has evidence, use the v0.89 bootstrap decision and label it
   `BOOTSTRAP_COST_EVIDENCE`.
4. If both have evidence, choose the lower predicted p95 cost.
5. Require the candidate to remain preferred for three compatible samples
   before switching.
6. Apply the landed cost-model safety margin when costs are close.
7. Record every FULL choice through the existing typed reason contract. Do not
   create a controller-only FULL executor.

The controller never runs an otherwise unnecessary FULL refresh solely to
collect a sample. Mandatory FULL work, explicit FULL runs, reinitialization,
and existing safe fallbacks populate FULL evidence naturally.

### 5.6 Adaptive pipeline batch size

Reuse the v0.87 pipeline telemetry and `MemoryBudget`. The controller asks the
budget for the bytes available to one refresh after accounting for the current
worker target and other bounded components.

Calculate a safe row count from:

- observed or PostgreSQL-estimated bytes per row;
- operator amplification and private-state overhead;
- the per-refresh memory share;
- the v0.87 minimum and maximum batch bounds; and
- observed per-batch overhead and spill evidence.

Round the result down to an existing supported batch step. Change at most one
step after three consecutive grow or shrink proposals. Spill or a hard memory
cap can shrink immediately because it is a safety event, not tuning.

An explicit batch override remains exact only while it fits the hard memory
budget. If it does not fit, cap it, emit a health warning, and report both
values. Never exceed the memory budget to honor an override.

### 5.7 Priority, deferral, and execution units

Convert each targeted table's deadline slack into the priority input consumed
by the v0.87 fair queue:

- overdue feasible target;
- at-risk feasible target;
- meeting target;
- untargeted scheduled work;
- infeasible target at its sustainable cadence.

Within a class, smaller slack runs first. Retain the v0.87 aging rule so a
continuous one-second workload cannot starve an hour target or an untargeted
maintenance task.

Aggregate a multi-table execution unit before sorting:

- require the existing dependency and consistency readiness checks;
- use the minimum member slack;
- use the most urgent feasible member class;
- execute the complete atomic, repeatable-read, fused, or cyclic unit through
  its existing path; and
- assign the resulting visibility sample to each member using the provenance
  that its frontier consumed.

When v0.87 reports overload, defer only a unit whose slack remains positive
after the next bounded retry delay. Do not create a refresh-history row for
every deferred tick. Persist a new last decision only when the reason or
effective decision changes.

### 5.8 Hysteresis, bootstrap, and restart

Track pending changes independently:

| Dimension | Consistent observation | Applied change |
|---|---|---|
| Mode | Same candidate mode with compatible evidence | Switch after three samples. |
| Interval | Same increase or decrease direction | Move one bounded interval step after three ticks with new evidence. |
| Batch | Same increase or decrease direction | Move one supported batch step after three ticks. |
| Breach | A new exact sample makes the recomputed p95 exceed target | Enter breach after three new-sample evaluations. |
| Breach recovery | A new exact sample leaves the recomputed p95 at or below target | Recover after three new-sample evaluations. |
| Infeasible | New compatible minimum remains above target | Enter infeasible after three observations and at least five total samples. |
| Feasibility recovery | New compatible cost can meet target | Recover after three observations. |

The following actions bypass tuning hysteresis:

- a table becomes due;
- semantic validation requires FULL or reinitialization;
- a hard memory or worker bound tightens;
- drain, pause, shutdown, cancellation, or deadline handling runs; or
- the v0.87 hard overload guard prevents new admission.

A streak advances only when its relevant evidence token changes. Re-reading the
same cost summary, pipeline sample, or freshness sample on later scheduler
ticks does not create three measurements.

On scheduler restart, load the last applied interval, mode, and batch from the
controller table. Reset only pending streaks. Recompute pending age and due time
from durable buffers. Start a table with no applied state from conservative
v0.89 behavior and label the decision as bootstrap.

## 6. Cluster-wide adaptive workers

### 6.1 One adaptive admission target

Add the roadmap GUCs in `src/config/scheduler.rs`:

| GUC | Default | Valid range | Context |
|---|---:|---:|---|
| `pg_trickle.adaptive_workers` | `true` | boolean | SIGHUP |
| `pg_trickle.adaptive_workers_min` | `1` | `1` to the compile-time worker-slot limit | SIGHUP |
| `pg_trickle.adaptive_workers_max` | `8` | `1` to the compile-time worker-slot limit | SIGHUP |

Use a cluster configuration context so database-local settings cannot create
conflicting floor and ceiling values. Validate `min <= max` after SIGHUP. If
the pair is invalid, retain the last valid pair, report a health error, and do
not expand capacity.

Add one small `AdaptiveWorkerState` under a `PgLwLock` in `src/shmem.rs`. It
contains the current admission target, the last adjustment time, the active
signal, and its consecutive count. Reuse the database-scoped scheduler slots
from v0.85 to publish bounded demand samples:

- database OID and sample timestamp;
- ready queue depth;
- live and reserved worker counts;
- feasible at-risk SLA count;
- whether all local workers were idle;
- CPU sample and validity; and
- v0.87 overload state.

Do not add a new worker registry. One scheduler per adjustment interval takes
the adaptive-state lock, discards stale database samples, aggregates the live
samples, and advances the pure resize state machine. The lock covers only the
fixed-size snapshot and state transition. It does not cover SPI, worker spawn,
or refresh execution.

When adaptive workers are enabled, extend the existing capacity calculation:

```text
effective worker limit = min(
    adaptive admission target,
    adaptive_workers_max,
    v0.85 pg_trickle hard cluster limit,
    max_parallel_workers when configured,
    available max_worker_processes capacity
)
```

The floor is `min(adaptive_workers_min, effective hard limit)`. A hard limit of
zero still disables dynamic workers and leaves the existing inline path
available. The adaptive target does not replace per-database quotas or
`max_concurrent_refreshes`; those remain safety and fairness ceilings.

If `adaptive_workers = false`, use the existing v0.89 static capacity exactly.
The new state remains observable but does not affect admission.

### 6.2 Resize state machine

Use this signal order after three consecutive valid aggregate samples:

1. If CPU utilization is above 70 percent, reduce the target by one.
2. Otherwise, if at least one feasible SLA is at risk, increase the target by
   one.
3. Otherwise, if ready queue depth is greater than twice the current target,
   increase the target by one.
4. Otherwise, if every active database reports no queued, reserved, or live
   work, reduce the target by one.
5. Otherwise, keep the target and reset the pending direction.

CPU protection wins over growth because the roadmap explicitly requires that
pg_trickle not starve OLTP. The existing v0.87 overload guard may stop new
admission before the three-sample resize completes.

Only valid CPU samples count toward the 70 percent rule. If CPU evidence is
unavailable, skip that signal and expose `cpu_source = unavailable`. Do not
derive a percentage from active backend count or load average.

An infeasible table does not contribute to at-risk worker demand. It remains
in the fair queue at its sustainable cadence. This prevents an impossible
target from pushing the pool to its ceiling forever.

After any resize, reset the signal count. Sustained pressure can therefore
change capacity by at most one worker every three adjustment intervals. This
is the cooldown and oscillation control. No extra GUC is added.

### 6.3 Reservation and shrink behavior

Pass the adaptive target into the same immutable `WorkerCapacity` snapshot
used for durable job enqueue and exact slot reservation.

- Reserve only if occupied slots are below the new effective limit.
- Recheck capacity under the existing reservation lock.
- If capacity changes between queue construction and reservation, cancel the
  durable queued job through the existing path and leave it eligible for a
  later tick.
- If the target shrinks below current occupancy, stop new admissions. Let live
  workers finish and release their exact slots.
- Never signal, cancel, or terminate a correct running refresh merely to make a
  gauge reach the new target.
- Reconciliation continues to reason about individual reserved and live slots.
  It must not assign occupancy from the adaptive target.
- Drain, pause, crash recovery, and database isolation continue to use the
  v0.85 state machines.

### 6.4 Worker diagnostics

Extend `worker_pool_status()` and the native metrics endpoint with:

- adaptive enabled;
- configured floor and ceiling;
- hard cluster ceiling;
- current adaptive target;
- reserved and live counts;
- aggregate queue depth;
- current resize signal and consecutive count;
- CPU value and source;
- feasible at-risk target count; and
- last resize timestamp.

Use one cluster row rather than one metric label per database where the value
is cluster-wide. Existing database labels remain on per-database queue and
worker gauges.

## 7. SLA status, infeasibility, and resource behavior

### 7.1 Status state machine

Only a newly settled exact sample can advance breach or recovery streaks.

| State | Entry | Exit |
|---|---|---|
| `INSUFFICIENT_DATA` | Fewer than 20 exact samples in the active window. | The twentieth compatible sample settles. |
| `MEETING` | p95 is at or below target and predicted completion uses less than 80 percent of target. | A risk, breach, infeasibility, or evidence failure occurs. |
| `AT_RISK` | Predicted completion uses at least 80 percent of target or slack is non-positive, but three violating exact samples have not settled. | Prediction recovers, three violations enter breach, or infeasibility is proved. |
| `BREACHING` | Three consecutive new-sample evaluations have p95 above target. | Three consecutive new-sample evaluations have p95 at or below target, or infeasibility is proved. |
| `INFEASIBLE` | The continuous feasibility proof in section 7.2 succeeds. | Three compatible observations show that an eligible mode can complete within target. |
| `EVIDENCE_UNAVAILABLE` | PostgreSQL tracking, source provenance, plan identity, or settlement evidence is unavailable. | The missing evidence is restored and a valid sample settles. |

`NOT_APPLICABLE` is a rendered value for tables without an interval target. It
is not stored as active controller state.

Keep `breach_started_at` at the first p95 evaluation in the streak that entered
`BREACHING`. Compute breach duration at read time. Recovery clears the timestamp
only after the third meeting evaluation, so a restart does not erase an active
breach.

### 7.2 Continuous infeasibility proof

Use measured elapsed refresh cost, not total freshness age, to distinguish an
intrinsically impossible query from temporary queue pressure.

For the current plan identity:

1. Determine eligible modes after semantic admission and explicit overrides.
2. Require at least five compatible successful cost samples for the selected
   mode set.
3. Take the minimum observed execution cost inside the bounded cost window.
4. If that minimum exceeds `target_freshness`, record one infeasible
   observation.
5. Enter `INFEASIBLE` after three newly completed observations still satisfy
   the proof.

Using the minimum is deliberate. If even the fastest compatible execution
misses the target, queueing or transient load cannot make the target feasible.
Do not use planner cost units, an average from an old query, or a duration from
an incompatible mode.

Build the diagnosis from evidence already produced by the v0.88 delta plan and
v0.89 operator strategy. Prefer a stable operator label and relation name such
as `orders to line_items join`. Do not run `EXPLAIN ANALYZE` in the scheduler or
store the defining SQL in an alert.

Differentiate these cases:

- query execution is intrinsically slower than the target;
- an explicit mode, interval, batch, or concurrency override prevents the
  controller from selecting a feasible decision;
- the current instance is overloaded, but the query has previously met the
  target; and
- evidence is missing.

Only the first two may enter `INFEASIBLE`. Temporary overload enters
`AT_RISK` or `BREACHING` with a load diagnosis.

### 7.3 Behavior while infeasible

An infeasible target must not create a losing resource race, but the table must
continue processing committed changes.

- Stop counting the table as adaptive worker growth demand.
- Do not shorten its effective interval below its measured sustainable service
  time.
- Keep at most one refresh queued or running for the table through existing
  execution-unit state.
- Place it behind feasible overdue work but keep v0.87 queue aging, so it still
  progresses.
- Keep using the cheapest eligible measured mode unless an override fixes the
  mode.
- Continue collecting samples so the table can recover automatically.
- Emit one transition alert and timestamp-based reminders through the existing
  alert throttle. Do not emit once per tick.
- Never switch to manual, suspend the table, clear its target, or discard its
  buffers automatically.

The health detail includes target, fastest compatible observed cost, current
mode or override, dominant cost, and a concrete hint. A query diagnosis may
recommend a coarser target or a narrower query. An override diagnosis names
the override to remove.

### 7.4 Query and target changes

A defining-query change creates a new `plan_identity`. It clears compatible
mode-cost selection, infeasibility, and pending hysteresis state. It does not
delete old history. The existing protected reinitialization path remains the
result oracle and first new cost sample.

A target-only change:

- retains compatible cost and exact freshness samples;
- recomputes current p95 status against the new target;
- clears breach and infeasibility streaks and timestamps;
- resets pending interval, mode, and batch hysteresis; and
- writes one new decision after the next controller evaluation.

Adding or clearing an override resets only the affected tuning dimension and
its diagnosis. A safety-relevant query or mode change still uses the existing
full-refresh and CDC lifecycle rules.

## 10. Transaction, concurrency, and lifecycle behavior

### 10.1 Refresh transaction order

For a targeted deferred refresh:

1. Load and validate the durable frontier and required change buffers.
2. Freeze the protected old and proposed frontier interval.
3. Resolve the oldest exact source commit provenance for that interval.
4. Choose the applied controller decision before mutation.
5. Execute the existing DIFFERENTIAL, FULL, or reinitialization path.
6. Apply pipeline batches under the v0.87 transaction contract.
7. Write downstream CDC with propagated source provenance.
8. Finalize private operator state, target rows, frontier, and typed refresh
   result through the existing finalizer.
9. Store monotonic duration, source commit time, and the current visibility
   transaction ID in history.
10. Commit once under the established durability contract.
11. Settle the visibility commit timestamp in a later bounded scheduler
    transaction.

If any step before commit fails, PostgreSQL rolls back target, state, frontier,
downstream CDC, and history together. The controller records no successful
freshness sample.

### 10.2 Concurrent configuration changes

Use the existing stream-table ownership and catalog locking rules.

- CREATE writes target metadata, override provenance, and initial controller
  state in the same transaction.
- ALTER locks and validates the table before changing target or overrides.
- The scheduler snapshots metadata once per tick and compares `updated_at` or
  the existing generation before applying a decision.
- If target, query, mode, or schedule changes after the snapshot, discard the
  stale proposal and retry next tick.
- DROP cascades controller state through the `pgt_id` foreign key and prunes
  in-memory hysteresis on catalog invalidation.
- Pause, drain, suspend, and ERROR status win over controller due time.

Do not hold an SPI connection while waiting on a worker, lock, latch, or
network export.

### 10.3 Crash and restart

Crash recovery requirements:

- Committed change buffers retain source transaction provenance.
- A committed refresh may have an unsettled history row. The next scheduler
  settles it idempotently.
- An aborted refresh leaves neither target changes nor a completed history row.
- The adaptive worker target restarts at the configured floor and grows under
  measured demand. Exact worker-slot reconciliation remains authoritative.
- The controller reloads its last applied decision but resets pending
  hysteresis streaks.
- An active breach or infeasible state survives through its catalog timestamp.
- Missing or corrupt controller state does not stop data maintenance. Rebuild
  it from metadata and bounded history, use conservative scheduling, and
  report the repair.

Add chaos points only through the existing test infrastructure. Do not ship a
new production GUC solely for controller tests.

### 10.4 Backup, restore, and replicas

- Physical backup and streaming replication preserve buffers, history,
  controller state, and exact commit timestamp data under PostgreSQL's normal
  durability rules.
- A standby does not run the scheduler until promotion, as today.
- After promotion, validate that required commit timestamp evidence is
  available before claiming SLA status.
- Logical dump preserves target and override configuration. Rebuild derived
  controller summaries after restore.
- Dynamic change-buffer definitions include the provenance columns in fresh
  objects and upgrade validation.
- If transaction commit timestamp history needed by unsettled rows is no
  longer available after restore, mark those samples unavailable. Do not
  synthesize them.

### 10.5 Security and information bounds

- Keep `pgtrickle.freshness()` and recommendation functions read-only and
  stable.
- Apply existing ownership checks to target and override changes.
- Parameterize catalog values. Quote dynamic relation identifiers through the
  existing helpers.
- Cast PostgreSQL `name` columns to `text` before reading them as Rust
  `String`.
- Keep diagnosis strings bounded and free of full defining SQL or row values.
- Escape Prometheus labels and OTLP attributes with the existing helpers.
- Give every new `unsafe` block a `// SAFETY:` comment. The pure controller
  should need no unsafe code.

## 14. Upgrade and compatibility

### 14.1 Migration order

`sql/pg_trickle--0.89.0--0.90.0.sql` performs these steps transactionally:

1. Add nullable history evidence columns and the focused controller-state
   table.
2. Add override provenance with conservative defaults.
3. Add nullable provenance columns to every buffer registered in
   `pgt_change_buffers`. Use the registry, not a broad schema wildcard.
4. Recreate managed trigger functions so new writes populate provenance.
5. Update WAL and stream-table writer metadata expected by the v0.90 binary.
6. Infer interval override provenance for existing target rows.
7. Seed one controller-state row per interval target.
8. Replace `pg_stat_pgtrickle` and SQL function wrappers.
9. Restore comments, ownership, and grants.
10. Bump catalog and extension versions only after every object is valid.

Adding nullable columns must be metadata-only on PostgreSQL 18. Recreating
managed trigger functions must not drop the source triggers or lose changes.
The documented upgrade procedure drains schedulers first, and the version
guard prevents old workers from running against the new catalog.

### 14.2 Existing target tables

Infer the v0.86 one-time translation as follows:

- If an interval target's schedule exactly matches the canonical translation
  that v0.86 generated, mark it `MIGRATED_DERIVED`, clear it from user
  configuration, and let the controller own timing.
- If the schedule is noncanonical, preserve it and mark it an explicit interval
  override.
- If an operator intentionally set the same value as the canonical translation
  before adding the target, migration cannot distinguish it. Document the
  inference and tell the operator to reapply the schedule after upgrade to mark
  an override.
- Preserve explicit FULL and DIFFERENTIAL as mode overrides. AUTO remains
  controller-owned.
- Preserve `ON_COMMIT` and `MANUAL` unchanged.

If exact evidence is available, begin in `INSUFFICIENT_DATA` and retain the
current safe schedule until the controller has enough evidence to tune. If
evidence is unavailable, begin in `EVIDENCE_UNAVAILABLE` and keep the existing
schedule indefinitely until the operator fixes the prerequisite.

No stream table needs a data reinitialization only because controller metadata
was added. Existing pending buffer rows lack source transaction provenance and
cannot become exact samples. Process them safely, exclude them from freshness
statistics, and start exact sampling with new v0.90 writes.

### 14.3 API compatibility

- Existing create and ALTER calls without a target behave as in v0.89.
- Existing interval, `on_commit`, `manual`, and clear inputs remain valid.
- `pgtrickle.freshness()` and `recommend_target_freshness()` are additive.
- `pg_stat_pgtrickle` adds columns at the end unless the existing generated
  contract specifies named placement. Never reorder existing columns silently.
- `commit_latency_stats()` keeps its signature. Its tracking mode becomes
  truthful, and exact fields no longer use duration fallback.
- `tune_recommendations()` remains callable for one compatibility cycle but
  stops returning controller-owned tuning advice.
- A removed GUC gets an upgrade entry with its replacement or the statement
  that no replacement is needed.
- Saved settings for removed GUCs must be reset before binary activation when
  PostgreSQL would reject them. Include exact `ALTER SYSTEM RESET` and
  `ALTER DATABASE RESET` commands in `UPGRADING.md`.

### 14.4 Rollback

Disabling `pg_trickle.adaptive_workers` returns worker admission to the v0.89
static path. Clearing a target materializes the last effective interval as a
normal schedule. These are operational fallbacks, not a SQL downgrade.

The project does not promise in-place extension downgrade. Document rollback
as restoring the pre-upgrade physical backup and v0.89 binaries. Because new
buffer columns are additive, emergency operation with the v0.90 binary and
adaptive workers disabled remains available while an operator diagnoses the
controller.

### 14.5 Version closure

Update:

- `Cargo.toml`, lockfile, extension control, and every version constant;
- fresh-install and archive SQL;
- upgrade completeness manifests;
- Docker and package metadata;
- `docs/WHATS_NEW.md`, `CHANGELOG.md`, and release notes;
- SQL and GUC generated catalogs; and
- compatibility and rollback documentation.

Run version sync, stale-version, package-install, and upgrade-chain checks
before marking the roadmap implemented.

## 16. Risks and mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| Commit timestamp tracking is off or history has been truncated | The controller cannot measure its contract. | Reject new targets, degrade upgraded targets, settle only exact samples, and report the restart requirement. |
| Transaction-ID conversion or wraparound is mishandled | Wrong timestamps could corrupt SLA decisions. | Validate the PostgreSQL 18 type contract in WP0, keep buffer intervals short, use set-based server functions, and property-test wrap boundaries. |
| Provenance columns increase CDC overhead and storage | The controller could violate the low-impact promise. | Use one bulk expression, nullable fixed-width fields, no per-row SPI, and defend the v0.87 overhead gate. |
| Downstream provenance resets at each stream table | Reported age would understate end-to-end latency. | Propagate the oldest source commit time through every stream-table buffer and test multi-level chains. |
| `now()` produces transaction-stable durations | Cost evidence becomes zero or stale. | Persist monotonic elapsed duration and use `clock_timestamp()` only for display timestamps. |
| Sparse samples make p95 and mode cost unstable | The controller may oscillate or claim confidence too early. | Require minimum samples, cap the rolling window, use three-observation hysteresis, and label bootstrap decisions. |
| Continuous values never form an identical hysteresis candidate | Tuning would never apply. | Compare numeric direction and move one supported step; compare exact candidates only for discrete mode changes. |
| Per-table SPI queries dominate a large catalog | Scheduler latency grows linearly with query count. | Batch metadata and history, query unique sources once, fan out in memory, and gate query count at 10,000 rows. |
| Adaptive schedulers in multiple databases fight over one pool | Capacity oscillates or exceeds the cluster limit. | Publish fixed-size demand samples and advance one locked cluster state below the v0.85 reservation authority. |
| CPU telemetry is missing or misleading | Worker sizing could hurt OLTP. | Use only the proven v0.87 CPU source, mark missing values unavailable, and retain the hard overload guard. |
| Shrink cancels a running refresh | Partial work or repeated load could result. | Shrink admission only and let exact live slots drain normally. |
| A one-second SLA is below tick plus service time | The controller cannot meet the target. | Use event-driven wake-ups, predict before the deadline, detect infeasibility, and scope the published claim to measured hardware. |
| An infeasible target remains highest priority | Other tables starve while the pool stays full. | Remove infeasible demand from growth, use sustainable cadence, and keep fair queue aging. |
| Explicit overrides are mistaken for derived state during upgrade | User intent changes silently. | Infer only the known v0.86 canonical schedule, report migration provenance, and document how to reapply an ambiguous override. |
| Old query samples influence a new plan | Mode and feasibility decisions are invalid. | Store and filter by plan identity, reset affected state on query change, and keep history for audit only. |
| Per-tick catalog updates create WAL and bloat | Self-tuning harms the primary workload. | Persist only new evidence, transitions, and applied decision changes. Keep pending streaks in scheduler memory. |
| Metric labels or diagnosis text create high cardinality | Monitoring memory and export cost grow without bound. | Use existing bounded table labels and keep reason detail out of labels. Batch OTLP export. |
| Removing a GUC breaks an operational workaround | Upgrade causes a regression. | Prove call sites, classify conservatively, keep needed safety limits advanced, and document every removal. |
| Controller state is missing or corrupt | Scheduling could stop or become unsafe. | Rebuild derived state, use conservative v0.89 behavior, and report repair without advancing a frontier. |

   integration, and multi-database stress.
8. **Reporting and telemetry.** Add SQL surfaces, explain, health, alerts,
   Prometheus, OTLP metrics, and recommendation output.
9. **Configuration and upgrade.** Remove proven redundant controls, write the
   migration, regenerate catalogs, and close compatibility tests.
10. **Soak and release closure.** Publish benchmarks, enable gates, finish docs,
    run the full CI matrix, and update version artifacts.

Keep each PR bisectable. The exact metric work may land before controller
activation, but no intermediate PR may label duration fallback as an SLA.
