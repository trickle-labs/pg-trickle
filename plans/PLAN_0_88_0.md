# v0.88.0 Implementation Plan: Vectorized Aggregates and Delta Planning

> **Status:** Implemented
> **Target:** v0.88.0
> **Baseline:** v0.87.17
> **Roadmap:** [roadmap/v0.88.0.md](../roadmap/v0.88.0.md)
> **Last updated:** 2026-08-31

> **Implementation outcome:** MT-8 uses dependency-free typed pages and a
> PostgreSQL temporary accumulator. LT-9 records statistics, estimates,
> observations, and shadow candidates; ADR-010 leaves physical SQL planning to
> PostgreSQL and keeps unvalidated rewrites out of the execution path.

## 1. Outcome

v0.88.0 speeds up the differential path without changing stream-table query
semantics. The release adds a dependency-gated vectorized executor for the
narrow pure-aggregate case and a statistics-backed planner for safe delta
operator ordering.

The v0.87.1 through v0.87.6 correctness program is a hard dependency. Its
exact oracle, replay corpus, semantic coverage, relation-schema contracts, and
release gate must protect the physical rewrites in this plan.

The work lands in this order:

1. Decompose `DiffContext` without changing generated SQL.
2. Record the aggregate dependency decision in an ADR.
3. Add the dependency-free aggregate batch path unless the ADR proves that
   Arrow earns its compile-time and maintenance cost.
4. Add statistics collection, a pure cost model, safe physical rewrites, and
   `pgtrickle.explain_delta_plan(pgt_id)`.
5. Prove exact result equivalence and defend the performance targets.

The release reuses three existing mechanisms:

- the direct aggregate change-buffer bypass in
  `src/dvm/operators/aggregate.rs`.
- the v0.87 bounded portal and temporary-batch machinery in
  `src/refresh/pipeline.rs`.
- the aggregate DELETE, UPDATE, and INSERT apply templates in
  `src/refresh/merge/mod.rs` and `src/refresh/codegen.rs`.

It does not add another refresh transaction, another frontier finalizer, or a
second aggregate apply strategy.

### 1.1 Release invariants

- A refresh remains one PostgreSQL transaction. Target changes, downstream
  CDC rows, frontier advancement, history, and status either commit together
  or roll back together.
- The vectorized path must produce the same logical delta schema as the SQL
  aggregate path. Existing apply and finalization code must not care which
  producer filled the batch relation.
- Unsupported functions, types, collations, expressions, or operator shapes
  use the existing SQL path. Eligibility is fail-closed.
- A runtime failure after the vectorized path starts aborts the refresh. It
  must not replay the same source interval through the SQL path in the same
  transaction.
- PostgreSQL owns SQL type semantics. Rust kernels are eligible only where
  they reproduce PostgreSQL NULL, overflow, comparison, and aggregate-result
  types exactly.
- The page size is an internal constant of 1,024 source rows. v0.88 adds no
  page-size GUC.
- Page-local state obeys the effective v0.87 pipeline memory slice. The
  executor may reduce a page below 1,024 rows for wide values.
- Cost planning never changes output column order, row identity, duplicate
  multiplicity, NULL extension, or exception behavior.
- Outer, full, semi, anti, lateral, recursive, and volatile boundaries are
  reorder barriers unless a specific equivalence rule and test prove otherwise.
- Missing, stale, or unreadable statistics keep the current operator order.
  They do not cause creation or refresh to fail.
- A cached delta template is not reused after the statistics that selected
  its physical order change.
- `explain_delta_plan()` performs planning only. It does not execute the
  defining query, consume change rows, mutate caches, or advance a frontier.
- No new direct dependency lands unless the ADR accepts it and all dependency
  gates pass.

### 1.2 Roadmap ambiguities resolved

The implementation uses these contracts:

| Roadmap ambiguity | v0.88 contract |
|---|---|
| "15-field `DiffContext`" | Decompose the actual baseline struct. Preserve fields added after the roadmap was written. |
| "Pure aggregate" | A top-level `Aggregate` over one `Scan`, including an empty `GROUP BY`. A transparent output-only project may be admitted only after the same eligibility helper proves that it is a rename or reorder. |
| AVG benefit, but no AVG accumulator | AVG uses the existing SUM and non-NULL COUNT auxiliary state. It has no separate averaging kernel. |
| MIN and MAX deletions | Vectorize page aggregation. If a deletion can invalidate the stored extremum, use the existing per-group rescan logic for that group. Do not guess the replacement value. |
| "SIMD-friendly" | Use contiguous typed `Vec<T>` columns and simple loops that LLVM can auto-vectorize. Do not add explicit architecture intrinsics in v0.88. |
| "Batched MERGE" | Reuse the existing batch relation and the selected apply strategy. Algebraic aggregates retain the faster explicit-DML apply path. MERGE remains available where the existing selector requires it. |
| Mutable `pg_statistic` with cached SQL | Store a statistics epoch with each planned template and invalidate when ANALYZE changes that epoch. |
| DISTINCT before projection | Move DISTINCT below a projection only when the projection is a one-to-one rename or reorder of all child columns. Other projections stay in place. |
| `EXPLAIN (FORMAT JSON) SELECT explain_delta_plan(...)` | The function itself returns the chosen engine plan as `jsonb`. The supported diagnostic is `SELECT pgtrickle.explain_delta_plan(pgt_id)`. Wrapping that call in PostgreSQL `EXPLAIN` explains the function call, not the internal delta plan. |
| DVM invariant validator | Strengthen validation to compare exact multisets for test and diagnostic use. A row-count-only comparison is insufficient. |
| "No TPC-H plan regression" | Compare correctness, estimated intermediate tuples, execution time, and spill behavior against a committed v0.87 baseline. Use the thresholds in section 10. |

### 1.3 Non-goals

- Parallel SPI connections or thread-based delta fan-out. PERF-O4 remains in
  the post-1.0 decoupled-compute roadmap.
- Arrow, Parquet, or object-store support unrelated to aggregate execution.
- A general PostgreSQL expression JIT in Rust.
- Vector kernels for user-defined aggregates, ordered-set aggregates,
  DISTINCT aggregates, aggregate FILTER clauses, collation-sensitive keys, or
  arbitrary extension types.
- Reordering across outer joins, semi joins, anti joins, lateral references,
  recursive CTEs, set operations, windows, or subqueries in v0.88.
- Running ANALYZE automatically. The planner consumes available statistics and
  reports when they are missing.
- A user-facing optimizer registry, hint syntax, or cost-weight GUC.

## 3. Target flow

```text
defining query
    -> parse and semantic admission
    -> collect one statistics snapshot
    -> build a safe physical delta plan
    -> validate row identity and output schema again
    -> choose delta producer
         -> vector aggregate pages, when eligible
         -> existing SQL differentiation, otherwise
    -> existing batch relation
    -> existing MERGE or aggregate explicit DML
    -> existing downstream capture and finalizer
```

Parsing decides what the query means. The cost planner decides only how safe
parts of the delta are evaluated. The refresh selector decides whether the
vector producer can replace the SQL producer for this execution. These
decisions stay separate so a missing statistic cannot weaken semantic
admission and a vector fallback cannot change operator order.

## 4. ENG-1: Decompose `DiffContext` first

### 4.1 Context ownership

Keep `DiffContext` as the single value passed to operator functions. Compose it
from the roadmap's three subcontexts and leave truly operator-local semantic
flags at the top level.

`CdcContext` owns:

- `prev_frontier` and `new_frontier`.
- `change_buffer_schema` and `delta_source`.
- `source_cdc_columns` and `source_key_columns`.
- `st_source_pgt_ids` and `source_buffer_names`.
- the methods that resolve previous and new LSNs and buffer names.

`CacheContext` owns:

- `cte_registry` and `cte_delta_cache`.
- `scan_pushed_predicate`.
- `st_bypass_tables`.
- `scan_delta_ctes`.
- `snapshot_cte_cache` and `snapshot_fingerprint_cache`.
- `fallback_leaf_oids`.

`OptimizationContext` owns:

- `cte_counter`, emitted CTEs, and the NOT MATERIALIZED set.
- `diff_depth`, `max_diff_depth`, and `max_diff_ctes`.
- the v0.88 physical plan and statistics evidence once LT-9 lands.
- CTE naming, depth guards, limit checks, and final WITH rendering.

The top-level `DiffContext` retains semantic state that does not fit those
groups:

- target table identity and defining-query metadata.
- `st_user_columns`, `st_has_pgt_count`, and `merge_safe_dedup`.
- temporary traversal flags such as `inside_semijoin` and `having_filter`.
- `st_column_alias_map`.
- `agg_sum_coalesce_defaults`.

Do not create a fourth subcontext only to make the top-level struct empty. The
three required contexts must have clear ownership. Remaining fields may stay
where their lifetime is obvious.

### 4.2 Delegation and migration

1. Add the three structs in `src/dvm/diff.rs` with private fields by default.
2. Move existing methods before moving operator call sites. `DiffContext`
   delegates LSN, cache, CTE, and limit operations.
3. Replace direct field access only where ownership moved. Do not rename
   unrelated operators or SQL fragments.
4. Preserve `DiffContext::new()` and `new_standalone()` as the two constructors.
5. Add focused builder or setter methods only for state currently populated in
   `src/dvm/mod.rs` or benchmarks. Do not add a generic builder framework.
6. Preserve save-and-restore behavior for `having_filter`,
   `inside_semijoin`, pushed predicates, and alias maps during recursive walks.
7. Keep recursion depth decrement on every success and error path.

### 4.3 No-behavior-change proof

Before the refactor, capture generated delta SQL and metadata for this corpus:

- scan, filter, and project.
- aggregate with SUM, COUNT, AVG, MIN, and MAX.
- inner, left, full, semi, and anti joins.
- DISTINCT and set operations.
- CTE reuse and recursive CTE.
- IMMEDIATE transition-table input.
- stream-table sources with bypass tables.
- deep joins that exercise snapshot caches and depth limits.

After the refactor, assert exact equality for SQL, output columns,
deduplication, key-change, and algebraic flags. Then run the full existing E2E
suite before ENG-1 merges.

## 5. ADR gate for the batch representation

### 5.1 Decision question

Publish a new ADR in `plans/adrs/` that answers:

> Should the v0.88 pure-aggregate executor use dependency-free typed Rust
> columns or add `arrow-array` and `arrow-compute`?

The default is dependency-free. Arrow wins only if measured end-to-end refresh
throughput improves enough to justify its costs. A microbenchmark of array
addition alone is not sufficient.

### 5.2 Required evidence

Measure both prototypes on the same toolchain and host:

- clean debug and release build wall time.
- incremental build time after editing the aggregate module.
- release extension binary size.
- direct and transitive dependency count.
- `cargo deny` license and advisory results.
- aggregate page throughput for COUNT, SUM, AVG, MIN, and MAX.
- end-to-end differential refresh throughput, including SPI read and apply.
- peak memory at 1,024-row pages.
- supported PostgreSQL types and semantic escape hatches.

Use at least five measured repetitions after one warmup. Record the median and
range. Commit the commands, toolchain version, host details, and raw result
summary in the ADR.

### 5.3 Acceptance rule

Choose dependency-free columns unless Arrow improves the median end-to-end
gate workload by at least 20 percent and does not prevent the release's 5x
target. This threshold prevents a large permanent dependency from landing for
a small kernel-only win that SPI and apply costs erase.

If the ADR accepts dependency-free columns:

- leave `Cargo.toml` and `Cargo.lock` unchanged.
- implement only the owned scalar types required by the eligibility matrix.

If the ADR accepts Arrow:

- add only `arrow-array` and `arrow-compute` with disabled default features.
- update dependency, license, security, and compile-time documentation.
- make the Arrow version exact enough to keep PostgreSQL extension builds
  reproducible.

The implementation must stop after the ADR if neither prototype can meet the
5x target without changing PostgreSQL semantics. Revise the roadmap instead of
shipping a nominal vector path that is slower than SQL.

## 6. MT-8: Vectorized aggregate path

### 6.1 One eligibility result

Add `VectorizedAggregateOperator` in
`src/dvm/operators/vectorized_agg.rs`. It owns pure eligibility and plan
construction. Runtime SPI work belongs in the refresh layer.

The helper returns either a `VectorAggregatePlan` or a stable fallback reason.
The plan contains:

- source OID and resolved change-buffer name.
- ordered group-key columns and type metadata.
- aggregate function, input column, input type, result type, and output alias.
- required auxiliary columns.
- target output order.
- frontier bounds or placeholder positions.
- whether an output-only project must rename or reorder columns.

Use one fallback enum for diagnostics and tests. Required reasons include:

- `not_single_scan_aggregate`.
- `join_or_subquery`.
- `unsupported_projection`.
- `distinct_aggregate`.
- `aggregate_filter`.
- `unsupported_function`.
- `unsupported_input_type`.
- `collation_sensitive_key`.
- `group_rescan_required`.
- `immediate_mode`.
- `partition_or_trigger_apply_constraint`.
- `statistics_or_type_metadata_unavailable`.

Eligibility must be pure once source and type metadata have been collected.
Unit tests must not require PostgreSQL.

### 6.2 Initial function and type matrix

The first implementation supports only built-in aggregates whose transition
semantics can be reproduced exactly:

| Function | Initial inputs | Result state | Notes |
|---|---|---|---|
| `COUNT(*)` | any eligible row | `i64` | Counts I and D weights. |
| `COUNT(column)` | any copied eligible value | `i64` | Ignores NULL exactly. |
| `SUM` | `int2`, `int4` | `i64` | Checked accumulation. Overflow raises the same SQLSTATE class as PostgreSQL. |
| `AVG` | `int2`, `int4` | `i64` sum plus `i64` count | Reuses existing auxiliary SUM and COUNT. Final division remains in PostgreSQL apply SQL. |
| `MIN`, `MAX` | `int2`, `int4`, `int8`, `date`, `timestamp`, `timestamptz` | typed extremum | Collation-free fixed-width comparisons only. |

Extend the matrix only with execution-backed equivalence tests. In particular,
do not admit `numeric`, `interval`, floating-point NaN cases, text collations,
domains, enums, arrays, or extension types through a generic Datum comparison.
Those inputs retain the SQL path in v0.88.

Global aggregates with no `GROUP BY` are eligible. Group keys initially use
fixed-width by-value types plus binary-collation text only if the ADR prototype
proves exact PostgreSQL hashing and equality. Other group keys fall back.

### 6.3 Owned column pages

At refresh start:

1. Resolve the same source frontier interval used by the SQL aggregate bypass.
2. Open one ordered SPI cursor over only the action, group key, and aggregate
   input columns required by the vector plan.
3. Fetch at most 1,024 rows or the remaining byte budget, whichever is lower.
4. Copy every value out of the SPI tuple table into an owned typed column
   before the SPI session ends.
5. Close the fetch SPI session before reducing or fetching the next page.

The dependency-free representation is a small enum of concrete column vectors,
not a general dataframe. Each column stores a value vector and a NULL bitmap.
Action weights use `i8`, with I as `+1` and D as `-1`.

Any required unsafe Datum access must live behind one narrow conversion helper.
Every unsafe block needs a `// SAFETY:` comment. The helper verifies type OID,
typmod, pass-by-value or copy requirements, and the active PostgreSQL memory
context before returning owned data.

### 6.4 Page-local hash aggregation

For each page:

1. Build a hash table keyed by the ordered group-key tuple.
2. Accumulate insert and delete row counts.
3. Accumulate each aggregate's insert and delete transition state in contiguous
   arrays.
4. Drop groups whose net state causes no target change only after comparing
   against the current target row where required.
5. Emit one logical delta row per changed group into the existing temporary
   delta relation.
6. Run the existing aggregate apply templates for that relation.
7. Truncate the relation and release page memory before fetching again.

The hash table is page-local. A group may appear in many pages, and each page
may update that group once. This preserves bounded memory and remains correct
because supported transition states are associative. Do not hold all changed
groups for the full refresh.

Use checked arithmetic for counts and integer sums. Convert overflow to a
`PgTrickleError` variant in `src/error.rs`, then raise it at the SQL boundary.
No SQL-reachable `unwrap()`, `expect()`, `panic!()`, or `unreachable!()` may
guard runtime eligibility.

### 6.5 MIN and MAX repair

MIN and MAX need more than page-local insert and delete extrema. For each
changed group:

- an insert can update the stored extremum directly.
- a deletion that does not equal the stored extremum leaves it unchanged.
- a deletion equal to the stored extremum marks that group for the existing
  source rescan.
- mixed insert and delete pages compare the inserted candidate with either the
  retained old extremum or the rescan result.

Collect affected group keys in the current page only. Use one parameterized or
temporary-key rescan per page, not one SPI query per group. The rescan reads the
post-change source snapshot and uses PostgreSQL MIN or MAX, so empty groups,
NULLs, and type semantics remain authoritative.

### 6.6 Apply integration

Extract the current aggregate apply sequence into one function that accepts a
type-identical delta relation name. Both producers call it:

- the SQL producer materializes its generated delta into the relation.
- the vector producer fills the relation from page-local accumulators.

The shared function performs the existing DELETE, UPDATE, and INSERT sequence,
downstream stream-table capture, row counters, trigger handling, and cleanup.
It must not advance the frontier or finalize history.

If the existing selector requires MERGE for a supported target layout, pass
the relation to the v0.87 pipeline MERGE shell. Do not force aggregate explicit
DML onto Citus, partitioned targets, or user-trigger modes that already have a
different safe path.

### 6.7 Fallback and failure behavior

Plan-time ineligibility uses the SQL path and records the fallback reason.
Runtime failures are divided into two classes:

- Before the first source row is read or target row is changed, a metadata
  mismatch may return to the SQL producer after resetting vector state.
- After source reading or apply begins, any error aborts the outer refresh
  transaction. The scheduler retries the original frontier interval later.

Never catch an overflow, comparator error, tuple-copy error, or apply error and
continue with a partial page.

### 6.8 Metrics

Extend existing bounded metrics rather than add per-table shared-memory maps.
Record:

- vector path selected.
- rows read and pages completed.
- groups emitted and groups rescanned for MIN or MAX.
- bytes copied and largest page bytes.
- SQL fallback counts by stable reason.
- read, reduce, rescan, and apply time.

Expose counters through the existing diagnostic or monitoring families. Avoid
labels derived from table names or query text.

## 7. LT-9: Cost-based delta planning

### 7.1 Separate SPI evidence from pure planning

Add a focused `src/dvm/planner.rs` module. It contains owned statistics types,
cost formulas, valid rewrite enumeration, plan selection, and JSON evidence.

Collect statistics in one short `Spi::connect()` block before planning. Query:

- `pg_class.reltuples` and `relpages`.
- `pg_statistic.stanullfrac` and `stadistinct`.
- MCV frequencies or histogram bounds only for supported built-in types.
- `pg_stat_all_tables` ANALYZE and VACUUM timestamps and counters.
- `pg_attribute.attname::text`, type OID, typmod, and collation.

The SPI layer converts rows to owned Rust values and closes before the planner
runs. Missing relation, alias, expression, or column statistics return an
unknown estimate. Catalog lookups must handle empty results without panicking.

### 7.2 Statistics epoch and cache validity

Build a deterministic statistics epoch from:

- planner format version.
- source OID and relation identity.
- last manual and automatic ANALYZE timestamps.
- `reltuples` and `relpages`.
- the statistic fields actually used for predicates, joins, grouping, or
  DISTINCT.

Hash the canonical byte representation with the project's existing hash
helper. Store the epoch and planning version in L1 and L2 delta-template
entries. A hit is valid only when both the query hash and epoch match.

On a cache hit, first run one bounded epoch probe for source relation identity
and ANALYZE or VACUUM counters. Reuse the template when that probe matches the
entry. Collect MCV and histogram data and rebuild the full epoch only when the
probe changes. This keeps the common hit path smaller than a complete
`pg_statistic` read while catching operations that can change `reltuples` or
column statistics.

If statistics cannot be read, use a distinct `unknown` epoch and preserve the
logical order. Do not keep a previously optimized order under fresh unknown
evidence.

The catalog-backed template table therefore needs migration columns for the
epoch and planning version. Fresh-install and upgrade SQL must change in the
same PR.

### 7.3 Cardinality estimates

Keep the first model small and inspectable:

- Base scan rows are `max(reltuples, 1)` when known.
- Equality selectivity is the matching MCV frequency when available.
  Otherwise use `(1 - null_fraction) / max(n_distinct, 1)`.
- `IS NULL` uses `null_fraction`. `IS NOT NULL` uses its complement.
- Supported range predicates use the histogram position. Without a compatible
  histogram, use PostgreSQL's documented default range selectivity.
- AND multiplies independent selectivities and clamps the result to `[0, 1]`.
- OR uses inclusion-exclusion and clamps the result.
- An equijoin estimate uses non-NULL input rows divided by the larger known
  distinct count, then clamps to the Cartesian bound.
- Unknown expressions carry an unknown estimate, not a fabricated zero.

Every estimate records its evidence and formula. The diagnostic must make MCV,
histogram, distinct-count, default, and unknown estimates distinguishable.

Do not claim that estimated tuple count is PostgreSQL planner cost or elapsed
time. v0.88 minimizes estimated intermediate tuples because that unit is
stable enough to compare valid DVM orderings.

### 7.4 Filter scheduling

Split only top-level AND conjunctions. For each conjunct:

1. Resolve every referenced source alias.
2. Push a conjunct through contiguous inner joins when it references one side
   only.
3. Stop at an outer, full, semi, anti, lateral, recursive, set-operation,
   window, aggregate, subquery, or volatile boundary.
4. Keep multi-source and unresolved predicates at their original level.
5. Order side-local filters by ascending estimated output cardinality.

The existing direct `Filter` to `Scan` pushdown remains the final SQL emission
mechanism. LT-9 moves eligible predicates into that shape before
differentiation.

### 7.5 Inner-join scheduling

Flatten only a contiguous region of inner equijoins whose predicates resolve
to known aliases. Preserve every predicate and the original logical output
description.

For up to eight inputs, use dynamic programming to choose the connected
left-deep order with the lowest sum of intermediate tuple estimates. Reject a
candidate that introduces a Cartesian join while a connected candidate exists.

For more than eight inputs, use a deterministic greedy order:

1. Start with the smallest filtered input.
2. Add the connected input that produces the smallest next intermediate.
3. Break ties by source OID and original position.

The implementation must include a `ponytail:` comment on the eight-input
enumeration ceiling and name measured planner time as the condition for
changing it.

After reordering:

- project columns back to the original output order.
- preserve canonical row-ID input order independently of physical join order.
- rerun `verify_plan_row_id_schema()`.
- compare output names and types with the pre-plan tree.
- discard the physical rewrite if any check differs.

Swapping the textual left and right inputs does not guarantee PostgreSQL's
hash build side. Confirm the chosen physical effect with PostgreSQL JSON
EXPLAIN in E2E tests. If PostgreSQL still picks a better build side, keep its
choice rather than adding planner hints.

### 7.6 DISTINCT scheduling

Move `Distinct(Project(child))` to `Project(Distinct(child))` only when the
project:

- contains direct column references only.
- references every child output exactly once.
- adds no expression, cast, constant, duplicate column, or dropped column.
- preserves the same collation and type for every output.

This rule removes work caused only by a rename or reorder. Any projection that
can collapse two distinct input rows is a barrier.

### 7.7 Cost decision and fallback

Generate the current order as candidate zero. Apply a rewrite only when:

- semantic checks pass.
- every estimate used to distinguish the winner is known.
- estimated intermediate tuples improve by at least five percent.
- the winner is deterministic under documented tie-breaking.

The five-percent margin avoids cache churn for differences smaller than
statistics noise. It is an internal constant, not a GUC.

If planning exceeds 10 milliseconds, stop enumeration and keep the best valid
candidate found so far. Record the timeout in the diagnostic. The implementation
must measure this bound in the deep-join benchmark before release.

## 8. `explain_delta_plan()` contract

### 8.1 SQL API

Add:

```sql
pgtrickle.explain_delta_plan(pgt_id bigint) RETURNS jsonb
```

The function uses `#[pg_extern(schema = "pgtrickle")]`, follows the existing
diagnostic ownership and visibility policy, and returns `PgTrickleError` at the
Rust boundary. A missing stream table returns the existing contextual not-found
error.

The function does not need a format argument. JSON is the stable machine
contract. Human inspection can use `jsonb_pretty()`.

### 8.2 JSON shape

Return a versioned object:

```json
{
  "format_version": 1,
  "pgt_id": 42,
  "statistics_epoch": "...",
  "statistics_complete": true,
  "vector_path": {
    "eligible": true,
    "selected": true,
    "fallback_reason": null
  },
  "original": {
    "operator_order": ["orders", "customers", "regions"],
    "estimated_intermediate_rows": 1200000
  },
  "chosen": {
    "operator_order": ["regions", "customers", "orders"],
    "estimated_intermediate_rows": 84000
  },
  "rules": [],
  "skipped_rules": [],
  "planning_time_us": 430
}
```

Each rule entry names the rule, affected stable operator IDs, before and after
estimates, and evidence source. Each skipped entry names the semantic barrier
or missing statistic. Do not include raw `pg_statistic` values that expose MCV
data to callers who cannot inspect the source table.

### 8.3 Relationship to existing diagnostics

- Keep `pgtrickle.explain_delta(name, format)` for PostgreSQL's plan of the
  generated delta SQL.

## 10. Verification and performance gates

### 10.1 Unit tests

- Context delegation preserves frontiers, placeholders, CTE names, caches,
  limits, and temporary traversal state.
- Vector eligibility accepts only the frozen function and type matrix.
- Typed pages preserve NULLs, action weights, and values after SPI memory is
  released.
- COUNT, SUM, AVG, MIN, and MAX match PostgreSQL edge semantics for every
  admitted type.
- Arithmetic overflow returns `PgTrickleError`.
- Statistics formulas clamp valid ranges and preserve unknowns.
- Filter pushdown stops at every barrier.
- Join enumeration preserves predicates and uses deterministic tie-breaking.
- DISTINCT moves only across bijective projections.
- Statistics epoch and planning-version changes invalidate templates.
- Diagnostic JSON is stable and serializable.

### 10.2 Integration tests

- The SPI collector casts `name` fields to `text` and handles missing catalog
  rows.
- Manual ANALYZE changes the epoch and forces a new physical plan.
- Unanalyzed tables keep logical order and report incomplete evidence.
- L1 and L2 cache hits preserve the selected plan only under the same epoch.
- `explain_delta_plan()` enforces the established diagnostic access policy.
- The diagnostic performs no DML, frontier write, buffer cleanup, or cache
  mutation.

### 10.3 Light E2E tests

- Grouped and global COUNT, SUM, AVG, MIN, and MAX handle INSERT, DELETE, and
  UPDATE across one and many pages.
- NULL-only groups, empty groups, group-key changes, and extremum deletion
  match the defining query.
- Unsupported aggregate functions, types, FILTER, DISTINCT, joins, HAVING,
  and unsafe projects use the SQL path with the expected reason.
- A vector failure rolls back target rows, downstream rows, frontier, and
  history.
- Filter and join reordering preserve exact rows and row IDs.
- Outer joins and other barriers retain their original order.
- The existing SQL aggregate path remains correct when vector eligibility is
  false.

### 10.4 Full E2E and stability tests

- Exact multiset equivalence runs after every mutation cycle with
  `pg_trickle.validate_delta_invariants` enabled.
- Stream-table chains receive identical downstream D and I rows.
- Partitioned, Citus, user-trigger, IMMEDIATE, recursive, and fused cases use
  their documented existing paths.
- Crash and injected-error tests leave the original frontier interval
  replayable.
- Concurrent scheduler and manual refreshes do not share vector page state.
- Long-running soak coverage shows bounded backend memory and no group drift.

### 10.5 Aggregate benchmark

Commit one canonical primary gate and a broader tracking matrix.

The primary gate uses:

- 1,000,000 source rows.
- 10,000 integer groups.
- one `SUM(int4)`, one `COUNT(*)`, and one `AVG(int4)`.
- a 100,000-row mixed delta with deterministic INSERT, DELETE, and UPDATE.
- a 1,024-row vector page.
- one warmup and five measured refreshes.
- identical PostgreSQL, container CPU, memory, and GUC settings.
- exact multiset validation after each measured refresh.

Compare median changed source rows per second with the saved v0.87 SQL path.
The release gate is at least 5x throughput with no correctness mismatch. Report
p50 and p95 refresh time, peak RSS, temporary bytes, pages, emitted groups, and
apply time.

The tracking matrix adds:

- each supported aggregate alone.
- group cardinalities 1, 100, 10,000, and 1,000,000.
- delta ratios 0.1, 1, and 10 percent.
- insert-only, delete-only, update-only, and mixed changes.
- MIN and MAX with 0, 1, and 50 percent extremum invalidation.
- unsupported-type SQL fallbacks to detect regressions.

Do not average the vector and fallback cases into the 5x claim.

### 10.6 TPC-H regression contract

Use the existing TPC-H E2E corpus with a committed v0.87 artifact. For each
differential query, store:

- exact result hash or multiset comparison.
- chosen engine order and statistics epoch.
- PostgreSQL JSON plan.
- estimated intermediate tuples.
- median execution time across five measured cycles.
- temporary bytes and spill occurrence.

The release fails if:

- any result differs.
- any previously differential query falls back to FULL.
- total median differential time regresses by more than 5 percent.
- any individual query regresses by more than 10 percent without a reviewed
  documented exception.
- a new spill appears on a query that did not spill in v0.87.
- planning time exceeds 10 milliseconds for the supported join corpus.

## 14. Risks and mitigations

| Risk | Mitigation |
|---|---|
| Rust aggregate semantics differ from PostgreSQL | Admit a small built-in type matrix, use checked operations, leave final AVG division and MIN and MAX rescans to PostgreSQL, and compare exact results. |
| SPI Datums outlive their memory context | Copy to owned typed columns inside the fetch session and test after the session closes. |
| Page boundaries change aggregate results | Use associative transition state, apply each group at most once per page, and test the same delta at page sizes 1, 7, 1,024, and above one page. |
| MIN or MAX deletion leaves a stale extremum | Detect deletion of the stored extremum and batch affected groups through PostgreSQL rescan. |
| A runtime fallback applies a delta twice | Permit SQL fallback only before reading or applying any row. Abort after execution starts. |
| Vector output bypasses downstream CDC or triggers | Feed the existing relation-based apply path and run chain and user-trigger E2E tests. |
| Arrow returns through an unrelated feature | ADR scope permits only aggregate arrays and compute. No Parquet or object-store code. |
| Context refactor changes SQL | Land ENG-1 alone and require exact generated-SQL fixtures plus full E2E. |
| Join reorder changes row IDs or column order | Preserve canonical logical order, rerun row-ID verification, compare output schemas, and discard unsafe rewrites. |
| Filter movement changes NULL behavior | Push only side-local predicates through inner joins. Treat all other joins as barriers. |
| DISTINCT movement changes multiplicity | Require a bijective direct-column projection. |
| Statistics are absent or stale | Keep current order, report incomplete evidence, and tie cache validity to the ANALYZE epoch. |
| Planning cost exceeds refresh savings | Bound exhaustive enumeration at eight inputs and 10 milliseconds, then use deterministic greedy planning. |
| Cache churn follows noisy estimates | Require at least five-percent estimated improvement and a changed statistics epoch. |
| Diagnostic leaks source statistics | Return estimates and evidence kinds, not raw MCV values, and follow existing access policy. |
| The 5x target measures only a kernel | Gate end-to-end refresh throughput with SPI, apply, finalization, and exact oracle enabled. |
| TPC-H gets faster estimates but slower execution | Gate wall time and spill behavior as well as estimated intermediates. |
