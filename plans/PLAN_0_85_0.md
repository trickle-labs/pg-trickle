# v0.85.0 Implementation Plan — Scheduler and Resource Resilience Gate

**Status:** Planned
**Target:** v0.85.0
**Baseline:** v0.84.0
**Roadmap:** [roadmap/v0.85.0.md](../roadmap/v0.85.0.md)
**Last updated:** 2026-08-16

---

## 1. Outcome

v0.85.0 makes the existing in-process scheduler safe and predictable across
multiple databases, delayed worker startup, worker crashes, blocked refreshes,
large catalogs, slow metrics clients, and adversarial API input.

The release is complete only when these invariants hold:

1. Every coordinator uses one effective cluster worker limit derived from all
   pg_trickle limits and PostgreSQL's `max_parallel_workers`. Reservation,
   spawn, worker start, worker exit, and crash reconciliation cannot exceed or
   silently reduce that limit.
2. Shared scheduler state that names a stream table or database is keyed by
   database OID. Identical `pgt_id` values in different databases cannot share
   pause state, scheduler health, queue depth, or watermark state.
3. Entering drain mode is a persistent dispatch gate. Completion does not
   resume scheduling; only an explicit resume action or postmaster restart
   returns the cluster to normal dispatch.
4. Drain completion proves that every registered database scheduler has
   observed the request and has no relevant inline, reserved, spawning, queued,
   or live refresh work.
5. Every scheduled refresh runs with finite transaction-local lock and
   statement deadlines. A deadline records a typed retryable failure, releases
   worker capacity, and allows drain to complete.
6. Inline and dynamic-worker refreshes use one persistent outcome,
   error-accounting, remediation, retry, and suspension path. No in-memory
   retry path can erase repeated catalog-visible failures.
7. OOM remediation actually lowers the affected stream table's effective
   refresh memory, lock-timeout remediation actually backs off dispatch, and
   both reset only after the documented successful-cycle threshold.
8. Queue-depth gauges represent jobs still in `QUEUED`, not cumulative
   enqueues. Claims, cancellations, spawn failures, crash recovery, and
   reconciliation preserve the exact value.
9. Terminal scheduler jobs, refresh history, and deferred cleanup are pruned
   during normal uptime in bounded batches. No maintenance backlog can create
   an unbounded scheduler tick.
10. An idle metrics endpoint performs no metrics collection query. Network I/O
    is non-blocking, request work is deadline-bounded, and a slow client cannot
    delay refresh dispatch.
11. Every alert payload is valid JSON and valid UTF-8 below PostgreSQL's
    `NOTIFY` payload limit. Reminder cadence is based on last successful
    emission, not scheduler-tick timing.
12. SQL parsing, bulk APIs, pause/resume controls, and blocking control calls
    have conservative finite defaults and non-bypassable hard maxima.
13. Client cancellation or disconnect leaves scheduler state in a complete,
    documented state: a requested pause/drain remains a valid control state,
    and no partial capacity reservation or half-applied target set remains.
14. Fuzz smoke and nightly jobs derive their target list from one source of
    truth, run every declared target, exercise production parser/rewrite and
    CDC decode seams, and fail if required property case counts are not met.
15. Mandatory linting detects dynamic SQL assembled in variables before being
    passed to SPI unless the construction uses the repository's typed,
    parameterized, or explicitly reviewed identifier path.

This release does not add an external worker protocol, adaptive external pool,
new monitoring backend, general job queue, or scheduler feature. It hardens the
existing single-node architecture and preserves differential refresh as the
primary mode.

## 3. Target Design

### 3.1 Database-scoped shared scheduler registry

Build the database-scoped shared-state foundation before changing worker,
pause, drain, queue, or watermark behavior. Keep fixed-capacity shared-memory
structures in `src/shmem.rs`; do not add a shared-memory allocator or generic
registry framework.

Use database OID as the stable key:

```rust
#[derive(Copy, Clone, Eq, PartialEq)]
struct DatabaseKey(u32);

struct DatabaseSchedulerSlot {
    database_oid: u32,
    scheduler_pid: i32,
    running: bool,
    last_wake_epoch_secs: i64,
    drain_seen_epoch: u64,
    inline_pgt_id: i64,
    queue_depth: u32,
    last_tick_oldest_xmin: u64,
    last_tick_safe_lsn_u64: u64,
}

struct PausedNodeEntry {
    database_oid: u32,
    pgt_id: i64,
}
```

Exact names may follow existing conventions. Required behavior:

1. Register or refresh a database slot when its scheduler starts.
2. Clear the slot only when that database scheduler exits or the launcher
   proves its PID is dead.
3. Store scheduler health, drain acknowledgement, inline execution, queue
   depth, and watermark state in the matching database slot.
4. Address pause entries by `(database_oid, pgt_id)`.
5. Reject registration or pause insertion with a typed capacity error. Never
   overwrite another database, evict a live entry, or report success after a
   failed insert.
6. Keep cluster-wide monotonic counters separate from scoped gauges. Existing
   cumulative reliability counters remain atomic where exact scoping is not
   required.
7. Use one lock acquisition for batch pause insertion so capacity validation
   and mutation are atomic from other backends' perspective.
8. Prune stale database and pause entries only after proving the scheduler or
   stream table no longer exists. Hash/modulo collision is not a proof.

The compile-time registry maximum must be documented and at least the
supported maximum number of database schedulers. Startup must fail closed for
the affected database if no slot is available; it must not run with
cluster-global fallback state.

Pure helpers cover slot lookup, insertion, stale-slot replacement, capacity
calculation, and database isolation without PostgreSQL.

### 3.2 Authoritative worker limit and reservation lifecycle

Define one immutable `WorkerCapacity` snapshot per dispatch tick:

```rust
struct WorkerCapacity {
    pgtrickle_dynamic_limit: u32,
    pgtrickle_parallel_limit: Option<u32>,
    postgres_parallel_limit: u32,
    effective_limit: u32,
}
```

The effective limit is the minimum of:

- `pg_trickle.max_dynamic_refresh_workers`;
- `pg_trickle.max_parallel_workers` when non-zero;
- PostgreSQL `max_parallel_workers`.

Read PostgreSQL's setting with one typed query during coordinator startup and
after SIGHUP, not once per candidate job. A zero PostgreSQL limit disables
dynamic refresh dispatch and leaves inline mode available. Continue treating a
background-worker registration failure caused by `max_worker_processes` as an
explicit spawn failure; do not claim `max_parallel_workers` replaces
PostgreSQL's separate hard worker-process ceiling.

Replace the anonymous active counter with a fixed-capacity worker-slot table:

```rust
enum WorkerSlotState {
    Free,
    Reserved,
    Live,
}

struct RefreshWorkerSlot {
    generation: u64,
    database_oid: u32,
    job_id: i64,
    scheduler_pid: i32,
    worker_pid: i32,
    state: WorkerSlotState,
    reserved_at_epoch_ms: u64,
}
```

All state transitions occur under one `PgLwLock`:

| Event | Required transition |
|---|---|
| Coordinator accepts a ready unit | Allocate `Free -> Reserved` only if `reserved + live < effective_limit` |
| Job enqueue fails | Release that exact reservation |
| Worker registration fails | Cancel the queued job, then release that exact reservation |
| Worker connects and claims the job | Promote the matching `Reserved -> Live`; store worker PID |
| Worker cannot claim/cancels before execution | Release the matching reservation |
| Worker completes normally | Release the matching live slot after durable job completion |
| Worker crashes | Reconciliation marks its job retryable, then releases the matching live slot |
| Coordinator crashes before spawn | Reconciliation cancels the orphaned queued job and releases its reservation |

Use `(database_oid, job_id, generation)` as the reservation identity. Pass the
generation in `bgw_extra` or load it from a new non-null job column; a stale
worker must not release a newer job's slot.

Reconciliation rules:

- Never assign `live_count` directly from a sampled aggregate.
- Reconcile individual slots against scheduler PID, worker PID,
  database-local job state, and reservation age.
- Absence from `pg_stat_activity` is sufficient to reap a `Live` slot whose
  worker PID was previously recorded.
- Absence of a worker PID is not sufficient to reap a `Reserved` slot; delayed
  worker startup is a valid state.
- A reservation is reaped only when its coordinator is dead, its job is
  terminal/missing, or its spawn path recorded failure.
- Failed reconciliation leaves the slot reserved and reports degraded capacity;
  it never invents free capacity.
- Reconciliation exposes counts for reserved, live, effective limit, and stale
  slots through `worker_pool_status()` and Prometheus.

Per-database quota and burst calculation consumes the same capacity snapshot
and exact cluster occupancy. Remove any call that acquires against the raw
configured limit after computing a smaller effective limit.

### 3.3 Database-local pause semantics

`pause_scheduler(nodes)` and `resume_scheduler(nodes)` remain database-local.
They use the current database OID plus canonical stream-table identity from the
v0.84.0 resolver.

The pause call is ordered:

1. Reject NULLs, duplicates, and an array larger than the configured control
   target limit.
2. Resolve and authorize every name before changing shared memory.
3. Determine the number of new `(database_oid, pgt_id)` entries.
4. Acquire the pause-state lock once, verify total capacity, and insert the
   full set atomically.
5. Wait only for local queued/running jobs or inline execution whose
   `member_pgt_ids` intersect the selected IDs.
6. Return success only after selected work stops. A timeout is a typed error or
   explicit timeout result, not a warning followed by `"OK"`.

Already-paused nodes are idempotent and do not consume capacity. A failed batch
leaves the prior pause set unchanged. A cancelled wait leaves the complete
requested pause set in place, which is safe and documented; the caller can
resume it explicitly.

`resume_scheduler(nodes)` performs the same full prevalidation and removes the
batch under one lock. Waiting for selected nodes must not inspect unrelated
workers in another database.

### 3.4 Persistent drain state machine

Replace requested/completed epoch comparison with an explicit cluster-wide
state:

```rust
enum DrainPhase {
    Running,
    Draining,
    Drained,
}

struct DrainState {
    phase: DrainPhase,
    epoch: u64,
    requested_at_epoch_ms: u64,
}
```

Drain protocol:

1. `drain(timeout_s)` validates and caps the timeout, changes `Running` to
   `Draining`, increments the epoch, and wakes every database scheduler.
2. A scheduler observing `Draining` stops enqueueing work before any readiness
   or token reservation.
3. Each scheduler finishes its current inline transaction, processes terminal
   worker outcomes, confirms no local queued/reserved/live work remains, and
   stores `drain_seen_epoch`.
4. The state becomes `Drained` only when every live database scheduler slot has
   acknowledged the current epoch and the worker-slot table contains no
   reserved or live entries.
5. `Drained` continues to gate dispatch on every tick.
6. A timeout returns `false` but leaves the state in `Draining`; maintenance
   safety must not disappear because the waiting client stopped waiting.
7. Repeated `drain()` calls join the current epoch rather than creating an
   endless sequence of requests.
8. `pgtrickle.resume_after_drain()` explicitly changes `Draining` or `Drained`
   to `Running`, clears acknowledgements for the old epoch, and wakes
   coordinators.
9. Postmaster restart initializes `Running`. Per-database scheduler restart,
   SIGHUP, extension upgrade, and client disconnect do not resume a drain.

Make the three states SQL-visible without conflating "not requested" and
"completed":

```text
pgtrickle.is_drained() -> boolean
    NULL  = no drain request / Running
    false = Draining
    true  = Drained

pgtrickle.resume_after_drain() -> boolean
    true  = a drain state was cleared
    false = already Running
```

The nullable `is_drained()` result is an intentional minor-release behavior
change. Add `drain_phase`, epoch, request age, unacknowledged database count,
reserved workers, and live workers to diagnostics/metrics.

The new resume function is `admin_global` in
`scripts/sql_api_policy.json`, uses the existing extension-owner/superuser
authorization, and receives exact migration ACLs.

### 3.5 Scheduled refresh deadlines and typed timeout outcomes

Add scheduler GUCs with finite defaults:

| GUC | Default | Range | Scope |
|---|---:|---:|---|
| `pg_trickle.scheduled_lock_timeout_ms` | `30000` | `100..=600000` | Time any scheduled refresh statement may wait for a lock |
| `pg_trickle.scheduled_statement_timeout_ms` | `900000` | `1000..=86400000` | Time any scheduled refresh statement may execute |

The defaults are long enough for normal large refreshes but finite. Manual
`refresh_stream_table()` retains caller-controlled PostgreSQL timeout semantics;
only scheduler-initiated inline, dynamic, fused, cyclic, and atomic-group work
receives these defaults.

At the start of every scheduled refresh transaction:

```sql
SET LOCAL lock_timeout = '<configured-ms>ms';
SET LOCAL statement_timeout = '<configured-ms>ms';
```

Apply both through one helper before catalog row locking, source locking,
planning, FULL materialization, differential SQL, and finalization. Values come
from validated integers and are not user-interpolated arbitrary text.

Preserve PostgreSQL error metadata while crossing the pgrx boundary:

```rust
enum RefreshFailureKind {
    LockTimeout,
    StatementTimeout,
    Deadlock,
    Serialization,
    OutOfMemory,
    Cancelled,
    Permanent,
    UnknownRetryable,
}

struct RefreshFailure {
    kind: RefreshFailureKind,
    sqlstate: Option<String>,
    message: String,
    retryable: bool,
    counts_toward_suspension: bool,
}
```

Classification uses SQLSTATE first:

- `55P03` plus the lock-timeout report becomes `LockTimeout`;
- `57014` plus the statement-timeout report becomes `StatementTimeout`;
- user/admin cancellation remains `Cancelled`, not a fabricated timeout;
- message matching is a compatibility fallback only when no SQLSTATE survives.

Schema changes:

```sql
ALTER TABLE pgtrickle.pgt_refresh_history
    ADD COLUMN error_code text,
    ADD COLUMN error_sqlstate text,
    ADD COLUMN retryable boolean;

ALTER TABLE pgtrickle.pgt_scheduler_jobs
    ADD COLUMN outcome_code text,
    ADD COLUMN outcome_sqlstate text,
    ADD COLUMN worker_slot_generation bigint;
```

Add focused checks for the stable error-code vocabulary. Historical rows remain
NULL. Timeout failures complete both history and job rows in a fresh valid
transaction, release the exact worker slot, enter retry backoff, and contribute
to suspension accounting.

### 3.6 Unified persistent error accounting and self-healing

Refactor refresh execution into two layers:

1. The core refresh transaction returns `RefreshExecutionResult` or a typed
   `RefreshFailure`; it does not independently decide suspension.
2. One `record_scheduled_outcome()` path persists history/job outcome, updates
   retry/error/remediation state, emits alerts, and returns the coordinator's
   scheduling outcome.

Inline and dynamic workers call the same outcome recorder exactly once.
Coordinator polling of an already-recorded dynamic result adjusts only
in-memory DAG readiness/backoff; it must not increment errors a second time.

Persist the promised remediation state on `pgt_stream_tables`:

```sql
ALTER TABLE pgtrickle.pgt_stream_tables
    ADD COLUMN self_heal_work_mem_percent smallint NOT NULL DEFAULT 100,
    ADD COLUMN self_heal_lock_backoff_exponent smallint NOT NULL DEFAULT 0,
    ADD COLUMN self_heal_success_streak smallint NOT NULL DEFAULT 0,
    ADD COLUMN last_error_code text,
    ADD COLUMN last_error_retryable boolean;
```

Constraints:

- work-memory percentage: `25..=100`;
- lock-backoff exponent: `0..=6`;
- success streak: `0..=3`;
- last error code belongs to the stable vocabulary when non-NULL.

Remediation rules:

| Outcome | Persistent action |
|---|---|
| OOM and `self_heal_oom=on` | Multiply effective work-memory percentage by 0.75, floor to a 25% minimum, clear success streak, record retryable failure |
| Lock timeout and `self_heal_lock_timeout=on` | Increment backoff exponent to a maximum of 6, clear success streak, record retryable failure |
| Any other failure | Keep existing remediation, clear success streak, record failure |
| Successful scheduled cycle with active remediation | Increment success streak |
| Third consecutive successful cycle | Reset memory percentage to 100, lock exponent to 0, and success streak to 0 |

Self-healing never resets `consecutive_errors`. Every retryable failure that
counts toward suspension increments it, including OOM and lock timeout. The
normal `max_consecutive_errors` threshold suspends repeated unresolved failure.
A successful refresh resets `consecutive_errors` through the common finalizer.

Construct a `RefreshRuntimeTuning` value when loading a stream table:

- effective `merge_work_mem_mb` and `delta_work_mem` are the validated base GUC
  values multiplied by `self_heal_work_mem_percent`;
- existing `delta_work_mem_cap_mb` remains an absolute cap;
- minimum non-zero effective memory is 1 MB;
- lock backoff multiplies only scheduler eligibility delay, not the user-defined
  schedule stored in the catalog;
- all planner-hint call sites receive the same tuning value rather than reading
  base GUCs independently.

Expose remediation state and last typed failure in `pgt_status()`,
`health_check()`, `explain_stream_table()`, refresh history, worker job
diagnostics, and Prometheus.

### 3.7 Exact queue depth and bounded catalog maintenance

Move queue depth into each database scheduler slot. The cluster metric is the
sum of registered database depths; per-database metrics include `db_oid` and
`db_name`.

Make `SchedulerJob` state transitions return whether a row left `QUEUED`:

- enqueue increments after the catalog insert commits;
- successful `QUEUED -> RUNNING` claim decrements once;
- `QUEUED -> CANCELLED` decrements once;
- cancellation of a running/terminal job does not decrement;
- spawn failure cancels the queued job and decrements through the same
  transition helper;
- orphan recovery decrements the number of queued rows it cancels;
- worker exit before claim uses cancellation, not a raw counter decrement.

On scheduler startup and periodically during uptime, reconcile only the current
database slot with:

```sql
SELECT count(*) FROM pgtrickle.pgt_scheduler_jobs WHERE status = 'QUEUED';
```

A failed query preserves the prior gauge and increments a reconciliation error;
it does not set zero.

Add bounded maintenance GUCs:

| GUC | Default | Range |
|---|---:|---:|
| `pg_trickle.scheduler_maintenance_batch_size` | `1000` | `10..=10000` |
| `pg_trickle.scheduler_job_retention_seconds` | `3600` | `60..=2592000` |

Maintenance protocol:

1. Run at most one terminal-job delete batch, one refresh-history delete batch,
   and one deferred-cleanup batch per scheduler tick.
2. Delete rows by an indexed limited key/`ctid` subquery, not one unbounded
   `DELETE`.
3. If a batch is full, mark that category as having backlog and run its next
   batch on the next tick rather than waiting for the long periodic interval.
4. If a batch is short, clear backlog and wait until the configured interval.
5. Rotate categories so continuous history backlog cannot starve terminal-job
   or cleanup work.
6. Record rows processed, elapsed time, backlog state, and errors.
7. Keep each SPI transaction short and outside dispatch-critical locks.

Change the current history-prune loop to one batch per tick. Apply the same
budget to terminal `pgt_scheduler_jobs`, deferred resource cleanup, and any
template-cache purge touched by this release. Add/verify indexes for terminal
`finished_at` and refresh-history `start_time`.

### 3.8 Scheduler-safe metrics endpoint

Invert the current metrics API: the endpoint determines whether a valid scrape
exists before the scheduler collects metrics.

Target interface:

```rust
metrics_server.poll(|remaining_budget| {
    collect_metrics_text_with_deadline(remaining_budget)
});
```

Required behavior:

1. `accept`, request reads, and response writes are non-blocking.
2. Keep a small fixed-capacity connection state machine with an absolute
   monotonic deadline from `pg_trickle.metrics_request_timeout_ms`.
3. Process a bounded number of bytes/connections per scheduler tick.
4. A partial/slow request remains pending until its deadline without sleeping
   the scheduler; an expired request receives `408` when possible and closes.
5. `/health` and 404/400 responses do not call `collect_metrics_text()`.
6. A complete `GET /metrics` invokes collection once.
7. Metrics SPI runs with a transaction-local `statement_timeout` no greater
   than the request's remaining budget.
8. A collection timeout returns a bounded `503` response and typed metrics
   error; dispatch continues.
9. A slow reader never causes a blocking write loop. Write a bounded chunk per
   tick or close after the deadline.
10. Idle polling performs zero SPI and zero metrics string construction.

Add `pg_trickle.metrics_bind_address`, default `127.0.0.1`. Accept only a
literal IPv4/IPv6 address, reject hostnames/NUL, and combine it with the
validated port using `SocketAddr`. This makes source, GUC description,
configuration docs, multi-tenant guidance, logs, and security guidance agree.
Existing users wanting remote exposure explicitly configure `0.0.0.0` or
`::`.

Each database still requires a distinct metrics port. Changing bind address or
port follows the documented scheduler-restart boundary; no hot socket swap is
added.

Metrics tests use an injected collector closure/counter to prove:

- 10,000 idle polls perform zero collections;
- `/health` performs zero collections;
- one complete scrape performs exactly one collection;
- malformed and slow requests stay within the tick budget;
- a collection timeout yields 503;
- bind address parsing and logs match configuration.

### 3.9 Structured alerts and timestamp throttling

Route every `pgtrickle_alert` producer through one parameterized helper.
Remove direct `NOTIFY ... '<escaped>'` SQL and hand-built JSON from buffer,
slot, watermark, fuse, frozen-tier, cleanup, and scheduler paths.

Build payloads as `serde_json::Value`, then enforce the byte budget before final
serialization:

1. Reserve bytes for required fields: `event`, database identity, stream-table
   identity where applicable, and `"truncated": true`.
2. Traverse string values and truncate on `char_indices()` boundaries.
3. Prefer truncating large detail/error fields before identifiers.
4. If optional fields still exceed the budget, remove them deterministically
   and include `omitted_fields`.
5. Serialize only after reduction.
6. Assert serialized byte length is at most 7,900 and parse it back as JSON in
   debug/tests.
7. Send with `SELECT pg_notify('pgtrickle_alert', $1)` and a bound parameter.
8. Return a result so throttles advance only after successful emission.

Do not byte-slice serialized JSON or append guessed braces.

Replace modulo reminders with scheduler-local timestamps keyed by
`(database_oid, pgt_id, AlertEvent)`:

```rust
if now_ms.saturating_sub(last_emitted_ms) >= interval_ms {
    if emit_alert(...).is_ok() {
        last_emitted_ms = now_ms;
    }
}
```

Prune entries for removed stream tables during normal scheduler state pruning.
The first eligible reminder after scheduler restart may emit once; fast ticks
cannot duplicate it, and slow ticks cannot miss the next interval.

### 3.10 Resource ceilings and cancellation-safe controls

Use conservative defaults and hard maxima:

| Resource | v0.85.0 default | Hard maximum | Behavior at limit |
|---|---:|---:|---|
| Parse-tree nodes | `100000` | `1000000` | Reject before DVM tree allocation/rewrite expansion |
| Parse recursion depth | `64` | `256` | Return `QueryTooComplex` |
| Grouping-set branches | `64` | `1024` | Reject before expansion |
| Differential CTE count | `1000` | `10000` | Fail closed to FULL in AUTO; reject explicit incremental mode |
| Bulk API items | `256` | `1000` | Reject the complete request before target mutation |
| Pause/resume targets per call | `64` | `256` | Reject before shared-state mutation |
| Drain API timeout | configured `60s` | `3600s` | Reject values outside the range |
| Pause wait timeout | configured `30s` | `3600s` | Reject values outside the range |

`max_parse_nodes = 0` no longer disables the guard. Install/upgrade migration
and documentation call out the behavior change. Keep a hard compile-time cap in
addition to the GUC maximum so a corrupted setting cannot bypass allocation
guards.

Add `pg_trickle.max_bulk_api_items` and
`pg_trickle.max_control_targets` with the defaults/maxima above. Direct and
bulk code shares constants/helpers from existing validation/config modules;
do not retain separate 1,000-item literals.

All control calls:

- validate the entire request before changing shared state;
- apply one atomic shared-state batch;
- use an interruptible PostgreSQL wait helper rather than
  `std::thread::sleep`;
- check postmaster death and `CHECK_FOR_INTERRUPTS` between bounded waits;
- preserve a fully requested drain/pause after cancellation rather than
  partially rolling it back;
- release any worker reservation through an explicit transition before a
  cancellable wait begins.

### 3.11 Truthful fuzz and property workflows

Use `fuzz/Cargo.toml` as the only cargo-fuzz target inventory. Replace workflow
arrays with a script that emits the declared `[[bin]]` names in deterministic
order. `scripts/check_fuzz_targets.py` validates both smoke and nightly
workflows consume that inventory rather than checking whether target text
appears somewhere in one file.

Rename misleading targets while preserving/migrating corpora:

- parser helpers that do not call PostgreSQL parsing become
  `api_guard_fuzz`;
- SQLSTATE classification becomes `error_classifier_fuzz`;
- CDC/WAL decoding targets are named for the production decoder seam they

Add a production test-decoding parser target that calls the same
`extract_table_name_from_test_decoding`, action parser, new/old column parsers,
schema-mismatch detector, and parameter-plan builder used by
`poll_wal_changes()`. Fuzz-only wrappers may expose those functions but may not
duplicate their logic.

add a PostgreSQL-backed adversarial property suite rather than claiming the

- zero matching tests, missing corpus, or skipped target is a failure unless
  the workflow explicitly runs a bounded seed fuzz;

- the PostgreSQL-backed parser/rewrite and CDC property suites run in both

### 3.12 Mandatory variable-built dynamic SQL lint

- variables assigned from `format!`, `write!`, `push_str`, or concatenation

- those variables passed to `Spi::run`, `Spi::get_*`, `client.select`,

- `just lint`;
- `just lint-ci`;
- the PR CI lint job.

Unit fixtures cover direct, multiline, variable-built, helper-returned,

## 4. Error Model

Add focused `PgTrickleError` variants where existing variants cannot preserve
the required context:

| Condition | Required context and behavior |
|---|---|
| Worker capacity exhausted | effective limit, reserved count, live count, database OID; retryable |
| Worker reservation missing/stale | database OID, job ID, generation; invariant failure, never release another slot |
| Shared-state capacity exhausted | registry name, capacity, database OID/target; fail without mutation |
| Drain timeout | epoch, phase, unacknowledged databases, reserved/live counts; drain remains active |
| Pause timeout | selected target IDs and remaining relevant jobs; pause remains active |
| Scheduled lock timeout | pgt_id, SQLSTATE, configured deadline; retryable and counted |
| Scheduled statement timeout | pgt_id, SQLSTATE, configured deadline; retryable and counted |
| Metrics request/collection timeout | endpoint phase and configured budget; scheduler continues |
| Resource limit | resource name, observed/estimated size, effective limit, hard maximum |
| Alert payload reduction failure | event and final byte count; do not send malformed payload |
| Maintenance batch failure | category, bound, last processed key; retain backlog |

Rules:

- SQLSTATE metadata is captured before converting a PostgreSQL report to text.
- No worker or queue reconciliation error becomes zero/free capacity.
- No shared-memory capacity failure becomes `"OK"`.
- No timeout cancels a completed catalog mutation unless PostgreSQL rolls back
  that mutation transactionally.
- Error messages include database OID, pgt_id/job identity, configured limit,
  and remediation where useful.
- Refresh history and scheduler jobs use stable machine-readable codes in
  addition to human-readable messages.
- Broad catches may protect a scheduler loop only after the affected job,
  reservation, and catalog outcome are made explicit.

## 7. Upgrade and Compatibility Plan

### 7.1 Migration order

The `0.84.0 -> 0.85.0` migration runs transactionally:

1. Add refresh-history typed error columns.
2. Add scheduler-job typed outcome and worker-slot generation columns.
3. Add stream-table remediation and last-error columns with safe defaults.
4. Backfill existing active rows to neutral remediation values.
5. Add and validate remediation/error-code constraints.
6. Create/replace `drain()`, nullable `is_drained()`, and
   `resume_after_drain()`.
7. Update diagnostic views/functions for new fields.
8. Apply exact API-policy ACLs and comments.
9. Update GUC-visible generated metadata through the new binary.
10. Insert the v0.85.0 migration audit row only after all DDL succeeds.

Shared memory is initialized by the v0.85.0 binary at postmaster start. The
upgrade guide therefore requires a PostgreSQL restart before relying on new
database-scoped state or worker-slot behavior. The scheduler must fail closed
if v0.85.0 SQL is installed while the required v0.85.0 shared-memory layout is
unavailable.

### 7.2 Breaking and tightened behavior

This is intentionally a minor release:

- `is_drained()` returns NULL when no drain was requested, false while
  draining, and true only when persistently drained.
- `drain()` timeout no longer resumes dispatch.
- explicit `resume_after_drain()` is required unless the postmaster restarts.
- `pause_scheduler()` no longer returns success when shared state is full or
  selected work exceeds its timeout.
- `max_parse_nodes = 0` no longer means unlimited.
- parser depth/node/expansion maxima are reduced to defensible hard ceilings.
- bulk API and control target defaults may reject previously accepted oversized
  requests.
- scheduled work gains finite lock and statement deadlines.
- OOM and lock-timeout failures count toward suspension even when remediation
  is enabled.
- metrics bind behavior becomes explicit and defaults to loopback.
- stale/misleading fuzz target names and corpus paths change.

Provide preflight queries for:

- current parser/complexity GUCs above new maxima;
- scripts that assume `is_drained()` is always non-NULL;
- maintenance scripts that rely on drain timeout to auto-resume;
- bulk calls above the new default;
- metrics ports intended for remote access without an explicit bind address;
- stream tables already near `max_consecutive_errors`.

Do not silently clamp session settings or automatically expose metrics on all
interfaces.

### 7.3 Rollback

The SQL columns are additive, but the shared-memory layout and drain semantics
are not binary-compatible. Rollback requires:

1. explicit `resume_after_drain()` or postmaster stop;
2. backup before upgrade;
3. restore of the v0.84.0 database/extension state;
4. restart with the v0.84.0 shared library and shared-memory layout.

Do not load the v0.84.0 library into a postmaster initialized with v0.85.0
shared memory. Do not ship a down migration that guesses drain/worker state or
discards v0.85.0 audit history in place.

- Remove claims that timeout or a no-op catalog update resumes drain.

No new ADR is required if the design stays within the existing in-process
scheduler. Add an ADR only if implementation discovers that a persistent SQL
catalog, external process, or changed cluster-vs-database drain scope is
necessary.

## 10. Risks and Mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| Shared-memory layout underestimates database/worker capacity | High | Compile-time maxima aligned with supported GUC maxima; typed capacity failure; no overwrite/fallback |
| PostgreSQL worker limits change after SIGHUP | Medium | Refresh immutable capacity snapshot on SIGHUP and expose configured/effective values |
| Reconciliation frees a slow-start reservation | Critical | Slot identity/generation; reserved state is not inferred from absent live PID; fail closed |
| Reconciliation leaks capacity after an unrecoverable catalog error | Medium | Preserve reservation, expose degraded state/alert, retry reconciliation; never invent capacity |
| Drain becomes stuck because a scheduler dies before acknowledgement | High | Launcher proves dead PID, clears stale database slot, reconciles its reservations, then reevaluates drain |
| Explicit drain resume surprises existing automation | High | Minor-release note, preflight grep guidance, nullable state, clear runbook and API |
| Statement deadline interrupts a legitimate large refresh | Medium | 15-minute default, configurable up to 24 hours, typed history, manual refresh remains caller-controlled |
| Timeout SQLSTATE loses context across pgrx panic conversion | High | Capture `ErrorReport` fields at the closest guarded boundary; unit and injected E2E |
| Self-heal memory reduction is not applied to every work_mem path | High | One `RefreshRuntimeTuning` value passed through all planner-hint/merge paths; grep/test inventory |
| Remediation masks repeated failures | Critical | Every qualifying failure increments persistent errors; common recorder; suspension tests |
| Queue gauge changes before transaction commit | Medium | Update after successful catalog transition/transaction; periodic catalog reconciliation |
| Maintenance backlog progresses too slowly | Medium | Full-batch backlog schedules next tick; category rotation; configurable bounded batch |
| Metrics collection still delays a tick | Medium | Collect only on scrape, transaction-local deadline, measure/report collection latency; no network blocking |
| Non-blocking metrics response is truncated for slow readers | Low | Connection state with bounded partial writes until deadline; explicit 503/close behavior |
| Alert reduction removes critical identity | High | Reserve mandatory fields first; property tests at max Unicode sizes |
| Lower parser/bulk maxima reject real workloads | Medium | Preflight, configurable defaults up to hard max, preview errors with observed/limit values |
| Interrupt during control call leaves surprising state | Medium | Full prevalidation and atomic batch; document safe persistent requested state; idempotent explicit resume |
| Renamed fuzz targets lose corpus history | Medium | Move corpus directories with target rename and verify replay counts |
| Dynamic SQL lint creates noisy false positives | Medium | Fixture-driven conservative analysis and narrow reviewed marker; no broad path allowlist |

Correctness, durability, and conservative capacity accounting take precedence
over maximum scheduler availability. When state cannot be proven, stop
dispatching rather than exceed limits or lose a committed change.

## 11. Suggested Pull Request Sequence

1. **State/schema foundations:** pure state machines, new GUCs, catalog columns,
   migration, unit tests.
2. **Database scoping:** scheduler registry, pause/watermark/health/queue keys,
   two-database tests.
3. **Worker accounting:** effective limit, exact reservations, generation,
   spawn/crash reconciliation.
4. **Drain and controls:** persistent state, explicit resume, selected-node
   waits, interruptible bounded APIs, docs.
5. **Deadlines and outcomes:** local timeouts, SQLSTATE capture, common recorder,
   history/job diagnostics.
6. **Self-healing:** effective memory/backoff, success reset, suspension
   accounting, serial/parallel injection.
7. **Queue and maintenance:** exact gauges, bounded normal-uptime pruning,
   backlog metrics.
8. **Metrics and alerts:** lazy non-blocking scrape path, bind address,
   structured UTF-8-safe alerts, timestamp throttles.
9. **Limits and assurance:** finite resource ceilings, unified fuzz inventory,
   real parser/decoder properties, mandatory SQL lint.
10. **Release closeout:** multi-database stress, sustained soak, full docs,
    upgrade parity, manual CI/stability/fuzz gates.

Each PR must leave the scheduler fail-closed and testable. Do not land new
drain semantics without the resume API, new catalog columns without migration,
or worker reservations without every failure/exit transition.

## 12. Definition of Done

- [ ] Every coordinator computes the same effective worker limit including
      PostgreSQL `max_parallel_workers`.
- [ ] Reservation plus live workers never exceeds the effective limit.
- [ ] Delayed startup, spawn failure, worker exit, worker crash, and
      coordinator crash preserve exact worker-slot accounting.
- [ ] Reconciliation never replaces reserved/live state with an aggregate
      sample.
- [ ] Pause, health, queue, and watermark shared state are keyed by database
      OID.
- [ ] Identical `pgt_id` values in two databases are fully independent.
- [ ] Shared-state capacity exhaustion returns a typed failure and no partial
      mutation.
- [ ] Pause waits only for selected local nodes.
- [ ] Drain has distinct Running, Draining, and Drained SQL-visible states.
- [ ] Drain remains active after completion and timeout.
- [ ] Only `resume_after_drain()` or postmaster restart clears drain.
- [ ] Drain completion verifies all live database acknowledgements and no
      inline/reserved/live/queued work.
- [ ] Scheduled inline and dynamic refreshes apply finite lock and statement
      deadlines.
- [ ] Timeout outcomes retain stable code, SQLSTATE, retryability, and message
      in history/jobs.
- [ ] Timeout/cancellation releases capacity and permits drain.
- [ ] Inline and dynamic workers call one persistent outcome recorder exactly
      once.
- [ ] OOM remediation lowers effective per-table memory with a 25% floor.
- [ ] Lock-timeout remediation increases persistent capped backoff.
- [ ] Three successful cycles reset remediation.
- [ ] Remediated failures still increment errors and eventually suspend.
- [ ] Queue depth equals currently queued catalog rows after every transition.
- [ ] Queue reconciliation preserves the prior value on query failure.
- [ ] Terminal jobs are pruned during normal uptime.
- [ ] History/job/cleanup maintenance performs at most the configured batch per
      category per tick and progresses under continuous load.
- [ ] Idle metrics polling executes zero collection queries.
- [ ] Slow/malformed clients do not block scheduler dispatch and respect the
      configured request deadline.
- [ ] Metrics bind address, logs, and documentation agree.
- [ ] Every alert producer emits parameterized valid JSON/UTF-8 at most 7,900
      bytes.
- [ ] Reminder cadence uses last successful emission timestamps.
- [ ] Parse, grouping, CTE, bulk, pause, and timeout inputs have finite defaults
      and hard maxima.
- [ ] Oversized input fails before expensive work or mutation.
- [ ] Cancelled/disconnected control calls leave complete, documented,
      recoverable scheduler state.
- [ ] Smoke and nightly fuzz workflows derive and run the same complete target
      inventory.
- [ ] Production CDC decode and SQL-facing parser/rewrite paths receive
      adversarial property coverage.
- [ ] Required property case counts and seeds are asserted/reported.
- [ ] Variable-built dynamic SQL detection is part of `just lint` and PR CI.
- [ ] Fresh and v0.84.0-upgraded catalogs have identical normalized v0.85.0
      manifests.
- [ ] Multi-database stress with delayed startup and forced exits passes.
- [ ] Sustained soak has no leaked slots, stuck drain, unbounded catalog
      growth, or unexplained refresh mismatch.
- [ ] `just fmt`, `just lint`, unit, integration, light E2E, targeted full E2E,
      `just test-all`, fuzz, stability, and complete manual CI pass.

No worker-limit oversubscription, cross-database state bleed, transient drain,
unbounded scheduler tick, malformed alert, success-shaped control failure, or
unexplained data mismatch may be waived for v0.85.0.
